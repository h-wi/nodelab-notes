세 가지 계층: 역할, 실행 위치, 객체

왜 알아야 하나"control plane이 가장 상위인가?" 같은 질문은 계층이 하나라고 가정한다. 실제로는 계층이 세 개다. 각 계층은 다른 질문에 답한다.

  • 역할: 누가 결정하고(control plane), 누가 실행하는가(kubelet).
  • 실행 위치: 프로세스가 실제로 어느 상자 안에 있는가.
  • 객체: YAML로 만드는 것들이 서로를 어떻게 만들고 연결하는가.
자주 하는 오해"가장 상위"를 물을 때는 먼저 어느 계층인지 정한다. control plane은 ①에서 가장 위다. 하지만 ③의 객체 트리에는 없다.

프로세스, 사용자, 권한process · UID

왜 알아야 하나"Permission denied"는 가장 흔한 오류다. 원인은 항상 "어떤 사용자의 프로세스가, 누구 소유의 파일에, 어떤 동작을 했는가"이다.

  • 프로세스는 실행 중인 프로그램이다. 모든 프로세스는 UID(사용자 번호)를 가진다.
  • 파일은 소유자, 그룹, 권한 비트(rwx)를 가진다.
  • 커널은 이름이 아니라 번호(UID, GID)를 비교한다. 이름은 사람을 위한 표시다.
  • root(UID 0)는 대부분의 권한 검사를 통과한다.
내 환경에서taehwi(UID 1000)와 nodelab(UID 1001)은 다른 사용자다. 계정 분리는 파일과 프로세스의 접근 권한을 나눈다. CPU와 메모리는 나누지 않는다. 자원을 나누려면 cgroup이 필요하다.
자주 하는 오해컨테이너 안의 UID 1000과 호스트의 UID 1000은 같은 번호다. 이름이 달라도 커널에게는 같은 사용자다. 그래서 볼륨 파일의 소유자가 이상하게 보일 수 있다.
직접 확인 
id                       # 내 UID, GID, 그룹
ls -ln ~                 # 이름 대신 번호로 소유자 표시
ps -o pid,uid,user,cmd -u nodelab

파일시스템과 마운트mount

왜 알아야 하나리눅스에서 경로는 디스크를 알려 주지 않는다. /mnt/hdd는 HDD다. /var/lib/docker는 SSD다. 성능 실험에서 데이터가 어느 장치에 있는지 모르면 결과를 설명할 수 없다.

  • 리눅스는 디렉터리 트리를 하나만 가진다. 맨 위는 /다.
  • 장치(디스크, 파티션)의 파일시스템을 트리의 한 디렉터리에 붙인다. 이것을 마운트라고 한다.
  • 그 디렉터리를 마운트 지점이라고 한다. 그 아래의 파일은 붙은 장치에 저장된다.
  • 바인드 마운트는 장치가 아니라 다른 디렉터리를 다른 경로에 다시 보이게 한다. 컨테이너 볼륨이 이 방법을 쓴다.
내 환경에서루트(/)는 SATA SSD의 ext4(LVM)다. /mnt/hdd는 2 TB SMR HDD다. kind 노드와 PVC 데이터는 기본적으로 Docker 저장 영역, 즉 SSD에 있다.
직접 확인 
findmnt -D               # 마운트 목록과 크기
findmnt -T /mnt/hdd      # 이 경로는 어느 장치인가
lsblk -f                 # 장치와 파일시스템

du와 df는 왜 다른 값을 보이는가

왜 알아야 하나실습 A에서 "노드를 몇 개 더 둘 수 있는가"를 계산한다. 두 명령의 값이 다르면 어느 쪽을 믿을지 알아야 한다.

dudf
질문이 디렉터리 아래 파일들은 얼마나 큰가?이 파일시스템에 남은 공간은 얼마인가?
방법파일을 하나씩 찾아서 더한다파일시스템에 사용 블록 수를 묻는다
범위지정한 경로 아래, 내가 볼 수 있는 파일마운트된 파일시스템 전체

du -h는 모든 하위 디렉터리를 한 줄씩 보인다. 마지막 줄이 합계다. du -sh는 합계 한 줄만 보인다(-s = summary). 어느 디렉터리가 큰지 볼 때는 du -h --max-depth=1을 쓴다.

값이 다른 이유:

  • 지워졌지만 열려 있는 파일. 프로세스가 파일을 열고 있으면 삭제 후에도 공간이 남는다. du는 못 보고 df는 센다.
  • 예약 블록. ext4는 기본으로 약 5%를 root용으로 남긴다. df의 Used + Avail이 Size보다 작다.
  • 다른 파일시스템. du는 경로 안의 다른 마운트도 더한다. -x를 쓰면 막는다.
  • 권한. 읽을 수 없는 디렉터리는 du가 세지 못한다.
내 환경에서"공간이 얼마나 남았나"는 df로 본다. "노드 하나가 얼마나 쓰나"는 du로 본다. 2026-10-12 관찰: 루트 226G 중 약 156G 여유, 기존 노드 PVC bitcoin-data는 약 27G 사용. 노드 데이터는 kind 노드 안에 있으므로, Pod 안에서 du를 실행하면 노드 크기를 정확히 볼 수 있다.
직접 확인 
df -h /                                         # SSD 여유 공간
kubectl -n bitcoin-lab exec deploy/bitcoin-signet -- \
  du -sh /home/bitcoin/.bitcoin/signet          # 노드 하나의 크기
sudo lsof +L1 | head                            # 지워졌지만 열린 파일

docker 그룹은 root와 같다

왜 알아야 하나계정의 권한을 정할 때 필요하다. nodelab에 docker 그룹을 주면 사실상 root를 주는 것이다.

  • Docker 데몬(dockerd)은 root로 실행된다.
  • docker 그룹은 데몬의 소켓 /var/run/docker.sock에 쓸 수 있다.
  • 그래서 docker 그룹 사용자는 데몬에게 무엇이든 요청할 수 있다. 예: 호스트의 /를 컨테이너에 마운트한다. 그 컨테이너 안에서 root로 호스트 파일을 바꾼다.
  • 결과: sudo 없이도 호스트 root와 같은 일을 할 수 있다.
내 환경에서개인 실습 서버에서는 편의를 위해 허용할 수 있다. 다만 "nodelab은 권한이 적은 계정"이라고 생각하면 안 된다. 선택은 편의와 위험을 같이 보고 한다.
직접 확인 
ls -l /var/run/docker.sock     # 소유 그룹이 docker
getent group docker            # 누가 그룹에 있는가

메모리, 페이지 캐시, 스왑

왜 알아야 하나bitcoind 성능은 메모리와 디스크 사이에서 정해진다. "메모리가 부족하다"와 "캐시가 많다"를 구분하지 못하면 측정을 잘못 읽는다.

  • 커널은 빈 메모리를 놀리지 않는다. 디스크에서 읽은 내용을 메모리에 남긴다. 이것이 페이지 캐시다.
  • 페이지 캐시는 필요하면 즉시 비울 수 있다. 그래서 free의 available을 본다. free 열은 거의 의미가 없다.
  • 스왑은 메모리 내용을 디스크로 내보내는 공간이다. 스왑이 많이 쓰이면 느려진다.
  • 메모리 한도를 넘으면 커널의 OOM killer가 프로세스를 종료한다. 단, 그 전에 먼저 페이지 캐시를 버린다.
  • cgroup은 페이지 캐시도 그 cgroup의 메모리로 센다. 그래서 컨테이너의 메모리 사용량에는 캐시가 들어 있다.
  • 스왑 used가 크면 과거에 메모리 압박이 있었다는 흔적이다. 커널은 그 내용이 다시 필요할 때까지 스왑에 둔다.
자주 하는 오해같은 실험을 두 번 하면 두 번째가 빠를 수 있다. 데이터가 페이지 캐시에 남아 있기 때문이다. 이것을 "캐시 효과"라고 하고, 실험 기록에 남긴다.
내 환경에서promet의 메모리는 total 14Gi다. 2026-10-13 IBD가 끝난 뒤: available 9.7Gi, buff/cache 8.4Gi, 스왑 used 2.3Gi. 메모리를 나눠 쓰는 것: kind 상자(8G), indra-collector(2G), namu-crawler(2.5G), 한도 없는 indra 배치.

캐시를 잃으면: refault와 thrashing

왜 알아야 하나메모리가 부족해도 프로세스는 바로 죽지 않는다. 커널은 먼저 page cache를 버린다. 그러면 프로그램은 오류 없이 느려지기만 한다. 그래서 이 문제는 숫자로만 찾을 수 있다.

  • cgroup은 page cache도 그 cgroup의 메모리 사용량으로 센다.
  • cgroup이 한도에 닿으면 커널은 먼저 캐시를 버린다(evict). 그래도 모자라면 OOM killer가 프로세스를 종료한다.
  • 버린 데이터를 다시 읽으면 커널은 refault로 센다. refault가 계속되는 상태가 thrashing이다.

cgroup: 자원을 세고 제한하기

CPU limit의 실체: cpu.max와 throttling

왜 알아야 하나"CPU 한도가 느리게 했는가?"에는 추측하지 않고 숫자로 답할 수 있다. Kubernetes의 limits.cpu는 커널의 cpu.max 파일이 된다. 커널은 멈춘 횟수와 시간을 cpu.stat에 센다.

  • m은 밀리(1/1000)다. 1000m = 1코어, 250m = 0.25코어. 대문자 M은 메가(백만)다.
  • cpu.max의 형식은 <quota> <period>이고, 단위는 마이크로초(µs)다. 100000 100000은 "100ms마다 CPU 시간 100ms까지", 즉 1코어다. 500m이면 50000 100000이다.
  • 창 안에서 quota를 다 쓰면 커널은 다음 창까지 그 cgroup을 멈춘다. 이것이 throttling이다.
cpu.stat의 줄뜻계산
usage_usec지금까지 쓴 CPU 시간의 합÷ 걸린 시간 = 평균 사용 코어 수
nr_periods실행할 일이 있었던 창의 수—
nr_throttled그중 멈춘 창의 수÷ nr_periods = 멈춘 창의 비율
throttled_usec멈춘 시간의 합한도를 없애면 줄일 수 있는 최대 시간
내 환경에서2026-10-13에 bitcoin-node-1의 IBD 기록을 읽었다. limit 1000m → cpu.max = 100000 100000. 멈춘 창은 16,441 / 625,561(약 2.6%), 멈춘 시간은 약 625초(약 10분)였다. IBD는 약 4시간 53분이었으므로 CPU 한도는 주된 원인이 아니었다. 평균 사용은 약 7,922초 ÷ 17,570초 = 약 0.45코어였다. 즉 CPU는 시간의 절반 넘게 다른 것을 기다렸다.
자주 하는 오해throttling이 있다고 CPU가 원인인 것은 아니다. 비율과 시간을 계산한다. 평균 사용이 한도보다 훨씬 낮으면, CPU는 디스크나 네트워크를 기다린 것이다.

memory.events와 .local: 무엇을 세는가

왜 알아야 하나숫자를 비교하기 전에, 그 숫자가 무엇을 세는지 먼저 확인해야 한다. memory.events는 하위 cgroup의 이벤트까지 더한다. 그래서 부모의 값만 보고 "부모가 가득 찼다"고 말하면 틀릴 수 있다.

  • memory.events: 이 cgroup과 모든 하위 cgroup의 이벤트를 더한 값이다(계층 값).
  • memory.events.local: 이 cgroup 자신의 이벤트만 센다.
  • max: 사용량이 이 cgroup의 memory.max를 넘으려 한 횟수다. 이때마다 커널은 메모리를 회수한다. 먼저 page cache를 버린다.
  • 부모가 가득 차면 커널은 자식의 page cache도 회수한다. 자식의 한도에 여유가 있어도 그렇다. 이때 늘어나는 것은 부모의 max다. 자식의 max는 늘지 않는다.
내 환경에서실습 F 실행 2(상자 4GiB, 2026-10-14): 상자의 memory.events.local max는 21,206,152 → 23,813,701(+2,607,549)이 되었다. 같은 기간 node-1 컨테이너의 max는 0, peak는 1.44GiB였다. 그래도 refault는 969GB였다. 그래서 회수 압력은 상자 층에서 왔다. 주의: 이 증가분에는 상자를 4GiB로 줄인 순간의 회수(그때 memory.current 약 4.97GiB)와, 작업이 끝난 뒤의 대기 시간도 들어 있다.

아직 모르는 것. 실행 1(상자 8GiB)에서 컨테이너의 max는 113번뿐인데 refault는 412GB였다. Pod 층의 cgroup(한도 2Gi, pause 컨테이너 포함)이 먼저 가득 찼을 수 있다. 확인하지 않았다.

자주 하는 오해"부모의 max가 크다 = 부모가 가득 찼다"는 틀릴 수 있다. 하위 cgroup이 각자 자기 한도에 닿은 횟수도 부모의 값에 더해진다. 2026-10-13의 "상자가 2,400만 번 넘게 가득 찼다"도 이 계층 값이었다. 10-14에 .local로 다시 보니 약 83%가 상자 자신이었다. 결론은 유지되었지만, 이제 비교는 .local로 한다.

YAML 구조와 들여쓰기

왜 알아야 하나YAML에서 들여쓰기는 구조 자체다. 공백 두 칸이 틀리면 값이 다른 부모에 붙는다. 오류가 안 나고 다르게 동작할 때도 있다.

  • YAML은 두 가지로만 되어 있다. 맵(키: 값)과 리스트(- 항목).
  • 같은 깊이에 있는 키는 같은 부모에 속한다. 깊이는 공백으로 정한다. 탭은 쓰지 않는다.
  • -는 "리스트의 새 항목"이다. 그 뒤의 키들은 그 항목에 속한다.
  • 모든 매니페스트는 4개의 최상위 키를 가진다: apiVersion, kind, metadata, spec.
  • ---는 문서 구분선이다. 파일 하나에 객체 여러 개를 넣을 때 쓴다. kubectl apply는 이 선으로 나누어 객체를 하나씩 보낸다.
  • - 다음 첫 글자가 그 목록 항목의 기준선이다. 같은 항목의 키는 이 기준선에 맞춘다. 하위 키는 2칸 더 들어간다.
apiVersion: apps/v1          # 어느 API 그룹, 버전
kind: Deployment             # 어떤 객체
metadata:                    # 이름표 (맵)
  name: bitcoin-signet
  namespace: bitcoin-lab
spec:                        # 원하는 상태
  replicas: 1
  template:                  # 만들 Pod의 모양
    spec:
      containers:            # 리스트
      - name: bitcoind       # 첫 번째 항목 시작
        image: …             # name과 같은 깊이 = 같은 항목
        args: ["-signet"]
자주 하는 오해image:가 - name:보다 두 칸 왼쪽에 있으면, image는 컨테이너 항목이 아니라 spec에 붙는다. 파일을 적용하기 전에 kubectl apply --dry-run=server -f 파일로 검사한다.

오류 경로 읽기. unknown field "spec.volumeClaimTemplates[0].name"에서 점(.)은 "안으로", [0]은 "목록의 첫 항목"이다. 기대한 경로는 …[0].metadata.name이었다. 즉 name이 한 단계 덜 들어가 있었다. API 서버는 종류마다 허용 키 목록(스키마)을 알고, 모르는 키는 거부한다(strict decoding).

직접 확인

kubectl apply --dry-run=server -f bitcoin.yaml

Kubernetes namespace

왜 알아야 하나kubectl get pods에 내 Pod가 없으면, 보통 namespace를 빠뜨린 것이다.

  • namespace는 API 객체를 묶는 이름 공간이다. 폴더와 비슷하다.
  • 같은 namespace 안에서는 이름이 겹칠 수 없다. 다른 namespace에서는 겹쳐도 된다.
  • -n을 안 쓰면 default namespace를 본다.
  • namespace에 속하지 않는 객체도 있다. Namespace 자체, Node, PV, StorageClass는 클러스터 전체에 속한다. 그래서 kubectl get ns, kubectl get nodes에는 -n을 쓰지 않는다. 목록: kubectl api-resources --namespaced=false.
  • namespace만으로는 CPU, 메모리가 나뉘지 않는다. 한도는 limits나 ResourceQuota로 건다.
내 환경에서노드 객체는 전부 bitcoin-lab namespace에 있다. 매번 -n bitcoin-lab을 쓴다. 아니면 기본값을 바꾼다: kubectl config set-context --current --namespace=bitcoin-lab. 다른 namespace: kube-system(control plane, CoreDNS), local-path-storage(PVC 공간을 만드는 프로그램).

Service

왜 알아야 하나Pod IP는 바뀐다. 다른 Pod가 바뀌는 IP를 따라갈 수 없다. Service는 바뀌지 않는 이름과 주소를 준다.

headless Service

왜 알아야 하나노드끼리 연결할 때(실습 D), 각 노드는 "아무 노드"가 아니라 "특정 노드"에 연결해야 한다. headless Service가 Pod마다 고정 DNS 이름을 준다.

  • headless Service는 clusterIP: None인 Service다. 가상 IP가 없고, 나눠 보내지도 않는다.
  • 대신 DNS가 Pod IP를 직접 돌려준다.
  • StatefulSet과 같이 쓰면 Pod마다 이름이 생긴다: bitcoin-node-0.bitcoin-node.bitcoin-lab.svc.cluster.local. 형식은 <Pod 이름>.<Service 이름>이다.
  • Pod가 다시 생겨서 IP가 바뀌어도 이 이름은 같다.
  • 가상 IP가 없으므로 kube-proxy는 이 Service에 포트 규칙을 만들지 않는다. 그래서 밖에서 들어오는 문으로는 쓸 수 없다. 밖으로 열려면 NodePort Service를 따로 만든다.
자주 하는 오해headless에도 DNS가 있다. 없는 것은 가상 IP다. 그리고 clusterIP에 127.0.0.1을 쓰면 거부된다. 127.0.0.1은 각 Pod 자신을 가리키고, Service IP는 10.96.0.0/16에서 자동으로 받거나(일반) None(headless)이어야 하기 때문이다.
내 환경에서bitcoind에 -addnode=bitcoin-node-0.bitcoin-node:38333처럼 쓴다. 같은 namespace 안에서는 뒷부분을 줄여도 된다. 2026-10-12 관찰: 연결된 주소가 10.244.0.11(Pod 범위)였다. Service 범위(10.96)가 아니다. 가상 IP 없이 Pod에 직접 연결한다는 증거다. 열린 질문: 2026-10-14 kubectl get svc에서 bitcoin-node가 ClusterIP 10.96.23.209로 보였다. 설계는 headless였다. 원인은 아직 확인하지 않았다. 확인: kubectl -n bitcoin-lab get svc bitcoin-node -o yaml | grep clusterIP.
직접 확인 
kubectl -n bitcoin-lab exec bitcoin-node-1 -- getent hosts bitcoin-node-0.bitcoin-node

NodePort Service와 externalTrafficPolicy

왜 알아야 하나Pod IP는 Pod가 다시 생길 때마다 바뀐다. 그래서 바깥 규칙에 Pod IP를 쓸 수 없다. NodePort는 Kubernetes 노드(kind 상자)에 바뀌지 않는 문을 만든다. 그 뒤의 Pod IP는 Kubernetes가 따라간다.

  • NodePort는 Service 종류의 하나다. 모든 Kubernetes 노드의 같은 포트에서 받는다. 포트는 30000–32767 중 하나다.
  • 실제 규칙은 kube-proxy가 노드의 iptables에 DNAT로 만든다. 받는 주소를 대상 Pod IP:targetPort로 바꾼다.
  • kubectl get svc의 38333:30333/TCP는 "노드 포트 30333으로 받아서 Service 포트 38333으로"라는 뜻이다.
  • selector로 대상 Pod를 고른다. StatefulSet은 Pod마다 statefulset.kubernetes.io/pod-name 라벨을 자동으로 붙인다. 이 라벨로 Pod 하나만 고를 수 있다.
  • headless Service는 포트 규칙을 만들지 않는다. 그래서 밖으로 여는 문은 NodePort를 따로 만든다.

왜 알아야 하나메모리가 부족하면 커널은 프로세스 하나를 골라 종료한다. 누구를 먼저 고를지는 점수로 정한다. Kubernetes는 requests와 limits로 이 점수를 정한다.

kind 클러스터의 구조

왜 알아야 하나kind는 실제 서버 클러스터와 다르게 동작하는 부분이 있다. 측정 결과에 kind 때문인 부분이 섞일 수 있다.

  • kind는 "Kubernetes in Docker"다. Kubernetes 노드 하나 = Docker 컨테이너 하나다.
  • 그 컨테이너 안에서 kubelet, containerd, API 서버가 실행된다. Pod 컨테이너는 그 안의 containerd가 만든다.
  • 그래서 호스트의 docker ps에는 Pod가 안 보인다. kind 노드만 보인다.
  • 클러스터 네트워크는 Docker 네트워크 안에 있다. 외부에서 Pod로 들어오려면 별도 포트 매핑이 필요하다.
  • kind의 포트 매핑(extraPortMappings)은 클러스터를 만들 때만 넣을 수 있다. 이미 만든 클러스터에서는 호스트의 DNAT 규칙으로 kind 상자의 NodePort에 보낸다(포트 포워딩 = DNAT).
내 환경에서노드는 bitcoin-lab-control-plane 하나다. 모든 Pod가 이 컨테이너 안에서 같은 SSD, 같은 CPU를 나눠 쓴다. "노드 여러 개"는 Kubernetes 노드가 아니라 bitcoind Pod 여러 개다. "노드"의 두 뜻을 본다. kind 노드 컨테이너에는 Docker 한도가 있다. 2026-10-13 확인: 메모리 4GiB(같은 날 8GiB로 늘림), CPU 3.5코어. 바꾸는 명령: docker update --memory 8g --memory-swap 8g bitcoin-lab-control-plane. 컨테이너는 재시작하지 않는다. 2026-10-14 확인: kind 상자는 Docker 네트워크에서 172.18.0.2다. promet은 이 Docker 네트워크의 브리지에 붙어 있어서 이 주소에 바로 닿는다. 실습 F 뒤 메모리는 다시 8GiB다.
자주 하는 오해kind 안의 kubelet은 이 Docker 한도를 모른다. 그래서 kubectl describe node의 메모리는 상자 크기가 아니라 호스트 메모리다. 2026-10-13의 IBD가 느렸던 원인이 이 차이였다(refault).

네트워크 NETWORK

노드는 네트워크 프로그램이다. 피어 연결 수와 전송량은 성능 측정의 기본 값이다.

IP 주소, 포트, TCP 연결

왜 알아야 하나"연결이 안 된다"의 원인은 넷 중 하나다. 주소가 틀리다. 포트가 틀리다. 듣는 프로그램이 없다. 중간에서 막는다.

  • IP 주소는 장치(정확히는 네트워크 인터페이스)를 찾는다.
  • 포트는 그 장치 안의 프로그램을 찾는다. 0–65535 번호다.
  • TCP 연결은 네 값으로 구분한다: 내 IP, 내 포트, 상대 IP, 상대 포트.
  • 서버는 한 포트에서 listen(대기)한다. 클라이언트가 connect(접속)한다.
  • 포트는 IP마다 따로 있다. 같은 IP에서는 한 포트를 한 프로그램만 기다릴 수 있다. 두 번째 프로그램은 Address already in use 오류를 받는다. IP가 다르면 같은 번호를 써도 된다. 그래서 StatefulSet의 Pod 2개가 모두 38333에서 기다린다.
  • 바깥 포트와 안쪽 포트의 번호는 달라도 된다. 예: kind 상자의 30333 → Pod의 38333(NodePort).

IP의 본질. IP 주소는 "패킷을 어디로 보낼지"를 정하는 번호다. 패킷마다 보내는 주소와 받는 주소가 있다. 라우터와 커널은 받는 주소만 보고 다음 방향을 정한다. IP는 기계가 아니라 네트워크 인터페이스에 붙는다. IP는 기계까지, 포트는 그 안의 프로그램까지 데려간다.

네트워크 인터페이스: 랜카드, lo, veth

왜 알아야 하나IP는 기계가 아니라 인터페이스에 붙는다. Pod IP가 왜 생기고 왜 사라지는지 알려면 인터페이스를 알아야 한다.

네트워크 인터페이스는 커널 안의 "패킷 출입구" 객체다. 출입구 뒤에 무엇이 있는지는 종류마다 다르다.

종류뒤에 있는 것예
물리실제 랜카드. 패킷이 케이블로 나간다eno1, enp3s0 (이름은 장치마다 다르다)
lo없음. 보낸 패킷이 바로 자기에게 돌아온다127.0.0.1
veth가상 케이블. 항상 양 끝 한 쌍으로 생긴다Pod의 eth0과 노드 쪽 veth…
bridge가상 스위치. 여러 veth를 묶는다docker0, br-… (kind 네트워크)

  • Pod는 자기가 랜카드를 가졌다고 생각한다. 실제로는 가상 케이블의 한쪽 끝이다.
  • Pod가 지워지면 veth도, 그 IP도 사라진다.
자주 하는 오해인터페이스가 곧 랜카드는 아니다. 호스트의 인터페이스 대부분은 커널이 만든 가상 장치다.

Pod IP는 어디서 오고, 왜 바뀌는가

왜 알아야 하나Pod IP는 Pod를 다시 만들 때 바뀔 수 있다. 그래서 bitcoind 설정에 IP 대신 이름을 쓴다. 이 흐름을 알면 "왜 이름이 필요한가"를 설명할 수 있다.

  1. scheduler가 Pod를 둘 노드를 정한다.
  2. 그 노드의 kubelet이 containerd에 컨테이너 생성을 요청한다.
  3. containerd가 CNI 플러그인을 부른다. CNI는 netlink(커널 네트워크 설정용 소켓)로 veth 쌍을 만든다.
  4. CNI의 IPAM(IP 주소 관리)이 노드의 Pod 범위에서 빈 주소 하나를 고른다.
  5. kubelet이 그 IP를 API 서버에 보고한다 (status.podIP).
  6. CoreDNS가 API 서버를 보고 DNS 응답을 바꾼다. bitcoind는 이름만 알면 된다.
자주 하는 오해같은 IP가 다시 나올 수도 있다. 하지만 보장되지 않는다. 보장이 없으므로 이름이 필요하다.
내 환경에서kind의 기본 CNI는 kindnet이다. Pod 범위는 10.244.0.0/16이다. 2026-10-12 관찰: node-0에서 bitcoin-node-1.bitcoin-node가 10.244.0.11로 바뀌었다.

kubectl -n bitcoin-lab get pod -o wide   # IP 열과 NODE 열

리슨 주소: 127.0.0.1과 0.0.0.0

왜 알아야 하나프로그램이 "실행 중"이어도 다른 Pod에서 접속이 안 될 수 있다. 어느 주소에서 듣는지가 접근 범위를 정한다.

  • 127.0.0.1(localhost)에서 들으면 같은 net namespace 안에서만 접속할 수 있다. Pod에서는 같은 Pod 안이다.
  • 0.0.0.0에서 들으면 모든 인터페이스에서 접속할 수 있다.
  • bitcoind의 RPC는 기본으로 localhost에서만 듣는다. 이것은 안전을 위한 기본값이다.
  • 127.0.0.1은 network namespace마다 따로 있다. promet의 127.0.0.1과 Pod의 127.0.0.1은 다른 곳이다. 그래서 promet에서 bitcoin-cli를 실행해도 Pod 안의 RPC에 닿지 않는다.
내 환경에서kubectl exec로 Pod 안에서 bitcoin-cli를 실행하면 localhost이므로 바로 된다. 다른 Pod에서 RPC로 접속하려면 -rpcbind와 -rpcallowip를 같이 바꿔야 한다. 필요할 때만 바꾼다. 다른 방법은 kubectl port-forward다. API 서버를 거쳐 promet의 포트를 Pod 안의 포트에 잇는다. Kubernetes 권한이 있어야 쓸 수 있으므로, RPC를 Pod 밖에 열지 않아도 된다.

NAT와 포트 포워딩

왜 알아야 하나내 노드는 밖으로 연결(outbound)할 수 있다. 하지만 밖에서 내 노드로 연결(inbound)은 보통 안 된다. NAT가 몇 겹 있기 때문이다.

  • 집 공유기는 사설 IP(예: 192.168.x.x)를 공인 IP 하나로 바꾼다. 이것이 NAT다.
  • 안에서 나간 연결의 응답은 돌아온다. 밖에서 먼저 온 연결은 어디로 보낼지 모른다. 그래서 막힌다.
  • 포트 포워딩은 "이 포트로 오면 이 내부 주소로 보낸다"는 규칙이다(DNAT).
  • NAT 층은 직접 만든 것이 아니다. 각 층을 설치할 때 하나씩 따라온다: 공유기(집 인터넷), Docker(컨테이너에 172.18.x를 준다), Pod 네트워크(10.244.x, kind의 kindnet).
  • CGNAT: 통신사가 여러 집을 공인 IP 하나 뒤에 묶는 방식이다. 이 경우 공유기에 포트 포워딩을 해도 통신사 장비에서 막힌다. 판별: 공유기 관리 페이지의 WAN IP와 curl -4 ifconfig.me 값을 비교한다. 같으면 공인 IP를 직접 받는다. WAN IP가 100.64.x, 10.x, 172.16–31.x, 192.168.x이면 CGNAT 또는 이중 NAT다.
내 환경에서밖에서 Pod까지 가려면 NAT가 여러 번 있다. 공유기 → 호스트 → Docker 네트워크(kind 노드) → Pod 네트워크. 2026-10-14 확인: 집 인터넷은 SK 유선이고, 공유기 WAN IP와 curl -4 ifconfig.me 값이 같았다. 그래서 CGNAT도 이중 NAT도 없다. 공유기에는 이미 443 → promet:443(Caddy) 규칙이 있다. 같은 방법으로 38333을 연다(포트 포워딩 = DNAT).
자주 하는 오해"NAT를 너무 많이 만들었다"가 아니다. 공유기 NAT는 어느 집에나 있다. Docker 층은 kind 같은 실습 환경에만 있다. 실제 서버에 Kubernetes를 설치하면 이 층이 없다. 외부 연결을 받는 Pod는 hostNetwork나 hostPort로 Pod 층도 건너뛸 수 있다.
직접 확인 
curl -4 -s ifconfig.me; echo      # 밖에서 본 내 공인 IP
ip route | grep default           # via 뒤 = 공유기 관리 페이지 주소. 그곳의 WAN IP와 비교

연결의 방향과 conntrack

왜 알아야 하나내 노드는 밖으로 연결할 수 있다. 하지만 밖에서는 내 노드로 연결할 수 없다. 두 방향의 차이는 커널의 conntrack 표에서 온다. 이것을 알면 "왜 나가는 것만 되는가"를 설명할 수 있다.

  • 연결의 방향은 누가 먼저 SYN을 보냈는가로 정한다. SYN은 TCP 연결을 시작하는 첫 패킷이다.
  • 연결이 만들어진 뒤에는 양쪽 모두 데이터를 보낸다. 그래서 outbound 피어와도 블록을 주고받는다.
  • 안에서 나가는 패킷은 경계에서 보낸 주소가 바뀐다(SNAT, MASQUERADE). 이때 커널은 이 연결을 conntrack 표에 적는다: "이 주소와 포트로 오는 응답은 안쪽의 누구에게".
  • 응답이 오면 커널은 표를 보고 주소를 되돌린다. 그래서 outbound는 규칙 없이 된다.
  • 밖에서 먼저 온 SYN은 표에 기록이 없다. 커널은 이 패킷을 누구에게 줄지 모른다. 그래서 규칙(DNAT, 포트 포워딩)을 미리 만들어야 한다.
집의 비유네트워크
현관이 하나다공인 IP 하나 (NAT)
경비원의 장부: "이 편지의 답장은 내 방으로"conntrack 표
경비원에게 미리 적은 상시 지시: "38333으로 오는 손님은 내 방으로"포트 포워딩 (DNAT 규칙)
단지 정문을 통신사가 관리한다CGNAT (NAT)
내 환경에서2026-10-14 N-1: bitcoin-node-0의 getpeerinfo에서 외부 피어 10개는 모두 "inbound": false였다. 노드는 kind 안에 갇혀 있지 않다. 밖에서 들어온 연결은 0개였다. 유일한 inbound는 10.244.0.15:50246이다. node-1이 클러스터 안에서 먼저 연결해 왔다. 50246은 node-1 쪽의 임시 포트다.
자주 하는 오해"inbound가 없으면 제대로 된 풀 노드가 아니다"는 틀리다. 노드는 모든 블록을 직접 검증한다. 빠진 것은 다른 노드가 먼저 연결해 올 자리다. 그래서 새 노드의 IBD를 돕지 못한다.
직접 확인

  getpeerinfo | grep -E '"addr"|"inbound"|"connection_type"'

포트 포워딩 = DNAT: 경계마다 규칙 하나

왜 알아야 하나inbound를 열려면 경계마다 "이 포트로 오면 안쪽의 이 주소로"라는 규칙이 하나씩 필요하다. 하나라도 빠지면 연결은 그 경계에서 끝난다.

  • DNAT(Destination NAT)는 받는 주소(목적지)만 바꾼다. 보낸 주소는 바꾸지 않는다. 그래서 bitcoind는 피어의 진짜 주소를 본다.
  • 포트 포워딩은 DNAT 규칙의 다른 이름이다. 공유기 관리 페이지의 표도 DNAT 규칙이다.
  • 포트는 IP마다 따로 있다. 그래서 공인 IP의 38333은 한 곳으로만 보낼 수 있다. 다른 노드도 밖에 열려면 다른 바깥 포트를 쓴다.
  • 바깥 포트와 안쪽 포트의 번호는 달라도 된다. 예: kind 상자의 30333 → Pod의 38333. 공인 IP의 바깥 포트를 바꾸면 -externalip=주소:포트로 그 포트를 광고한다.
  • promet의 규칙은 2개다. (1) nat 표의 PREROUTING: promet LAN IP:38333으로 온 패킷의 받는 주소를 172.18.0.2:30333으로 바꾼다. (2) DOCKER-USER: 172.18.0.2:30333으로 가는 패킷을 허용한다. Docker는 자기가 publish하지 않은 포트로 가는 패킷을 막을 수 있기 때문이다.
  • iptables 규칙은 재부팅하면 사라진다. 계속 쓰려면 따로 저장한다(I-4b).
내 환경에서2026-10-14 상태: Pod(node-0은 이미 -listen=1) ✓, kind 상자(NodePort 30333) ✓. 남은 일: I-4 promet DNAT과 DOCKER-USER 허용 → I-4b 재부팅 뒤에도 유지 → I-5 공유기 38333 → promet:38333 → I-6 -externalip → I-7 외부 inbound 피어 확인. promet → kind 상자 구간은 kind의 extraPortMappings 대신 호스트 DNAT로 연다. extraPortMappings는 클러스터를 만들 때만 넣을 수 있어서, 클러스터를 다시 만들어야 하기 때문이다.
자주 하는 오해promet의 DNAT 규칙에서 받는 주소(-d promet LAN IP)를 빼면 안 된다. 빼면 규칙이 우리 노드의 outbound(외부 피어의 38333으로 가는 패킷)까지 잡아서 kind 상자로 되돌린다. 그리고 PREROUTING은 밖에서 들어오는 패킷만 본다. promet 자신이 보낸 패킷은 OUTPUT 체인을 지나므로, 시험은 집 안의 다른 기기에서 한다.
자주 하는 오해"기본 포트가 아니면 다른 노드가 연결하지 않는다"는 예전 버전의 동작이다. 지금의 Bitcoin Core는 다른 포트에도 연결한다. 피하는 것은 22(ssh)처럼 보통 인증이 필요한 서비스의 포트(bad port)뿐이다. 그래도 38333을 쓰는 이유는 DNS seed다. DNS 응답에는 포트가 없어서, bitcoind는 seed에서 받은 주소에 기본 포트를 붙인다(src/net.cpp). 다른 포트로 열면 seed로는 내 노드를 알릴 수 없다.
직접 확인 
sudo iptables -t nat -S PREROUTING          # DNAT 규칙 보기
sudo iptables -S DOCKER-USER                # Docker보다 먼저 보는 허용 규칙
sudo iptables -t nat -L PREROUTING -n -v    # 규칙마다 맞은 패킷 수

왜 알아야 하나두 방법 모두 "입구 하나로 받아서 안쪽의 맞는 곳으로 보낸다". 그러나 받는 쪽이 보는 보낸 주소가 다르다. 비트코인 P2P에서는 이 차이가 중요하다.

  • "리버스"인 이유: 보통의 프록시(회사 인터넷 프록시)는 손님 쪽을 대신해서 밖으로 나간다. 리버스 프록시는 반대로 서버 쪽을 대신해서 손님을 받는다.
  • HTTP는 진짜 손님 주소를 X-Forwarded-For 헤더에 적어서 넘긴다. 비트코인 P2P에는 이런 헤더가 없다.
  • 프록시를 쓰면 bitcoind는 모든 inbound 피어를 같은 주소로 본다. 그러면 두 가지가 망가진다. (1) inbound 자리가 차면 bitcoind는 피어 하나를 내보낸다. 이때 네트워크 그룹(IPv4는 /16)을 보고 다양성을 지킨다. 주소가 모두 같으면 이 보호가 없어진다. (2) 나쁜 피어 하나를 차단하면 모든 inbound가 같이 막힌다.
내 환경에서promet 호스트의 Caddy는 443에서 기다린다. 공유기에는 443 → promet:443 규칙이 있다. 그래서 443은 38333 대신 쓸 수 없다. 포트 하나는 한 곳으로만 보낼 수 있기 때문이다. 38333은 DNAT로 연다(포트 포워딩 = DNAT).

Tailscale: 문을 열지 않고 집에 들어가기

왜 알아야 하나SSH(22)와 RPC(38332)는 주인만 쓰는 문이다. 이 문을 포트 포워딩으로 열면 전 세계의 누구나 두드릴 수 있다. Tailscale은 공유기에 문을 열지 않고 집 밖에서 promet에 들어가게 한다.

  • Tailscale의 두 기기는 모두 outbound로 연결을 시작한다. outbound는 NAT를 저절로 지난다(conntrack).
  • 두 기기가 동시에 서로에게 패킷을 보낸다. 그러면 양쪽 공유기의 장부에 기록이 생기고, 상대의 패킷이 "응답"처럼 들어온다. 이 기법을 NAT hole punching이라고 한다.
  • 그래도 안 되면 Tailscale의 중계 서버(DERP)를 거친다. 느리지만 연결은 된다.
  • 내 tailnet(계정)에 등록된 기기만 들어온다. 그래서 공유기에 22번을 여는 것보다 안전하다.

HTTPS 443웹 손님포트 포워딩 → Caddy
SSH 22, RPC 38332나만Tailscale. 공유기에 열지 않는다

자주 하는 오해Tailscale 주소(100.64.0.0/10)는 CGNAT와 같은 대역이다. tailscale0 인터페이스의 주소를 공유기 WAN 주소와 헷갈리지 않는다. CGNAT 판별에는 공유기 관리 페이지의 WAN IP를 쓴다(NAT).

tailscale ip -4      # 이 기기의 100.x 주소

Signet

왜 알아야 하나Signet에서 얻은 측정값을 메인넷에 그대로 쓰면 안 된다. 차이를 알아야 결과를 바르게 말할 수 있다.

  • Signet은 테스트 네트워크다. 코인에 가치가 없다.
  • 블록은 정해진 서명자만 만들 수 있다. 그래서 testnet보다 블록 간격이 안정적이다.
  • 체인이 메인넷보다 훨씬 작다. 동기화가 빠르다.
  • 프로토콜과 코드 경로는 메인넷과 거의 같다. 그래서 내부 동작을 배우기에 좋다.
자주 하는 오해Signet 블록은 트랜잭션이 적다. 검증 부하와 UTXO 크기가 메인넷과 다르다. "Signet에서 X분"은 "메인넷에서 X분"을 뜻하지 않는다.

-listen과 피어 연결

왜 알아야 하나노드끼리 연결하려면(실습 D) 한쪽은 들어오는 연결을 받아야 한다. -listen이 이것을 정한다.

  • outbound: 내 노드가 먼저 연결한다. 기본으로 여러 개를 자동으로 만든다.
  • inbound: 다른 노드가 내 노드에 연결한다. 내 노드가 P2P 포트에서 listen해야 받는다.
  • -listen=1: P2P 포트(Signet 38333)에서 들어오는 연결을 받는다. 기본값은 켜짐이다. 단 -connect나 -proxy를 쓰면 기본값이 꺼짐으로 바뀐다.
  • -addnode=주소: 이 피어에 계속 연결을 시도한다. 다른 피어도 쓴다.
  • -connect=주소: 이 피어에만 연결한다. 자동 연결을 끈다.
  • -externalip=주소: NAT 뒤의 노드는 자기 공인 주소를 모른다. 이 값을 주면 그 주소를 다른 노드에게 광고한다(addr 메시지). 광고해야 다른 노드가 나를 찾는다. 이 값을 주면 자동 탐지(-discover)는 꺼진다. 바깥 포트가 다르면 주소:포트로 쓴다. 확인: getnetworkinfo의 localaddresses.
  • -listen은 개수가 아니라 켜기/끄기(1/0)다. 연결 수는 -maxconnections가 정한다.
  • bitcoind는 피어를 보통 DNS seed(공개 주소 목록)에서 찾는다. 그래서 옆의 내 노드는 모른다. -addnode로 알려 준다.
  • 자기 자신에게 연결하면 bitcoind가 nonce(무작위 번호)를 비교해서 알아채고 끊는다.
connection_type기본 수하는 일
outbound-full-relay8블록, 트랜잭션, 주소를 모두 주고받는다
block-relay-only2블록만 주고받는다. 트랜잭션과 주소를 주고받지 않으므로, 공격자가 내 연결 상대를 추측하기 어렵다. 그래서 내 연결을 모두 차지하는 공격(eclipse attack)을 막는 데 돕는다
manual-addnode 수내가 지정한 피어. 자동 outbound 자리를 쓰지 않는다
inbound—상대가 먼저 연결해 온 피어. 수는 -maxconnections(기본 125) 안에서 정해진다

RPC와 쿠키 인증

왜 알아야 하나bitcoin-cli가 "Could not locate RPC credentials" 오류를 낼 때가 있다. 원인은 비밀번호가 아니라 쿠키 파일의 위치와 권한이다.

  • bitcoin-cli는 bitcoind에 HTTP로 JSON-RPC 요청을 보낸다. 모든 요청에는 인증이 필요하다.
  • 요청의 실제 모양: POST http://127.0.0.1:38332/, 본문 {"method": "getpeerinfo", "params": []}. bitcoind가 함수를 실행하고 결과를 JSON으로 돌려준다.
  • 인증이 필요한 이유: RPC로 노드를 끄고(stop), 지갑의 돈을 보내고, 피어를 차단할 수 있다.
  • 설정에 비밀번호가 없으면 bitcoind는 시작할 때 .cookie 파일을 만든다. 내용은 __cookie__:무작위값이다.
  • bitcoin-cli는 같은 데이터 디렉터리에서 이 파일을 읽어 인증한다.
  • 쿠키는 재시작할 때마다 바뀐다. bitcoind가 정상 종료하면 지워진다.
  • 결과: 파일을 읽을 수 있는 사용자 = RPC를 쓸 수 있는 사용자. 인증이 파일 권한으로 바뀐다.

pruned 노드

왜 알아야 하나디스크가 작으면 pruning이 답이 될 수 있다. 하지만 잃는 기능도 있다. 노드 여러 개를 둘 때의 선택지다.

  • pruned 노드도 모든 블록을 받아 모두 검증한다. 검증 수준은 풀 노드와 같다.
  • 검증 후 오래된 blk*.dat, rev*.dat를 지운다. 최근 블록과 UTXO 집합만 남긴다.
  • -prune=N: 블록 파일을 약 N MiB로 유지한다. 최소값은 550이다.
  • 잃는 것: 오래된 블록을 다른 노드에 줄 수 없다. -txindex를 쓸 수 없다. 오래된 지갑 재검색이 안 된다.
내 환경에서Signet은 작아서 지금은 pruning이 꼭 필요하지 않다. 다만 노드끼리 동기화하는 실험에서는 주의한다. pruned 노드는 처음부터 동기화하는 피어에게 오래된 블록을 줄 수 없다.

UTXO 집합과 dbcache

왜 알아야 하나IBD 속도에 가장 큰 영향을 주는 설정이다. 실습 F의 첫 번째 실험 변수가 될 수 있다.

  • UTXO는 아직 쓰지 않은 출력이다. 새 트랜잭션은 UTXO를 쓰고 새 UTXO를 만든다.
  • 블록을 검증할 때마다 UTXO를 찾고, 지우고, 추가한다. 이것이 작은 랜덤 I/O를 만든다.
  • -dbcache=N(MiB)은 UTXO를 메모리에 둘 공간이다. 크면 디스크에 덜 간다.
  • 캐시가 차면 디스크(chainstate)에 한 번에 쓴다. 이것을 flush라고 한다. 이때 I/O가 몰린다.
  • dbcache에 없는 UTXO는 chainstate/의 LevelDB 파일에서 읽는다. 그 파일이 page cache에 있으면 빠르고, 버려졌으면 디스크까지 간다.
  • 코드 경로: ConnectBlock(src/validation.cpp)이 입력 코인을 찾는다 → CCoinsViewCache::FetchCoin(src/coins.cpp, 크기 = dbcache) → 없으면 CCoinsViewDB(src/txdb.cpp) → LevelDB 읽기 → page cache → 디스크.
자주 하는 오해dbcache를 크게 하면 항상 빠른 것은 아니다. 컨테이너 메모리 limits를 넘으면 종료된다. 페이지 캐시와도 메모리를 나눈다. 측정으로 확인한다.

-reindex-chainstate와 bitcoin.conf

왜 알아야 하나실습 F는 같은 작업을 조건만 바꾸어 두 번 실행한다. IBD를 다시 하면 네트워크(피어 속도)가 결과를 흔든다. -reindex-chainstate는 네트워크 없이 같은 검증 작업을 다시 하게 한다.

  • -reindex-chainstate: chainstate/(UTXO 집합)를 지우고, 디스크에 이미 있는 블록으로 다시 만든다. 블록을 다운로드하지 않는다.
  • -reindex: 블록 인덱스(blocks/index/)까지 다시 만든다. 더 오래 걸린다.
  • 설정은 명령줄(args)과 bitcoin.conf에서 온다. 파일에서는 앞의 -를 빼고 쓴다: reindex-chainstate=1.
  • bitcoin.conf는 데이터 디렉터리의 맨 위에 둔다. signet/ 안이 아니다. signet/에는 데이터만 있다.
  • bitcoind는 시작할 때만 설정을 읽는다. 그래서 파일을 쓴 뒤 재시작해야 한다.
내 환경에서StatefulSet의 args에 넣으면 node-0과 node-1이 모두 reindex를 한다. 하지만 bitcoin.conf는 PVC 안에 있고, node-1의 PVC는 node-1만 쓴다. 그래서 2026-10-13에 node-1의 /home/bitcoin/.bitcoin/bitcoin.conf에만 한 줄을 썼다. 그다음 kubectl delete pod bitcoin-node-1로 재시작했다. 새 컨테이너는 새 cgroup을 받으므로 cpu.stat, io.stat, memory.stat이 0부터 다시 센다. 끝났을 때의 값이 그대로 이번 실행의 값이 된다. 2026-10-14 F-6: 실험이 끝난 뒤 bitcoin.conf(이 한 줄만 있었다)를 지우고 Pod를 다시 만들었다. 재시작 직후 blocks = headers = 326339, initialblockdownload: false였다. 재구축 없이 시작했다.
자주 하는 오해끝난 뒤에 설정 줄을 지워야 한다. 줄이 남아 있으면 Pod가 다시 시작될 때마다 reindex를 다시 한다. 그리고 블록 수로 남은 시간을 예상하지 않는다. Signet 초기 블록은 거의 비어 있어서 빨리 지나간다. verificationprogress가 더 정확하다.

성능을 보는 순서 (USE)

왜 알아야 하나느릴 때 아무 도구나 켜면 시간만 쓴다. 정해진 순서로 자원을 하나씩 확인하면 병목을 빠뜨리지 않는다.

자원(CPU, 메모리, 디스크, 네트워크)마다 세 가지를 본다:

질문예
Utilization (사용률)얼마나 바쁜가?CPU 90%, 디스크 %util
Saturation (포화)기다리는 작업이 있는가?load average, I/O 대기열, CPU throttling
Errors (오류)실패가 있는가?OOMKilled, 디스크 오류, 연결 끊김
  • 사용률이 낮아도 포화가 있을 수 있다. 예: CPU 한도 때문에 throttling되는 컨테이너.
  • 시스템 전체 값과 노드 하나의 값을 구분한다. 서버에는 다른 서비스도 있다.
내 환경에서2026-10-13의 조사를 USE로 다시 보면 이렇다.
  • CPU: 사용률 평균 약 0.45코어(낮음), 포화(throttling) 약 2.6%(낮음). 원인이 아니다.
  • 디스크: 읽기 약 1.89TB, 데이터의 약 78배. 이상하다.
  • 메모리: kind 상자의 memory.events max가 24,428,625였다(포화). 이 값은 하위 cgroup을 포함한다. 상자 자신의 값은 10-14 확인에서 약 83%였다. 오류(OOM)는 0이다.
결론: 메모리 포화 → 캐시 손실 → 디스크 읽기 → CPU 대기. 오류가 없어서 "느리기만" 했다.

USE 다음의 순서. USE는 어느 자원이 부족한지 찾는다. 실무에서는 보통 4단계로 내려간다.

  1. 시스템 관찰 (cgroup, iostat, USE): 어느 자원이 부족한가?
  2. 프로파일링 (perf, flame graph, bitcoind의 -debug=bench): 어느 함수에서 시간을 쓰는가?
  3. 소스 코드: 그 함수는 왜 그렇게 동작하는가?
  4. 수정과 재측정: 1단계의 숫자가 실제로 좋아졌는가?
자주 하는 오해성능 문제를 소스 코드부터 보지 않는다. 시간이 어디에서 쓰이는지 모르고 고치면 틀린 곳을 고친다. 이 프로젝트의 첫 원인도 코드가 아니라 환경(kind 상자 메모리)이었다. 설정 하나로 읽기가 990GB → 433GB로 달라졌다(실습 F).
내 환경에서2026-10-14에 1단계를 끝냈다. 2단계는 -debug=bench로 시작할 계획이다. 이 옵션은 블록마다 검증 단계별 시간을 debug.log에 남긴다. perf는 보통 root 권한이 필요하지만, 이 옵션은 필요 없다.

실험 설계의 기본

왜 알아야 하나측정 한 번은 증거가 아니다. 개선 효과를 남에게 보여 주려면 같은 결과가 다시 나와야 한다.

  1. 질문을 먼저 쓴다. 예: "dbcache 450 → 2000 MiB이면 Signet IBD 시간이 줄어드는가?"
  2. 기준선(baseline)을 잰다. 바꾸기 전의 값이다.
  3. 한 번에 하나만 바꾼다. 두 개를 바꾸면 어느 것이 원인인지 모른다.
  4. 여러 번 반복한다. 평균과 흩어짐을 같이 쓴다.
  5. 조건을 기록한다. 버전, 설정, 디스크, 캐시 상태, 피어 수, 다른 서비스의 부하.
  6. 결과를 원인으로 설명한다. "빨라졌다"가 아니라 "디스크 대기가 줄어서 빨라졌다".
자주 하는 오해네트워크 피어는 매번 다르다. 블록을 받는 속도가 결과를 흔든다. 검증 속도만 재고 싶으면 피어 조건을 고정하거나 없앤다. 예: 내 노드에만 -connect, 또는 블록을 다시 받지 않는 -reindex-chainstate.
