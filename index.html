전체 지도: bitcoind는 어디에서 실행되는가

왜 알아야 하나내 노드는 상자 안의 상자 안에서 실행된다. 문제가 생기면 먼저 "어느 상자의 문제인가?"를 정해야 한다. 상자를 틀리면 원인도 틀린다.

호스트 · promet (Ubuntu, 리눅스 커널 1개)
Docker · 컨테이너 런타임
kind 노드 · Docker 컨테이너 bitcoin-lab-control-plane
Kubernetes · API 서버, kubelet, containerd
namespace · bitcoin-lab
Pod · bitcoin-signet-xxxx
컨테이너 · bitcoind 프로세스
  • 모든 상자는 같은 리눅스 커널을 사용한다. 가상 머신이 아니다.
  • 그래서 bitcoind는 결국 호스트의 프로세스 하나다. 호스트에서 ps로 볼 수 있다.
  • 각 상자는 커널 기능(namespace, cgroup)으로 "다르게 보이고, 제한되는" 영역일 뿐이다.
  • kind 노드도 컨테이너다. 그래서 Pod 컨테이너는 "컨테이너 안의 컨테이너"다.
자주 하는 오해"자원 제한"에도 층이 있다. kind 노드 컨테이너에 거는 Docker 한도와 Pod에 거는 Kubernetes limits는 다른 층이다. 무엇을 제한하고 싶은지 먼저 정한다.
직접 확인 
# 호스트에서 bitcoind 프로세스가 보인다
ps -eo pid,user,rss,cmd | grep [b]itcoind
# kind 노드는 Docker 컨테이너다
docker ps --filter name=bitcoin-lab-control-plane

세 가지 계층: 역할, 실행 위치, 객체

왜 알아야 하나"control plane이 가장 상위인가?" 같은 질문은 계층이 하나라고 가정한다. 실제로는 계층이 세 개다. 각 계층은 다른 질문에 답한다.

  • 역할: 누가 결정하고(control plane), 누가 실행하는가(kubelet).
  • 실행 위치: 프로세스가 실제로 어느 상자 안에 있는가.
  • 객체: YAML로 만드는 것들이 서로를 어떻게 만들고 연결하는가.
자주 하는 오해"가장 상위"를 물을 때는 먼저 어느 계층인지 정한다. control plane은 ①에서 가장 위다. 하지만 ③의 객체 트리에는 없다.

control plane과 worker node

왜 알아야 하나내 노드 이름은 bitcoin-lab-control-plane인데 bitcoind도 여기서 실행된다. 두뇌와 손발이 어떻게 나뉘는지 알면 이 이름이 헷갈리지 않는다.

구성 요소하는 일
API 서버모든 요청을 받는다. 검사하고 etcd에 저장한다.
etcd원하는 상태와 현재 상태를 저장하는 데이터베이스다.
scheduler아직 노드가 없는 Pod에 노드를 정한다.
controller-managerDeployment, StatefulSet 컨트롤러가 실행된다. Pod 객체를 만든다.
kubelet자기 노드에 배정된 Pod를 실제로 실행한다.
내 환경에서kind 클러스터는 노드가 1대다. 그래서 bitcoin-lab-control-plane 하나가 두뇌와 손발을 둘 다 한다. 두뇌의 구성 요소도 kube-system namespace의 Pod로 실행된다.
직접 확인 
kubectl -n kube-system get pods     # apiserver, etcd, scheduler, controller-manager
kubectl get nodes -o wide

"노드"의 두 가지 뜻

왜 알아야 하나이 프로젝트에서는 "노드"라는 말이 두 가지 뜻으로 쓰인다. 뜻을 섞으면 "노드 3개를 띄운다"가 서버 3대처럼 들린다.

내 환경에서우리는 서버(worker node)를 직접 다루지 않는다. StatefulSet, Service 같은 객체를 API 서버에 넣는다. 어느 서버에서 실행할지는 scheduler가 정한다.

컨테이너와 Kubernetes는 리눅스 기능 위에 있다. 이 기본이 약하면 위층의 동작을 설명할 수 없다.

프로세스, 사용자, 권한process · UID

왜 알아야 하나"Permission denied"는 가장 흔한 오류다. 원인은 항상 "어떤 사용자의 프로세스가, 누구 소유의 파일에, 어떤 동작을 했는가"이다.

  • 프로세스는 실행 중인 프로그램이다. 모든 프로세스는 UID(사용자 번호)를 가진다.
  • 파일은 소유자, 그룹, 권한 비트(rwx)를 가진다.
  • 커널은 이름이 아니라 번호(UID, GID)를 비교한다. 이름은 사람을 위한 표시다.
  • root(UID 0)는 대부분의 권한 검사를 통과한다.
내 환경에서taehwi(UID 1000)와 nodelab(UID 1001)은 다른 사용자다. 계정 분리는 파일과 프로세스의 접근 권한을 나눈다. CPU와 메모리는 나누지 않는다. 자원을 나누려면 cgroup이 필요하다.
자주 하는 오해컨테이너 안의 UID 1000과 호스트의 UID 1000은 같은 번호다. 이름이 달라도 커널에게는 같은 사용자다. 그래서 볼륨 파일의 소유자가 이상하게 보일 수 있다.
직접 확인 
id                       # 내 UID, GID, 그룹
ls -ln ~                 # 이름 대신 번호로 소유자 표시
ps -o pid,uid,user,cmd -u nodelab

파일시스템과 마운트mount

왜 알아야 하나리눅스에서 경로는 디스크를 알려 주지 않는다. /mnt/hdd는 HDD다. /var/lib/docker는 SSD다. 성능 실험에서 데이터가 어느 장치에 있는지 모르면 결과를 설명할 수 없다.

  • 리눅스는 디렉터리 트리를 하나만 가진다. 맨 위는 /다.
  • 장치(디스크, 파티션)의 파일시스템을 트리의 한 디렉터리에 붙인다. 이것을 마운트라고 한다.
  • 그 디렉터리를 마운트 지점이라고 한다. 그 아래의 파일은 붙은 장치에 저장된다.
  • 바인드 마운트는 장치가 아니라 다른 디렉터리를 다른 경로에 다시 보이게 한다. 컨테이너 볼륨이 이 방법을 쓴다.
내 환경에서루트(/)는 SATA SSD의 ext4(LVM)다. /mnt/hdd는 2 TB SMR HDD다. kind 노드와 PVC 데이터는 기본적으로 Docker 저장 영역, 즉 SSD에 있다.
직접 확인 
findmnt -D               # 마운트 목록과 크기
findmnt -T /mnt/hdd      # 이 경로는 어느 장치인가
lsblk -f                 # 장치와 파일시스템

du와 df는 왜 다른 값을 보이는가

왜 알아야 하나실습 A에서 "노드를 몇 개 더 둘 수 있는가"를 계산한다. 두 명령의 값이 다르면 어느 쪽을 믿을지 알아야 한다.

dudf
질문이 디렉터리 아래 파일들은 얼마나 큰가?이 파일시스템에 남은 공간은 얼마인가?
방법파일을 하나씩 찾아서 더한다파일시스템에 사용 블록 수를 묻는다
범위지정한 경로 아래, 내가 볼 수 있는 파일마운트된 파일시스템 전체

값이 다른 이유:

  • 지워졌지만 열려 있는 파일. 프로세스가 파일을 열고 있으면 삭제 후에도 공간이 남는다. du는 못 보고 df는 센다.
  • 예약 블록. ext4는 기본으로 약 5%를 root용으로 남긴다. df의 Used + Avail이 Size보다 작다.
  • 다른 파일시스템. du는 경로 안의 다른 마운트도 더한다. -x를 쓰면 막는다.
  • 권한. 읽을 수 없는 디렉터리는 du가 세지 못한다.
내 환경에서"공간이 얼마나 남았나"는 df로 본다. "노드 하나가 얼마나 쓰나"는 du로 본다. 2026-10-12 관찰: 루트 226G 중 약 156G 여유, 기존 노드 PVC bitcoin-data는 약 27G 사용. 노드 데이터는 kind 노드 안에 있으므로, Pod 안에서 du를 실행하면 노드 크기를 정확히 볼 수 있다.
직접 확인 
df -h /                                         # SSD 여유 공간
kubectl -n bitcoin-lab exec deploy/bitcoin-signet -- \
  du -sh /home/bitcoin/.bitcoin/signet          # 노드 하나의 크기
sudo lsof +L1 | head                            # 지워졌지만 열린 파일

연결: 마운트PV와 PVCpruned 노드

docker 그룹은 root와 같다

왜 알아야 하나계정의 권한을 정할 때 필요하다. nodelab에 docker 그룹을 주면 사실상 root를 주는 것이다.

  • Docker 데몬(dockerd)은 root로 실행된다.
  • docker 그룹은 데몬의 소켓 /var/run/docker.sock에 쓸 수 있다.
  • 그래서 docker 그룹 사용자는 데몬에게 무엇이든 요청할 수 있다. 예: 호스트의 /를 컨테이너에 마운트한다. 그 컨테이너 안에서 root로 호스트 파일을 바꾼다.
  • 결과: sudo 없이도 호스트 root와 같은 일을 할 수 있다.
내 환경에서개인 실습 서버에서는 편의를 위해 허용할 수 있다. 다만 "nodelab은 권한이 적은 계정"이라고 생각하면 안 된다. 선택은 편의와 위험을 같이 보고 한다.
직접 확인 
ls -l /var/run/docker.sock     # 소유 그룹이 docker
getent group docker            # 누가 그룹에 있는가

메모리, 페이지 캐시, 스왑

왜 알아야 하나bitcoind 성능은 메모리와 디스크 사이에서 정해진다. "메모리가 부족하다"와 "캐시가 많다"를 구분하지 못하면 측정을 잘못 읽는다.

  • 커널은 빈 메모리를 놀리지 않는다. 디스크에서 읽은 내용을 메모리에 남긴다. 이것이 페이지 캐시다.
  • 페이지 캐시는 필요하면 즉시 비울 수 있다. 그래서 free의 available을 본다. free 열은 거의 의미가 없다.
  • 스왑은 메모리 내용을 디스크로 내보내는 공간이다. 스왑이 많이 쓰이면 느려진다.
  • 메모리 한도를 넘으면 커널의 OOM killer가 프로세스를 종료한다.
자주 하는 오해같은 실험을 두 번 하면 두 번째가 빠를 수 있다. 데이터가 페이지 캐시에 남아 있기 때문이다. 이것을 "캐시 효과"라고 하고, 실험 기록에 남긴다.
직접 확인 
free -h          # available 열을 본다
vmstat 1 5       # si, so 열: 스왑 입출력

이미지와 컨테이너

왜 알아야 하나컨테이너를 지우면 안의 데이터도 지워진다. 노드 데이터를 어디에 둘지 정하려면 이 구조를 알아야 한다.

  • 이미지는 읽기 전용 파일 묶음이다. 프로그램과 라이브러리가 있다. 여러 층(layer)으로 되어 있다.
  • 컨테이너는 이미지로 시작한 프로세스다. 이미지 위에 쓰기 가능한 얇은 층이 하나 붙는다.
  • 컨테이너가 쓴 파일은 이 쓰기 층에 간다. 컨테이너를 지우면 쓰기 층도 지워진다.

리눅스 namespace: 다르게 보이게 하기

왜 알아야 하나컨테이너 안에서 ps를 하면 프로세스가 몇 개만 보인다. 호스트에서는 전부 보인다. 이 차이를 만드는 것이 namespace다.

namespace는 프로세스가 보는 세계를 나눈다. 자원의 양은 나누지 않는다.

종류나누는 것결과
mnt마운트 목록컨테이너는 자기 /를 본다
pid프로세스 번호컨테이너 안의 첫 프로세스가 PID 1이다
net네트워크 장치, IP, 포트컨테이너마다 IP와 포트 공간이 따로 있다
uts호스트 이름컨테이너마다 이름이 다르다
ipc, user, cgroup공유 메모리, UID 매핑, cgroup 경로더 깊은 격리
자주 하는 오해Kubernetes의 Namespace(k8s namespace)는 이름만 같다. 그것은 API 객체를 묶는 논리적 폴더다. 리눅스 namespace와 관계없다.
직접 확인 
ls -l /proc/self/ns      # 내 프로세스의 namespace 번호
sudo lsns -t net         # 호스트의 모든 net namespace

cgroup: 자원을 세고 제한하기

왜 알아야 하나자원 실험(실습 E, F)은 전부 cgroup으로 한다. kubectl top, Docker 한도, Kubernetes limits는 모두 cgroup 값을 쓰거나 읽는다.

  • cgroup은 프로세스 묶음이다. 커널은 묶음마다 CPU, 메모리, I/O 사용량을 센다.
  • 묶음에 한도를 걸 수 있다. 예: memory.max, cpu.max.
  • cgroup은 트리다. 자식은 부모의 한도를 넘을 수 없다.
  • 내 서버는 cgroup v2를 쓴다. 파일은 /sys/fs/cgroup 아래에 있다.
namespacecgroup
질문무엇이 보이는가?얼마나 쓸 수 있는가?
예다른 프로세스가 안 보인다메모리 2 GiB를 넘으면 종료된다
내 환경에서트리는 대략 이렇다. 호스트 → Docker의 kind 노드 cgroup → kubelet의 Pod cgroup → 컨테이너 cgroup. kind 노드에 Docker 한도를 걸면 그 아래의 모든 Pod가 함께 제한된다. Docker의 --memory-swap은 "메모리 + 스왑"의 합계다. 그래서 --memory보다 작을 수 없다.
직접 확인

systemd-cgls --no-pager | head -40                    # cgroup 트리
kubectl -n bitcoin-lab exec deploy/bitcoin-signet -- \
  cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/memory.current

Kubernetes KUBERNETES

Kubernetes는 "명령을 실행하는 도구"가 아니다. "원하는 상태를 적어 두면 계속 맞추는 시스템"이다.

API 서버와 desired state

왜 알아야 하나Pod를 지워도 다시 생긴다. 이것은 오류가 아니다. Kubernetes의 기본 동작이다. 이 원리를 알면 대부분의 "이상한 동작"이 설명된다.

나YAML 작성
kubectl apply
요청 →
API 서버원하는 상태를 etcd에 저장
← 관찰
변경 →
컨트롤러, kubelet현재 상태와 비교
차이를 줄인다
  • desired state(원하는 상태): YAML의 spec. 예: "bitcoind Pod 1개".
  • current state(현재 상태): 실제로 있는 것. status에 기록된다.
  • 컨트롤러는 둘을 계속 비교한다. 다르면 고친다. 이 반복을 reconcile loop라고 한다.
  • 모든 구성 요소는 API 서버를 통해서만 대화한다. kubectl도 API 서버의 클라이언트일 뿐이다.
자주 하는 오해Pod를 직접 고치거나 지우는 것은 임시 조치다. 바꾸고 싶으면 원하는 상태(Deployment의 YAML)를 바꾼다.
직접 확인 
kubectl -n bitcoin-lab get deploy bitcoin-signet -o yaml | less   # spec과 status 비교
kubectl -n bitcoin-lab get events --sort-by=.lastTimestamp       # 컨트롤러가 한 일

YAML 구조와 들여쓰기

왜 알아야 하나YAML에서 들여쓰기는 구조 자체다. 공백 두 칸이 틀리면 값이 다른 부모에 붙는다. 오류가 안 나고 다르게 동작할 때도 있다.

  • YAML은 두 가지로만 되어 있다. 맵(키: 값)과 리스트(- 항목).
  • 같은 깊이에 있는 키는 같은 부모에 속한다. 깊이는 공백으로 정한다. 탭은 쓰지 않는다.
  • -는 "리스트의 새 항목"이다. 그 뒤의 키들은 그 항목에 속한다.
  • 모든 매니페스트는 4개의 최상위 키를 가진다: apiVersion, kind, metadata, spec.
apiVersion: apps/v1          # 어느 API 그룹, 버전
kind: Deployment             # 어떤 객체
metadata:                    # 이름표 (맵)
  name: bitcoin-signet
  namespace: bitcoin-lab
spec:                        # 원하는 상태
  replicas: 1
  template:                  # 만들 Pod의 모양
    spec:
      containers:            # 리스트
      - name: bitcoind       # 첫 번째 항목 시작
        image: …             # name과 같은 깊이 = 같은 항목
        args: ["-signet"]
자주 하는 오해image:가 - name:보다 두 칸 왼쪽에 있으면, image는 컨테이너 항목이 아니라 spec에 붙는다. 파일을 적용하기 전에 kubectl apply --dry-run=server -f 파일로 검사한다.
직접 확인 
kubectl explain deployment.spec.template.spec.containers   # 어떤 키가 어디에 오는가
kubectl apply --dry-run=server -f bitcoin.yaml

Kubernetes namespace

왜 알아야 하나kubectl get pods에 내 Pod가 없으면, 보통 namespace를 빠뜨린 것이다.

  • namespace는 API 객체를 묶는 이름 공간이다. 폴더와 비슷하다.
  • 같은 namespace 안에서는 이름이 겹칠 수 없다. 다른 namespace에서는 겹쳐도 된다.
  • -n을 안 쓰면 default namespace를 본다.
  • namespace만으로는 CPU, 메모리가 나뉘지 않는다. 한도는 limits나 ResourceQuota로 건다.
내 환경에서노드 객체는 전부 bitcoin-lab namespace에 있다. 매번 -n bitcoin-lab을 쓴다. 아니면 기본값을 바꾼다: kubectl config set-context --current --namespace=bitcoin-lab.

왜 알아야 하나노드 데이터는 PVC에 있다. PVC를 지우면 동기화한 데이터가 사라질 수 있다. 무엇이 실제 디스크이고 무엇이 요청서인지 구분해야 한다.

Service

왜 알아야 하나Pod IP는 바뀐다. 다른 Pod가 바뀌는 IP를 따라갈 수 없다. Service는 바뀌지 않는 이름과 주소를 준다.

  • Service는 라벨 선택자(selector)로 Pod를 고른다. 라벨이 맞는 Pod가 대상이다.
  • 기본 종류(ClusterIP)는 가상 IP 하나를 준다. 그 IP로 오는 연결을 대상 Pod 중 하나에 나눠 보낸다.
  • 이름으로도 접속한다: 서비스이름.namespace.svc.cluster.local.
자주 하는 오해Service가 대상을 못 찾으면 보통 라벨이 틀린 것이다. kubectl get endpointslices로 대상 Pod 목록을 확인한다.

headless Service

왜 알아야 하나노드끼리 연결할 때(실습 D), 각 노드는 "아무 노드"가 아니라 "특정 노드"에 연결해야 한다. headless Service가 Pod마다 고정 DNS 이름을 준다.

  • headless Service는 clusterIP: None인 Service다. 가상 IP가 없고, 나눠 보내지도 않는다.
  • 대신 DNS가 Pod IP를 직접 돌려준다.
  • StatefulSet과 같이 쓰면 Pod마다 이름이 생긴다: bitcoin-node-0.bitcoin-node.bitcoin-lab.svc.cluster.local. 형식은 <Pod 이름>.<Service 이름>이다.
  • Pod가 다시 생겨서 IP가 바뀌어도 이 이름은 같다.
내 환경에서bitcoind에 -addnode=bitcoin-node-0.bitcoin-node:38333처럼 쓴다. 같은 namespace 안에서는 뒷부분을 줄여도 된다. 연결 결과는 bitcoin-cli getpeerinfo로 본다.

kind 클러스터의 구조

왜 알아야 하나kind는 실제 서버 클러스터와 다르게 동작하는 부분이 있다. 측정 결과에 kind 때문인 부분이 섞일 수 있다.

  • kind는 "Kubernetes in Docker"다. Kubernetes 노드 하나 = Docker 컨테이너 하나다.
  • 그 컨테이너 안에서 kubelet, containerd, API 서버가 실행된다. Pod 컨테이너는 그 안의 containerd가 만든다.
  • 그래서 호스트의 docker ps에는 Pod가 안 보인다. kind 노드만 보인다.
  • 클러스터 네트워크는 Docker 네트워크 안에 있다. 외부에서 Pod로 들어오려면 별도 포트 매핑이 필요하다.
내 환경에서노드는 bitcoin-lab-control-plane 하나다. 모든 Pod가 이 컨테이너 안에서 같은 SSD, 같은 CPU를 나눠 쓴다. "노드 여러 개"는 Kubernetes 노드가 아니라 bitcoind Pod 여러 개다. "노드"의 두 뜻을 본다.
직접 확인

docker exec bitcoin-lab-control-plane crictl ps    # kind 노드 안의 컨테이너 목록

네트워크 NETWORK

노드는 네트워크 프로그램이다. 피어 연결 수와 전송량은 성능 측정의 기본 값이다.

IP 주소, 포트, TCP 연결

왜 알아야 하나"연결이 안 된다"의 원인은 넷 중 하나다. 주소가 틀리다. 포트가 틀리다. 듣는 프로그램이 없다. 중간에서 막는다.

  • IP 주소는 장치(정확히는 네트워크 인터페이스)를 찾는다.
  • 포트는 그 장치 안의 프로그램을 찾는다. 0–65535 번호다.
  • TCP 연결은 네 값으로 구분한다: 내 IP, 내 포트, 상대 IP, 상대 포트.
  • 서버는 한 포트에서 listen(대기)한다. 클라이언트가 connect(접속)한다.
Signet 포트용도누가 접속하나
38333P2P다른 비트코인 노드
38332RPC나 (bitcoin-cli)
직접 확인 
ss -tlnp            # 듣고 있는 TCP 포트 (Pod 안에서 실행하면 Pod 기준)
ss -tnp state established

연결: -listen과 피어리슨 주소NAT

리슨 주소: 127.0.0.1과 0.0.0.0

왜 알아야 하나프로그램이 "실행 중"이어도 다른 Pod에서 접속이 안 될 수 있다. 어느 주소에서 듣는지가 접근 범위를 정한다.

  • 127.0.0.1(localhost)에서 들으면 같은 net namespace 안에서만 접속할 수 있다. Pod에서는 같은 Pod 안이다.
  • 0.0.0.0에서 들으면 모든 인터페이스에서 접속할 수 있다.
  • bitcoind의 RPC는 기본으로 localhost에서만 듣는다. 이것은 안전을 위한 기본값이다.
내 환경에서kubectl exec로 Pod 안에서 bitcoin-cli를 실행하면 localhost이므로 바로 된다. 다른 Pod에서 RPC로 접속하려면 -rpcbind와 -rpcallowip를 같이 바꿔야 한다. 필요할 때만 바꾼다.

NAT와 포트 포워딩

왜 알아야 하나내 노드는 밖으로 연결(outbound)할 수 있다. 하지만 밖에서 내 노드로 연결(inbound)은 보통 안 된다. NAT가 몇 겹 있기 때문이다.

  • 집 공유기는 사설 IP(예: 192.168.x.x)를 공인 IP 하나로 바꾼다. 이것이 NAT다.
  • 안에서 나간 연결의 응답은 돌아온다. 밖에서 먼저 온 연결은 어디로 보낼지 모른다. 그래서 막힌다.
  • 포트 포워딩은 "이 포트로 오면 이 내부 주소로 보낸다"는 규칙이다.
내 환경에서밖에서 Pod까지 가려면 NAT가 여러 번 있다. 공유기 → 호스트 → Docker 네트워크(kind 노드) → Pod 네트워크. 실습 목적이라면 inbound 없이 outbound 피어만으로 동기화할 수 있다. 내 노드끼리는 클러스터 안에서 연결한다.

풀 노드가 하는 일

왜 알아야 하나노드가 무엇을 하는지 알아야 어떤 자원이 바쁜지 예상할 수 있다.

  1. 피어를 찾고 연결한다. (네트워크)
  2. 블록 헤더를 먼저 받는다. 가장 긴 체인을 고른다. (headers-first)
  3. 블록 본문을 받는다. 모든 규칙을 직접 검사한다. (CPU)
  4. 검사한 결과로 UTXO 집합을 고친다. (메모리, 디스크)
  5. 동기화가 끝나면 새 블록과 트랜잭션을 받고 전달한다.
  • 처음부터 따라잡는 과정을 IBD(Initial Block Download)라고 한다. 이때 자원을 가장 많이 쓴다.
  • IBD와 동기화 후의 평소 동작은 다른 작업 부하다. 측정할 때 구분한다.
직접 확인 
kubectl -n bitcoin-lab exec deploy/bitcoin-signet -- bitcoin-cli -signet getblockchaininfo
# headers와 blocks의 차이, initialblockdownload, verificationprogress

Signet

왜 알아야 하나Signet에서 얻은 측정값을 메인넷에 그대로 쓰면 안 된다. 차이를 알아야 결과를 바르게 말할 수 있다.

  • Signet은 테스트 네트워크다. 코인에 가치가 없다.
  • 블록은 정해진 서명자만 만들 수 있다. 그래서 testnet보다 블록 간격이 안정적이다.
  • 체인이 메인넷보다 훨씬 작다. 동기화가 빠르다.
  • 프로토콜과 코드 경로는 메인넷과 거의 같다. 그래서 내부 동작을 배우기에 좋다.
자주 하는 오해Signet 블록은 트랜잭션이 적다. 검증 부하와 UTXO 크기가 메인넷과 다르다. "Signet에서 X분"은 "메인넷에서 X분"을 뜻하지 않는다.

-listen과 피어 연결

왜 알아야 하나노드끼리 연결하려면(실습 D) 한쪽은 들어오는 연결을 받아야 한다. -listen이 이것을 정한다.

  • outbound: 내 노드가 먼저 연결한다. 기본으로 여러 개를 자동으로 만든다.
  • inbound: 다른 노드가 내 노드에 연결한다. 내 노드가 P2P 포트에서 listen해야 받는다.
  • -listen=1: P2P 포트(Signet 38333)에서 들어오는 연결을 받는다. 기본값은 켜짐이다. 단 -connect나 -proxy를 쓰면 기본값이 꺼짐으로 바뀐다.
  • -addnode=주소: 이 피어에 계속 연결을 시도한다. 다른 피어도 쓴다.
  • -connect=주소: 이 피어에만 연결한다. 자동 연결을 끈다.
내 환경에서bitcoin-node-0이 listen하고, bitcoin-node-1이 -addnode=bitcoin-node-0.bitcoin-node로 연결한다. 기존 bitcoin-signet은 -listen=0이므로 들어오는 연결을 받지 않는다.
직접 확인 
bitcoin-cli -signet getpeerinfo | grep -E '"addr"|"inbound"'
bitcoin-cli -signet getnetworkinfo     # localaddresses, connections_in, connections_out

RPC와 쿠키 인증

왜 알아야 하나bitcoin-cli가 "Could not locate RPC credentials" 오류를 낼 때가 있다. 원인은 비밀번호가 아니라 쿠키 파일의 위치와 권한이다.

  • bitcoin-cli는 bitcoind에 HTTP로 JSON-RPC 요청을 보낸다. 모든 요청에는 인증이 필요하다.
  • 설정에 비밀번호가 없으면 bitcoind는 시작할 때 .cookie 파일을 만든다. 내용은 __cookie__:무작위값이다.
  • bitcoin-cli는 같은 데이터 디렉터리에서 이 파일을 읽어 인증한다.
  • 쿠키는 재시작할 때마다 바뀐다. bitcoind가 정상 종료하면 지워진다.
  • 결과: 파일을 읽을 수 있는 사용자 = RPC를 쓸 수 있는 사용자. 인증이 파일 권한으로 바뀐다.
내 환경에서Pod 안에서 bitcoin-cli -signet을 실행하면 같은 데이터 디렉터리를 보므로 쿠키를 찾는다. 다른 사용자로 실행하거나 -datadir이 다르면 찾지 못한다. 고정된 계정이 필요하면 -rpcauth를 쓴다.

연결: 리슨 주소권한데이터 디렉터리

pruned 노드

왜 알아야 하나디스크가 작으면 pruning이 답이 될 수 있다. 하지만 잃는 기능도 있다. 노드 여러 개를 둘 때의 선택지다.

  • pruned 노드도 모든 블록을 받아 모두 검증한다. 검증 수준은 풀 노드와 같다.
  • 검증 후 오래된 blk*.dat, rev*.dat를 지운다. 최근 블록과 UTXO 집합만 남긴다.
  • -prune=N: 블록 파일을 약 N MiB로 유지한다. 최소값은 550이다.
  • 잃는 것: 오래된 블록을 다른 노드에 줄 수 없다. -txindex를 쓸 수 없다. 오래된 지갑 재검색이 안 된다.
내 환경에서Signet은 작아서 지금은 pruning이 꼭 필요하지 않다. 다만 노드끼리 동기화하는 실험에서는 주의한다. pruned 노드는 처음부터 동기화하는 피어에게 오래된 블록을 줄 수 없다.

UTXO 집합과 dbcache

왜 알아야 하나IBD 속도에 가장 큰 영향을 주는 설정이다. 실습 F의 첫 번째 실험 변수가 될 수 있다.

  • UTXO는 아직 쓰지 않은 출력이다. 새 트랜잭션은 UTXO를 쓰고 새 UTXO를 만든다.
  • 블록을 검증할 때마다 UTXO를 찾고, 지우고, 추가한다. 이것이 작은 랜덤 I/O를 만든다.
  • -dbcache=N(MiB)은 UTXO를 메모리에 둘 공간이다. 크면 디스크에 덜 간다.
  • 캐시가 차면 디스크(chainstate)에 한 번에 쓴다. 이것을 flush라고 한다. 이때 I/O가 몰린다.
자주 하는 오해dbcache를 크게 하면 항상 빠른 것은 아니다. 컨테이너 메모리 limits를 넘으면 종료된다. 페이지 캐시와도 메모리를 나눈다. 측정으로 확인한다.
직접 확인 
grep -E "Using .*MiB|Flush|UpdateTip" debug.log | tail
# 캐시 배분, flush 시점, 블록 처리 속도

성능을 보는 순서 (USE)

왜 알아야 하나느릴 때 아무 도구나 켜면 시간만 쓴다. 정해진 순서로 자원을 하나씩 확인하면 병목을 빠뜨리지 않는다.

자원(CPU, 메모리, 디스크, 네트워크)마다 세 가지를 본다:

질문예
Utilization (사용률)얼마나 바쁜가?CPU 90%, 디스크 %util
Saturation (포화)기다리는 작업이 있는가?load average, I/O 대기열, CPU throttling
Errors (오류)실패가 있는가?OOMKilled, 디스크 오류, 연결 끊김
  • 사용률이 낮아도 포화가 있을 수 있다. 예: CPU 한도 때문에 throttling되는 컨테이너.
  • 시스템 전체 값과 노드 하나의 값을 구분한다. 서버에는 다른 서비스도 있다.

실험 설계의 기본

왜 알아야 하나측정 한 번은 증거가 아니다. 개선 효과를 남에게 보여 주려면 같은 결과가 다시 나와야 한다.

  1. 질문을 먼저 쓴다. 예: "dbcache 450 → 2000 MiB이면 Signet IBD 시간이 줄어드는가?"
  2. 기준선(baseline)을 잰다. 바꾸기 전의 값이다.
  3. 한 번에 하나만 바꾼다. 두 개를 바꾸면 어느 것이 원인인지 모른다.
  4. 여러 번 반복한다. 평균과 흩어짐을 같이 쓴다.
  5. 조건을 기록한다. 버전, 설정, 디스크, 캐시 상태, 피어 수, 다른 서비스의 부하.
  6. 결과를 원인으로 설명한다. "빨라졌다"가 아니라 "디스크 대기가 줄어서 빨라졌다".
자주 하는 오해네트워크 피어는 매번 다르다. 블록을 받는 속도가 결과를 흔든다. 검증 속도만 재고 싶으면 피어 조건을 고정하는 방법(예: 내 노드에만 -connect)을 생각한다.
