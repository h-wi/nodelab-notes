소켓, 코어, 스레드: CPU 개수 읽기

왜 알아야 하나서버 사양의 "CPU 개수"는 물리 코어 수가 아닐 수 있다. 어떤 일을 어느 CPU에서 실행할지 생각하려면 이 숫자를 나눠 읽어야 한다.

  • 소켓: 메인보드에 꽂힌 CPU 칩 하나. 서버는 소켓이 2개 이상일 수 있다.
  • 코어: 혼자서 프로그램 하나를 실행할 수 있는 단위. 칩 하나 안에 여러 개 있다.
  • 하드웨어 스레드: 리눅스가 "CPU 하나"로 세는 단위. SMT가 켜져 있으면 코어 하나가 스레드 2개가 된다.
  • 리눅스의 CPU(s) = 소켓 수 × 소켓당 코어 수 × 코어당 스레드 수.
  • 리눅스는 스레드마다 번호를 붙인다(CPU 0, CPU 1, …). 같은 코어의 두 번호가 이웃하지 않을 수 있다. 그림처럼 0과 4가 짝일 수 있다.
자주 하는 오해"CPU 8개"는 "코어 8개"가 아니다. SMT가 켜져 있으면 물리 코어는 그 절반이다. 또 프로그램 안의 "스레드"(소프트웨어)와 하드웨어 스레드는 다른 것이다.
promet과 비교promet의 i5-8500은 소켓 1개, 코어 6개, 코어당 스레드 1개다. 그래서 CPU(s)는 6이다. SMT가 없으므로 CPU 번호 하나가 코어 하나다.
직접 확인 
lscpu | grep -E '^(CPU\(s\)|Socket|Core|Thread)'
lscpu -e         # CPU마다 한 줄: CPU, NODE, SOCKET, CORE
cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list   # cpu0과 같은 코어를 쓰는 CPU 번호

코어와 ALU

왜 알아야 하나코어를 "계산기 하나"로 생각하면 SMT가 왜 2배가 아닌지 이해할 수 없다. 코어 안에 무엇이 있는지 먼저 알아야 한다.

  • ALU(Arithmetic Logic Unit)는 더하기, 비교, 논리 연산을 하는 회로다. 계산만 한다.
  • 코어는 프로그램을 실행하는 단위 전체다. 명령을 가져와 해석하는 부분, 레지스터, 여러 개의 ALU, 부동소수점·벡터 장치, 자기 캐시(L1, L2)가 들어 있다.
  • 비유: 코어는 "요리사 한 명과 그 조리대 전체"다. ALU는 조리대 위의 칼 하나다.
  • L3 캐시와 메모리는 여러 코어가 같이 쓴다.
자주 하는 오해코어 = ALU가 아니다. 요즘 코어 하나에는 ALU가 여러 개 있다. 코어는 명령 여러 개를 동시에 실행하려고 한다.
promet과 비교promet에는 코어가 6개 있다. 코어마다 자기 L1, L2 캐시가 있다. L3 캐시는 6개 코어가 같이 쓴다.
직접 확인 
lscpu | grep -i cache    # L1d, L1i, L2, L3 크기
lscpu -C                 # 캐시마다 한 줄. ONE-SIZE는 하나의 크기, ALL-SIZE는 전체 합

SMT: 코어 하나를 CPU 2개로

왜 알아야 하나SMT가 켜진 서버에서는 CPU 2개가 실제로 코어 하나다. 두 CPU에 무거운 일을 같이 주면 서로 느려진다. 이 관계를 모르면 CPU 수를 잘못 믿는다.

  • SMT(Simultaneous Multi-Threading)는 코어 하나가 명령 흐름 2개를 같이 실행하는 기능이다. Intel은 Hyper-Threading이라고 부른다.
  • 왜 만들었나: 코어는 메모리를 기다리는 시간이 많다. 그동안 실행 장치가 논다. 다른 흐름이 그 빈 시간을 쓴다.
  • 두 흐름은 실행 장치(ALU 등)와 L1, L2 캐시를 나눠 쓴다. 그래서 성능은 2배가 되지 않는다. 일의 종류에 따라 조금 늘거나 거의 늘지 않는다.
  • 리눅스는 두 흐름을 CPU 2개로 센다. 같은 코어의 두 CPU를 서로 sibling(짝꿍)이라고 한다.
  • SMT는 보통 BIOS에서 켜거나 끈다. 리눅스에서도 끌 수 있다.
자주 하는 오해짝꿍 CPU 두 개는 독립된 코어 두 개가 아니다. 한쪽이 바쁘면 다른 쪽도 영향을 받는다.
promet과 비교i5-8500에는 SMT가 없다. 그래서 promet에서는 짝꿍 문제가 생기지 않는다. SMT가 있는 서버에서는 이 관계를 따로 생각해야 한다.
직접 확인

cat /sys/devices/system/cpu/smt/control   # on, off, notsupported …

NUMA: 가까운 메모리와 먼 메모리

왜 알아야 하나큰 서버에서는 같은 메모리 읽기도 CPU에 따라 속도가 다르다. 프로그램, 메모리, 장치가 서로 멀리 있으면 느려진다. 평균 사용률만 보면 이 원인이 보이지 않는다.

  • NUMA(Non-Uniform Memory Access)는 "메모리까지의 거리가 같지 않다"는 뜻이다.
  • 왜 생겼나: CPU가 많아지면 메모리 통로 하나로는 모자란다. 그래서 CPU를 묶음으로 나누고, 묶음마다 자기 메모리를 붙인다. 이 묶음이 NUMA node다.
  • 자기 node의 메모리(local)는 빠르다. 다른 node의 메모리(remote)는 통로를 지나야 해서 느리다.
  • 소켓이 여러 개면 보통 소켓마다 node가 생긴다. 소켓이 하나여도 BIOS 설정으로 나눌 수 있다(AMD의 NPS, Intel의 SNC 같은 설정).
  • 리눅스는 기본으로 메모리를 그 메모리를 처음 쓰는 CPU의 node에 둔다(first-touch).
  • NVMe, NIC 같은 PCIe 장치도 한 node에 붙는다.
자주 하는 오해NUMA node는 Kubernetes의 node가 아니다. 서버 한 대 안의 "CPU와 메모리 묶음"이다.
promet과 비교promet은 데스크톱 CPU 1개다. NUMA node가 1개뿐이다. 모든 메모리가 같은 거리에 있다. 그래서 이 차이는 promet에서 실험할 수 없다.
직접 확인 
lscpu | grep -i numa          # node 수와 node마다의 CPU 번호
numactl --hardware             # node마다 메모리 크기와 거리표 (numactl 패키지)
cat /sys/class/net/<인터페이스>/device/numa_node   # 랜카드가 붙은 node. -1이면 정보 없음

SMT와 NUMA는 다른 층이다

왜 알아야 하나두 단어가 같이 나오면 같은 종류의 설정처럼 보인다. 실제로는 크기가 다른 층의 이야기다. 그래서 한 서버에 둘이 같이 있을 수 있다.

NVMe: SSD가 말하는 방식

왜 알아야 하나"NVMe SSD"와 "SATA SSD"는 둘 다 SSD다. 하지만 동시에 처리할 수 있는 요청 수가 크게 다르다. 작은 읽기와 쓰기를 동시에 아주 많이 하는 프로그램에서는 이 차이가 속도를 정한다.

저장장치는 두 가지로 나눠 본다.

  • 어느 길로 연결되나: SATA 케이블, 또는 PCIe 레인(메인보드의 고속 통로).
  • 그 길에서 어떤 규칙으로 말하나: AHCI, 또는 NVMe.
  • SATA SSD는 SATA 길에서 AHCI로 말한다. AHCI는 원래 HDD를 위해 만든 규칙이다. 명령 줄(큐)이 1개이고, 한 줄에 32개까지 기다린다.
  • NVMe SSD는 PCIe 길에서 NVMe로 말한다. 줄을 아주 많이 만들 수 있다. 그래서 여러 CPU가 줄 하나를 두고 다투지 않는다.
자주 하는 오해NVMe는 SSD의 모양(M.2)이 아니다. M.2 모양의 SATA SSD도 있다. NVMe는 말하는 규칙이다.
promet과 비교promet의 MX500은 SATA SSD다(AHCI). WD Blue는 HDD다. 그래서 promet에서는 NVMe의 동시 처리를 시험할 수 없다. 측정 방법(IOPS, 지연)은 같다.
직접 확인 
lsblk -d -o NAME,TRAN,ROTA,MODEL,SIZE   # TRAN: sata 또는 nvme. ROTA 1: 회전하는 디스크
cat /sys/block/sda/device/queue_depth   # SATA 장치가 한 번에 받는 요청 수
ls /sys/block/nvme0n1/mq/               # NVMe가 있으면: 하드웨어 줄마다 디렉터리 하나

RAID0: 디스크 여러 개를 하나처럼

왜 알아야 하나큰 서버는 디스크 여러 개를 묶어 하나처럼 쓴다. 묶는 방법에 따라 속도, 용량, 고장 때의 결과가 다르다. 디스크 하나가 고장 나면 무엇을 잃는지 미리 알아야 한다.

  • 디스크 한 개에는 한계가 셋 있다: 용량, 속도, 고장. RAID는 디스크 여러 개를 묶어서 OS에 디스크 하나처럼 보이게 한다. 묶는 방법마다 번호(레벨)가 있다.
  • RAID0(스트라이핑): 데이터를 조각으로 잘라 디스크에 번갈아 쓴다. 용량은 합쳐진다. 큰 읽기와 쓰기는 거의 디스크 수만큼 빨라진다.
  • 대가: 디스크 하나만 고장 나도 전체를 잃는다. 모든 파일의 조각이 모든 디스크에 흩어져 있기 때문이다. 디스크가 많을수록 고장 확률도 커진다.
  • 자르는 단위를 chunk(stripe unit)라고 한다. 크기는 정할 수 있다(mdadm 기본 512KiB). 놓는 규칙은 고정이다: chunk 번호를 디스크 수로 나눈 나머지가 디스크 번호다(라운드로빈). 규칙이 계산이라서 "어느 조각이 어디 있나"를 적는 장부가 필요 없다.
  • chunk 크기의 효과: 큰 파일 하나를 읽을 때는 chunk가 작을수록 여러 디스크가 같이 일한다. 작은 요청이 많을 때는 요청 하나가 디스크 하나에서 끝나는 편이 낫다. chunk가 작으면 작은 요청도 chunk 경계에 걸려 디스크 둘로 나뉠 수 있다. 어느 쪽이 좋은지는 작업 형태가 정한다.
  • RAID1(미러링): 같은 데이터를 두 디스크에 똑같이 쓴다. 하나가 고장 나도 남는다. 용량은 절반이다.
  • 리눅스에서는 소프트웨어 RAID(mdadm)를 많이 쓴다. 묶은 장치는 /dev/md0 같은 이름이 된다.
자주 하는 오해RAID는 백업이 아니다. RAID1도 실수로 지운 파일은 두 디스크에서 같이 지운다.
promet과 비교promet은 SSD 1개와 HDD 1개를 따로 쓴다. RAID가 없다. 디스크 하나가 고장 나면 그 디스크의 데이터만 잃는다.

생각해 볼 질문블록체인 노드의 데이터를 잃으면, 다시 구할 방법이 있을까? 은행의 데이터베이스를 잃는 것과 무엇이 다를까?

직접 확인 
cat /proc/mdstat    # 소프트웨어 RAID가 있으면 여기에 보인다
lsblk               # TYPE 열에 raid0, raid1이 보인다

NIC와 드라이버

왜 알아야 하나네트워크 문제는 프로그램이 아니라 랜카드나 드라이버에서 생길 수 있다. 어느 카드가 어느 드라이버로 움직이는지 알아야 맞는 문서를 찾을 수 있다.

  • NIC(Network Interface Card)는 랜카드다. 패킷을 신호로 바꿔 케이블로 보낸다. 서버의 NIC는 보통 PCIe 장치다.
  • 드라이버는 커널이 그 카드와 말하는 방법을 담은 프로그램(커널 모듈)이다. 카드 회사와 모델마다 다르다.
  • 드라이버가 카드를 찾으면 커널이 인터페이스를 만든다. IP는 그 인터페이스에 붙는다.
  • 인터페이스 이름은 카드의 위치를 뜻한다(systemd의 이름 규칙). en 유선, wl 무선. o1 메인보드 내장 1번. p3s0 PCI 버스 3, 슬롯 0. s3 확장 슬롯 3. f1 PCI 기능 번호 1(포트가 여럿인 카드는 포트마다 다르다). n… 드라이버가 알려 준 포트 이름(예: np0은 포트 이름 p0).
자주 하는 오해이름 모양이 같아도 카드 종류는 다를 수 있다. 이름은 위치를 뜻한다. 카드와 드라이버는 ethtool -i로 본다.
promet과 비교promet의 NIC는 메인보드 내장 Intel I219-LM이다. 이 카드의 리눅스 드라이버는 보통 e1000e다. 내장 카드라서 이름은 보통 eno1 같은 모양이다. 정확한 이름은 아래 명령으로 확인한다.
직접 확인 
ip -br link                     # 인터페이스 이름과 상태
lspci | grep -i ethernet        # PCIe에 붙은 랜카드
ethtool -i <인터페이스>          # driver, firmware-version, bus-info
cat /sys/class/net/<인터페이스>/device/numa_node

Solana 기본 SOLANA

Solana가 블록을 만들고, 저장하고, 질문에 답하는 방식이다. 내 Bitcoin 노드와 비교한다.

Solana 전체 지도: cluster, validator, RPC 노드

왜 알아야 하나Solana의 단어는 Bitcoin과 겹치지만 뜻이 다르다. 누가 블록을 만들고, 누가 확인하고, 누가 사용자에게 답하는지 먼저 나눠야 한다.

  • cluster: 같은 장부를 같이 만드는 노드들의 모임이다. 실제 돈이 오가는 mainnet-beta, 시험용 testnet과 devnet이 있다. cluster마다 처음 설정(genesis)이 달라서 서로 섞이지 않는다.
  • validator: 블록을 받아 검증하고 투표하는 노드다. 맡긴 SOL의 양(stake)이 클수록 투표의 무게가 크다.
  • leader: 정해진 시간 칸(slot)에 블록을 만드는 validator다. 순서는 미리 정해져 있다. 돌아가며 맡는다.
  • RPC 노드: 같은 프로그램으로 블록을 받아 검증하고 저장한다. 하지만 투표하지 않는다. 사용자와 앱의 질문에 답하는 것이 주된 일이다.
  • 노드 프로그램(client)은 여러 개 있다. 많이 쓰는 것은 Anza의 Agave다. Jump Crypto의 Firedancer도 있다.
  • validator는 키를 셋 쓴다: identity, vote account, withdrawer. 투표하지 않는 RPC 노드에는 vote account가 없다. 자세한 것은 keypair 카드에 있다.
자주 하는 오해"RPC 노드"는 특별한 다른 프로그램이 아니다. validator와 같은 프로그램을 다른 역할로 실행한 것이다.
내 Bitcoin 노드와 비교Bitcoin에는 정해진 leader가 없다. 채굴자가 작업증명(PoW)으로 경쟁해서 먼저 찾은 쪽이 블록을 만든다. 내 bitcoind는 블록을 검증하고 저장하지만 채굴하지 않는다. 이 점에서 Solana의 RPC 노드와 역할이 비슷하다. Signet은 시험용 네트워크라는 점에서 devnet, testnet과 비슷하다.

slot, 블록 높이, epoch

왜 알아야 하나Solana의 시간은 slot으로 센다. slot 번호와 블록 높이는 다른 숫자다. 둘을 섞으면 "이 slot에는 블록이 없다"는 응답을 오류로 잘못 읽는다.

  • slot: leader 한 명이 블록 하나를 만들 수 있는 시간 칸이다. 목표 길이는 약 400ms다.
  • leader는 slot 4개를 연속으로 맡는다. 그다음 다른 leader로 넘어간다.
  • leader가 블록을 못 만들거나 그 블록이 받아들여지지 않으면 그 slot은 건너뛴 slot(skipped)이 된다. 그 slot에는 블록이 없다.
  • 그래서 slot 번호는 시간에 따라 늘고, 블록 높이(block height)는 블록이 있을 때만 는다. 블록 높이는 slot 번호보다 작다.
  • epoch: slot 432,000개다(mainnet-beta 기준, 약 2일 이상). epoch마다 stake를 보고 leader 순서표(leader schedule)를 정한다.
  • Solana는 거의 모든 것을 slot 번호로 부른다. getBlock도 블록 높이가 아니라 slot 번호를 받는다. snapshot 파일 이름에도 slot이 들어간다. 빈 slot에는 블록이 없으므로 그 slot의 snapshot도 없다.
  • getSlot은 지금의 slot 번호를 준다. getBlockHeight는 지금까지의 블록 수를 준다. 두 메서드가 따로 있는 이유가 이것이다.
내 Bitcoin 노드와 비교Bitcoin은 블록 사이가 평균 10분이다. 정해진 시간 칸이 없다. 그래서 Bitcoin에는 "높이"만 있다. Solana에는 시간 칸(slot)과 높이가 따로 있다.

curl -s https://api.devnet.solana.com -X POST -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"getEpochInfo"}'
# absoluteSlot(slot 번호)과 blockHeight(블록 높이)를 비교한다

트랜잭션과 서명

왜 알아야 하나Solana에서 트랜잭션을 찾는 열쇠는 서명이다. 트랜잭션의 구조를 알아야 "서명으로 트랜잭션을 찾는다"는 말이 이해된다.

  • 트랜잭션 = 서명들 + 메시지다. 메시지에는 쓸 계정 목록, 최근 블록 해시(recent blockhash), 명령(instruction)들이 있다.
  • instruction: "어느 프로그램에게, 어떤 계정으로, 무엇을 하라"는 요청 하나다. 트랜잭션 하나에 여러 개가 들어갈 수 있다. 전부 성공하거나 전부 취소된다.
  • 첫 번째 서명이 트랜잭션의 ID다. 64바이트이고, 사람이 읽을 때는 base58 글자(약 88자)로 쓴다.
  • recent blockhash는 약 150블록 동안만 유효하다(대략 1분 남짓). 그래서 오래된 트랜잭션을 다시 보내도 처리되지 않는다.
  • Compute Unit(CU): 트랜잭션이 쓰는 계산량의 단위다. 트랜잭션마다 한도가 있고, 블록 전체에도 한도가 있다.
자주 하는 오해"서명"과 "해시"는 다르다. 해시는 누구나 계산할 수 있다. 서명은 비밀키를 가진 사람만 만들 수 있다.
내 Bitcoin 노드와 비교Bitcoin의 txid는 트랜잭션 내용의 해시다(SHA-256 두 번). Solana의 ID는 해시가 아니라 서명이다. 또 Bitcoin은 UTXO를 쓰고 없앤다. Solana는 계정(account)의 값을 바꾼다.

ledger, blockstore, shred, genesis

왜 알아야 하나노드의 디스크에는 "기록"과 "상태"가 따로 쌓인다. ledger는 기록 쪽이다. 둘을 구분해야 snapshot과 디스크 사용량을 이해할 수 있다.

  • ledger: slot마다의 블록과 트랜잭션 기록이다. 노드는 이것을 blockstore에 저장한다. blockstore는 RocksDB(키-값 데이터베이스)다.
  • shred: leader는 블록을 작은 조각으로 잘라 보낸다. 조각 하나는 UDP 패킷 하나에 들어간다.
  • 조각은 두 종류다: 데이터 shred와 복구용 shred(coding shred). 데이터 조각 일부를 잃어도 복구용 조각으로 다시 만든다(erasure coding).
  • 조각은 나무 모양으로 퍼진다(Turbine). leader가 모든 노드에 직접 보내지 않는다. 받은 노드가 다음 노드들에게 넘긴다.
  • genesis: slot 0의 설정이다. 처음 계정들과 규칙(예: epoch 길이)이 들어 있다. 파일 이름은 genesis.bin이다. genesis의 해시로 cluster를 구분한다.
  • genesis 해시가 다르면 다른 cluster다. 그래서 genesis 해시는 cluster의 신분증 번호와 같다. getGenesisHash로 물을 수 있다.
자주 하는 오해ledger와 계정 상태는 다르다. ledger는 "무슨 일이 있었나"(기록)다. 계정 상태는 "지금 얼마인가"(결과)다. 상태는 accounts DB에 따로 있다.
내 Bitcoin 노드와 비교bitcoind는 블록을 blocks/blk*.dat 파일에 쌓고, 블록의 위치를 LevelDB 인덱스에 둔다. Bitcoin의 genesis 블록은 프로그램 코드 안에 들어 있다. Solana는 genesis를 파일로 받는다. Signet도 mainnet과 genesis 블록이 다르다. 그래서 같은 bitcoind 프로그램이라도 두 네트워크의 블록은 섞이지 않는다.

  curl -s $u -X POST -H 'Content-Type: application/json' \
    -d '{"jsonrpc":"2.0","id":1,"method":"getGenesisHash"}'; echo
done   # cluster마다 genesis 해시가 다르다

snapshot: full과 incremental

왜 알아야 하나새 노드는 처음 블록부터 모두 다시 실행하지 않는다. 다른 노드가 만든 상태의 사진(snapshot)에서 시작한다. snapshot에 무엇이 있고 무엇이 없는지 알아야 한다.

  • snapshot: 어느 slot 시점의 계정 상태 전체를 묶은 파일이다. 상태만 있다. 그 이전의 블록과 트랜잭션 기록은 없다.
  • full snapshot: 그 시점의 상태 전부다. 크다.
  • incremental snapshot: 어느 full snapshot 뒤에 바뀐 계정만 담는다. 작다. 기준(base)이 되는 full snapshot이 있어야 쓸 수 있다.
  • 새 노드는 full 하나와, 같은 base의 가장 새 incremental 하나를 내려받는다. 그 시점의 상태를 만들고, 그 뒤의 블록을 받아 실행해서 따라잡는다.
  • 노드는 실행 중에도 자기 snapshot을 주기적으로 만든다. 다시 시작할 때 쓴다.
  • 파일 이름에 slot 번호가 있다: snapshot-<slot>-<해시>.tar.zst, incremental-snapshot-<base slot>-<slot>-<해시>.tar.zst.
자주 하는 오해snapshot은 노드 데이터 전체의 백업이 아니다. 상태만 있다. snapshot에서 시작한 노드는 그 이전 slot의 블록을 자기 디스크에 갖고 있지 않다.
내 Bitcoin 노드와 비교내 bitcoind는 IBD에서 genesis부터 모든 블록을 검증했다. Bitcoin Core에도 비슷한 방법(assumeutxo: UTXO 집합의 사진에서 시작)이 있다. 하지만 Bitcoin Core는 그 뒤에 처음부터 다시 검증하는 일을 뒤에서 한다. Solana 노드는 snapshot의 해시를 확인하고 그 시점부터 시작한다.

account와 accounts DB

왜 알아야 하나Solana의 상태는 모두 계정(account)이다. 노드가 메모리를 많이 쓰는 큰 이유 하나가 계정의 수다.

  • 계정 하나는 주소와 다섯 가지 값을 가진다: lamports(잔액), owner(이 계정을 바꿀 수 있는 프로그램), data(바이트), executable(프로그램인가), rent_epoch.
  • 1 SOL = 1,000,000,000 lamports다.
  • 프로그램(스마트 컨트랙트)도 계정이다. executable이 true다. 프로그램이 다루는 데이터는 다른 계정들에 따로 둔다.
  • owner인 프로그램만 그 계정의 data를 바꾸거나 lamports를 뺄 수 있다.
  • 노드는 계정들을 accounts DB(디스크의 파일들)에 둔다. 주소로 빨리 찾기 위해 인덱스(주소 → 위치)를 메모리에 둔다. 계정이 아주 많아서 이 인덱스가 메모리를 많이 쓴다.
자주 하는 오해"계정"은 "지갑 하나"가 아니다. 지갑 주소도 계정이다. 하지만 토큰 잔액, 프로그램, 프로그램의 데이터도 각각 계정이다.
내 Bitcoin 노드와 비교bitcoind의 상태는 UTXO 집합이다. chainstate(LevelDB)에 있고, dbcache가 그 메모리 캐시다. Solana의 상태는 계정 집합이다. 둘 다 "기록(블록)"과 "지금 상태"를 따로 둔다.

상태와 기록: 지금에서 과거로 갈 수 없다

왜 알아야 하나노드에는 "지금 얼마인가"(상태)와 "무슨 일이 있었나"(기록)가 따로 있다. 하나로 다른 하나를 대신할 수 없다. 이것을 알아야 새 노드가 어떤 질문에 답하지 못하는지 안다.

  • 상태는 결과의 요약이다. Solana에서는 계정 집합(accounts)이다. snapshot은 어느 slot의 상태를 파일로 저장한 것이다.
  • 기록은 과정이다. 블록과 트랜잭션이다. 노드는 이것을 blockstore에 쌓는다.
  • 요약에서는 과정이 사라진다. 잔고가 100만 원인 통장을 생각한다. 그 잔고를 만든 과거는 여러 가지일 수 있다. 그래서 지금에서 과거를 거꾸로 계산할 수 없다. 해시를 거꾸로 풀 수 없는 것과 비슷하다.
  • 새 노드는 snapshot에서 시작한다. 그래서 그 slot부터 앞으로 오는 블록만 자기 디스크에 쌓는다. 그 이전의 블록은 없다.
  • 새 블록을 검증하는 데는 상태만 있으면 된다. 과거 블록은 필요 없다. 그래서 운영자는 기록을 얼마나 오래 둘지 고를 수 있다. 오래 둘수록 디스크를 많이 쓴다.
  • 노드끼리 빠진 조각을 요청하는 기능이 있다(repair). 이것은 지금 따라잡는 데 필요한 최근 조각을 채운다. 오래된 기록을 통째로 받는 기능이 아니다.
자주 하는 오해"그때의 snapshot이 있으면 그때 일을 안다"는 반만 맞다. 그때의 잔액(과거 상태)은 안다. 하지만 누가 누구에게 보냈는지(과거 기록)는 모른다. snapshot에는 거래 내역이 없다.
내 Bitcoin 노드와 비교bitcoind의 상태는 UTXO 집합(chainstate)이다. 기록은 blocks/의 블록 파일이다. -prune을 쓰면 오래된 블록 파일을 지운다. 그래도 UTXO 집합은 전부 남는다. 그래서 pruned 노드도 새 블록을 검증한다. 하지만 지운 블록을 묻는 getblock에는 답하지 못한다. Solana 노드가 기록을 얼마나 둘지 정하는 것도 같은 성격이다.

Solana RPC: HTTP와 WebSocket

왜 알아야 하나앱은 노드 안을 직접 보지 않는다. RPC로 묻는다. 묻는 방법은 두 가지(HTTP, WebSocket)다. 답이 얼마나 확정된 것인지(commitment)도 고를 수 있다.

  • Solana RPC는 JSON-RPC 2.0 형식이다. 요청에 method와 params를 넣는다. 답은 result나 error로 온다.
  • HTTP: POST 요청 하나에 답 하나다. 예: getSlot(지금 slot), getBalance(잔액), getBlock(slot 번호로 블록 하나), getTransaction(서명으로 트랜잭션 하나).
  • WebSocket: 연결을 열어 두고 구독(subscribe)한다. 그 뒤 값이 바뀔 때마다 노드가 먼저 보낸다. 예: slotSubscribe, accountSubscribe, signatureSubscribe.
  • commitment: 답의 확정 정도다. processed(이 노드가 처리함. 뒤집힐 수 있다) → confirmed(stake의 3분의 2 이상이 투표함) → finalized(그 위에 블록이 충분히 쌓여 되돌릴 수 없음).
  • WebSocket 구독은 짝으로 쓴다. 예: accountSubscribe와 accountUnsubscribe. programSubscribe, signatureSubscribe, logsSubscribe, slotSubscribe, slotsUpdatesSubscribe에도 각각 Unsubscribe가 있다. 구독하면 번호를 받는다. 취소할 때 그 번호를 준다.
  • 누가 구독하나: 지갑 앱은 내 계정을 구독해서 잔액을 바로 바꾼다. 거래소는 입금 트랜잭션의 서명을 구독해서 확정되는 순간 처리한다. 모니터링 도구는 slot을 구독해서 체인이 멈추지 않았는지 본다.
  • 메서드마다 무게가 다르다. getHealth는 "정상인가"만 묻는다. getProgramAccounts는 한 프로그램이 가진 계정을 모두 뒤진다. 무거운 요청이 몰리면 노드가 새 블록을 따라가는 일도 느려질 수 있다. 그래서 RPC는 보통 아무에게나 열지 않는다.
자주 하는 오해JSON-RPC의 "RPC"와 노드 종류의 "RPC 노드"는 같은 말에서 왔지만 다른 것이다. validator도 RPC 요청에 답할 수 있다. RPC 노드는 그 일을 주로 하는 노드다.
내 Bitcoin 노드와 비교bitcoin-cli getblockcount도 JSON-RPC 요청이다. HTTP POST로 bitcoind에 묻는다. bitcoind의 RPC는 쿠키나 비밀번호로 인증한다. Bitcoin의 "확정"은 블록 위에 쌓인 블록 수(confirmations)로 센다.

# commitment를 processed로 바꿔서 다시 묻는다. 숫자가 왜 다른지 생각해 본다

RPC의 층: TCP, HTTP, JSON-RPC, WebSocket

왜 알아야 하나RPC 문서에는 TCP, HTTP, JSON-RPC, WebSocket이 함께 나온다. 이 말들은 서로 다른 층을 가리킨다. 층을 나눠야 "어느 포트가 무엇에 쓰이나"와 "왜 연결이 끊기나"를 읽을 수 있다.

  • TCP: 도로와 트럭이다. 바이트를 빠짐없이, 순서대로 나른다. 포트 번호는 이 층에서 쓰인다.
  • HTTP: 우체국 규칙이다. 요청 하나를 보내면 답 하나가 온다. 서버가 먼저 말을 걸 수 없다. 그래서 새 소식을 알려면 계속 다시 물어야 한다.
  • WebSocket: 전화다. 처음에 HTTP 요청으로 "WebSocket으로 바꾸자(Upgrade)"고 한다. 서버가 101로 답하면 같은 TCP 연결을 계속 열어 둔다. 그 뒤로는 양쪽이 아무 때나 말한다. 그래서 HTTP와 WebSocket은 둘 다 TCP 포트를 쓴다.
  • JSON-RPC: 편지 양식이다. method에 부를 함수 이름, params에 인자, id에 편지 번호를 쓴다. HTTP로 보내든 WebSocket으로 보내든 양식은 같다.
  • RPC의 P(procedure)는 함수다. 데몬은 식당이고, 메서드는 메뉴 하나다. 요청의 "method":"getBalance"는 노드 코드 안의 함수 하나로 이어진다. 그래서 "원격에서 함수를 부른다"는 말이 그대로 맞다.
  • JSON은 글자 형식이다. 언어와 관계없다. 그래서 Rust로 만든 노드와 JavaScript로 만든 지갑이 대화할 수 있다. gRPC는 다른 선택이다. 사람이 읽을 수 없는 이진 형식(protobuf)을 쓴다. 대신 작고 빠르다. 양쪽이 같은 설계도(.proto 파일)를 먼저 나눠 가져야 한다. gRPC는 Google이 만들었고, Go 전용이 아니다.
  • 노드끼리의 통신(gossip, 블록 조각 전달, repair)은 주로 UDP다. 앱과 노드 사이의 RPC는 TCP다. 한 노드 프로그램 안에 둘이 섞여 있다.
자주 하는 오해RPC와 WebSocket은 블록체인만의 기술이 아니다. 회사 안의 서비스끼리 gRPC로 대화한다. VS Code는 언어 서버와 JSON-RPC로 대화한다. 채팅, 실시간 시세, 게임 알림은 WebSocket을 쓴다. 노드는 이미 있는 기술을 가져다 쓴 것이다.
내 Bitcoin 노드와 비교bitcoind의 RPC도 HTTP 위의 JSON-RPC다. bitcoin-cli는 HTTP POST로 JSON을 보낸다. bitcoind에는 WebSocket이 없다. 새 블록을 바로 알고 싶으면 ZMQ 알림(-zmqpubhashblock)을 쓴다. "서버가 먼저 알린다"는 목적은 같다.

응답의 두 부분: transaction과 meta

왜 알아야 하나getBlock과 getTransaction의 응답은 두 부분으로 되어 있다. 한 부분은 사용자가 보낸 것이다. 다른 부분은 노드가 실행해서 만든 것이다. 두 응답이 다르면, 어느 부분이 왜 다른지 나눠서 봐야 한다.

  • getBlock(slot)은 그 slot의 블록을 준다: blockhash, 부모 slot, 시간, 트랜잭션 목록. getTransaction(서명)은 트랜잭션 하나를 준다.
  • transaction: 사용자가 보낸 원본이다. 서명, 계정 목록, 명령이 있다. 주문서와 같다.
  • meta: 실행한 결과다. 영수증과 같다. 예: 수수료(fee), 성공 여부(err), 실행 전후 잔액(preBalances, postBalances), 로그(logMessages), 내부 호출(innerInstructions), 쓴 계산량(computeUnitsConsumed). 전체 목록은 Solana 공식 문서의 getTransaction 설명에 있다.
  • 실행 결과는 모든 노드에서 같아야 한다. 모든 노드가 같은 상태에서 같은 트랜잭션을 같은 순서로 실행하기 때문이다. 결과가 다르면 노드끼리 합의가 깨진다.
  • 노드마다 다를 수 있는 것은 저장이다. 노드는 실행하면서 meta를 만들고, 그다음 디스크에 저장한다. 무엇을 얼마나 오래 저장하는지는 노드마다 다를 수 있다. 저장하지 않은 것은 나중에 다시 만들 수 없다. 다시 만들려면 그때의 상태가 필요하기 때문이다.
자주 하는 오해"CU"라는 이름이 두 곳에서 쓰인다. Solana의 compute unit은 트랜잭션이 실행에 쓴 계산량이다(meta에 있다). RPC 서비스 회사의 가격표에 나오는 CU는 요청 한 번의 요금 단위다. 둘은 관계가 없다.
내 Bitcoin 노드와 비교Bitcoin 트랜잭션에도 수수료 칸이 없다. 수수료는 입력의 합에서 출력의 합을 빼서 계산한다. 그래서 이전 출력의 값을 알아야 한다. bitcoind는 블록을 검증할 때 쓴 이전 출력을 undo 파일(rev*.dat)에 둔다. getblock의 verbosity 2는 이 파일로 트랜잭션마다 fee를 보여 준다. undo 파일이 없는 블록에서는 이 칸이 빠진다.

gossip과 ContactInfo: 도달과 광고

왜 알아야 하나Solana 노드는 처음에 다른 노드의 주소를 모른다. gossip으로 서로의 "명함"을 주고받아서 찾는다. 명함에 무엇이 적히는지 알아야, 다른 노드가 내 노드의 어느 문으로 무엇을 보낼지 안다.

  • gossip: 노드끼리 소식을 퍼뜨리는 통신이다. 받은 소식을 다른 몇 노드에게 다시 전한다. 그래서 곧 모든 노드가 같은 소식을 안다. 주로 UDP를 쓴다.
  • entrypoint: 처음 연결할 노드의 주소다. 새 노드는 entrypoint에 붙어서 다른 노드들의 명함을 받는다.
  • ContactInfo: 노드의 명함이다. identity 공개키와 용도별 주소(IP:포트)가 있다. 예: gossip, 블록 조각 받기(TVU), 빠진 조각 요청(repair), 트랜잭션 받기(TPU), RPC, RPC의 WebSocket(pubsub). 쓰지 않는 용도는 비어 있다.
  • 다른 노드는 명함에 적힌 주소로만 보낸다. 적히지 않은 포트로는 먼저 찾아오지 않는다.
  • 도달과 광고는 다른 질문이다. 도달은 "그 문까지 갈 수 있나"다. 리슨 주소와 방화벽이 정한다. 광고는 "명함에 그 문이 적혀 있나"다. 문을 닫아도 명함에 적힐 수 있다. 명함에 없어도 문이 열려 있을 수 있다.
내 Bitcoin 노드와 비교bitcoind도 자기 주소를 다른 노드에게 알린다(addr 메시지). 처음 피어를 찾을 때는 DNS seed에 묻는다. 이것이 entrypoint와 비슷한 역할이다. inbound를 열 때 쓰는 -externalip는 "명함에 이 주소를 적어라"는 설정이다. 공유기의 포트 포워딩은 "문까지 오게 하라"는 설정이다. 외부 피어가 찾아와서 들어오려면 둘 다 필요하다.

생각해 볼 질문명함에 적힌 주소의 문이 실제로는 닫혀 있다. 다른 노드는 어떻게 될까? 반대로 문은 열려 있는데 명함에는 없다. 누가 그 문에 올 수 있을까?

# 노드 하나의 명함: pubkey, gossip, tpu, rpc 등. 비어 있는 칸은 null

keypair: 노드의 이름과 도장

왜 알아야 하나Solana 노드는 keypair 파일로 자기를 증명한다. 이 파일이 새면 다른 사람이 내 노드인 척할 수 있다. 어떤 키가 무엇에 쓰이는지 알아야 무엇을 지킬지 안다.

  • keypair = 비밀키 + 공개키다. 비밀키로 서명(도장)을 만든다. 누구나 공개키로 그 서명을 확인한다. 공개키에서 비밀키를 계산할 수는 없다. Solana는 Ed25519 방식을 쓴다.
  • 공개키는 base58 글자로 쓴다. 이것이 노드나 지갑의 이름(주소)이다. SSH 키와 같은 생각이다: 공개키는 남에게 주고, 비밀키는 내가 지킨다.
  • keypair 파일은 JSON 숫자 64개다. 앞 32바이트는 비밀 쪽, 뒤 32바이트는 공개키다. 그래서 이 파일 하나가 곧 비밀키다. 소유자만 읽게(600) 둔다.
  • seed phrase: 단어 12개 또는 24개다(BIP39 규칙). 이 단어들로 같은 keypair를 다시 만들 수 있다. 그래서 단어를 아는 사람은 키를 가진 것과 같다. passphrase를 더하면 단어와 passphrase가 모두 있어야 같은 키가 나온다.
  • paper wallet: 키나 seed phrase를 종이에만 적어 둔다. 네트워크에 붙은 컴퓨터에 없으므로 해킹으로 훔칠 수 없다. 이렇게 오프라인에 두는 것을 cold wallet이라고 한다.
  • vanity 공개키: 앞글자를 내가 고른 공개키다. 자동차 번호판에서 원하는 번호를 고르는 것과 같다. 공개키는 계산의 결과라서 직접 고를 수 없다. 그래서 keypair를 아주 많이 만들어 보고 맞는 것을 찾는다. 이 일을 solana-keygen grind가 한다. 고를 글자가 하나 늘 때마다 약 58배 오래 걸린다.
  • validator의 키는 셋이다. identity: 네트워크에서 이 노드가 누구인가(모든 노드). vote account: 투표를 기록하는 계정(투표하는 노드). withdrawer: vote account의 돈을 꺼내는 권한. 서버에 두지 않고 따로 보관한다. 투표하지 않는 노드에는 vote account가 없다.
자주 하는 오해SPL Token은 키가 아니다. Solana 위에서 토큰을 만들고 옮기는 프로그램이다. "token"이라는 단어 때문에 로그인 토큰이나 인증 키로 읽으면 안 된다.
내 Bitcoin 노드와 비교bitcoind 노드 자체에는 identity 키가 없다. 피어는 IP 주소로 구분한다. 키는 지갑에만 있다. seed phrase의 규칙(BIP39)은 Bitcoin 개선 제안에서 나왔다. Bitcoin Core 지갑은 이 단어 방식을 쓰지 않지만, 다른 많은 지갑이 쓴다. vanity 주소(예: 1Love…로 시작)도 같은 방법으로 찾는다: 많이 만들어 보고 고른다.

bash 스크립트: 종료 코드와 set -euo pipefail

왜 알아야 하나bash는 기본으로 명령이 실패해도 다음 줄을 계속 실행한다. 설치 스크립트가 중간에 실패한 것을 모르고 끝까지 가면, 반쯤 바뀐 서버가 남는다. 실패를 어떻게 알아채는지 알아야 안전한 스크립트를 쓸 수 있다.

  • 모든 명령은 끝날 때 종료 코드(exit code)를 남긴다. 0은 성공이다. 0이 아니면 실패다. 바로 앞 명령의 코드는 $?에 있다.
  • set -e: 명령이 실패하면 스크립트를 멈춘다. 단, if의 조건 안과 &&, || 앞의 명령은 예외다. 그 자리는 실패를 직접 다루는 자리이기 때문이다.
  • set -u: 정하지 않은 변수를 쓰면 오류로 멈춘다. 변수 이름의 오타를 잡는다. 오타 난 변수는 빈 값이 된다. 경로에 쓰면 엉뚱한 곳(예: /)을 가리킬 수 있다.
  • set -o pipefail: 파이프(a | b)의 결과를 정한다. bash는 기본으로 마지막 명령의 코드만 본다. 그래서 a가 실패해도 성공으로 본다. pipefail을 켜면 하나라도 실패하면 실패다.
  • set -x: 실행하는 줄을 찍는다. 디버깅에 좋다. 대신 변수에 담은 비밀값도 그대로 찍힌다.
  • 변수: NAME=값(= 양쪽에 공백이 없다). 쓸 때는 "$NAME"처럼 따옴표로 감싼다. 따옴표가 없으면 값의 공백에서 단어가 나뉘고, 빈 값은 사라진다. 바꾸지 않을 값은 대문자 이름을 쓰는 관례가 있다.
  • 조건: if [ ! -f "$FILE" ]; then … fi. [도 명령이라서 양쪽에 공백이 꼭 있어야 한다. -f 일반 파일, -d 디렉터리, -e 무엇이든 있음, ! 반대.
  • 옵션을 모르면 프로그램 --help를 본다. 많은 프로그램이 옵션마다 [default: 값]을 적는다. 이것이 그 버전의 기본값이다. 버전이 바뀌면 바뀔 수 있다.
자주 하는 오해set -e가 모든 실패를 잡지는 않는다. if 조건, &&와 || 앞, pipefail이 없을 때의 파이프 앞쪽은 빠진다. 그래서 중요한 단계는 결과를 직접 확인한다.
내 환경과 비교inbound 실습의 timeout 3 bash -c '</dev/tcp/172.18.0.2/30333' && echo OPEN || echo CLOSED도 종료 코드를 쓴 것이다. 연결되면 0이라서 OPEN을, 안 되면 0이 아니라서 CLOSED를 찍었다.

생각해 볼 질문pipefail을 켠 스크립트에서 grep 없는말 파일 | wc -l을 실행한다. 어떻게 될까? 찾은 줄이 0개인 것은 "실패"일까?

직접 확인 
false; echo $?                                           # 1
bash -c 'false | true; echo $?'                          # 0: 마지막 명령만 본다
bash -c 'set -o pipefail; false | true; echo $?'         # 1
bash -c 'set -u; echo "$NO_SUCH_VAR"'; echo $?           # 오류 메시지, 그리고 1
bash -n 내스크립트.sh                                      # 실행하지 않고 문법만 검사한다

멱등성: 여러 번 실행해도 같은 결과

왜 알아야 하나설치·설정 스크립트는 중간에 실패하면 다시 실행한다. 두 번 실행해서 결과가 달라지면(중복된 줄, 오류, 두 번 시작) 문제가 커진다.

  • 멱등(idempotent): 한 번 실행한 결과와 여러 번 실행한 결과가 같은 성질이다.
  • 멱등이 아닌 예: mkdir dir(두 번째에 오류), echo 줄 >> 파일(줄이 두 번 들어간다), kubectl create(두 번째에 AlreadyExists 오류).
  • 멱등인 예: mkdir -p dir, 파일 전체를 다시 쓰기(>), kubectl apply, systemctl enable.
  • 만드는 방법: "이것을 하라" 대신 "이 상태여야 한다"로 쓴다. 또는 바꾸기 전에 지금 상태를 확인한다.
  • 있는지 먼저 보는 패턴: [ -f "$F" ] || 만드는 명령. 파일이 없을 때만 만든다. 이미 있는 파일을 다시 만들어 덮어쓰지 않는다.
  • 설정 파일은 통째로 쓴다: cat > 파일 <<'EOF' … EOF. 몇 번 실행해도 내용이 같다. EOF를 따옴표로 감싸면 안의 $변수를 바꾸지 않고 글자 그대로 쓴다.
자주 하는 오해"오류 없이 끝났다"는 멱등이라는 뜻이 아니다. 오류 없이 같은 줄을 두 번 추가할 수 있다. 두 번 실행하고 결과를 비교해서 확인한다.
내 환경과 비교실습에서 쓰는 kubectl apply -f가 멱등이다. 같은 YAML을 열 번 적용해도 결과는 하나다. desired state 방식이기 때문이다.
직접 확인 
f=$(mktemp)
for i in 1 2; do echo 'a=1' >> "$f"; done; cat "$f"   # 두 줄
for i in 1 2; do echo 'a=1' > "$f"; done; cat "$f"    # 한 줄
grep -qx 'a=1' "$f" || echo 'a=1' >> "$f"             # 없을 때만 추가

systemd unit: 프로그램을 서비스로

왜 알아야 하나서버 프로그램은 부팅할 때 시작하고, 죽으면 다시 시작해야 한다. 사람이 터미널에서 실행하면 이것을 보장할 수 없다. 리눅스에서는 systemd가 이 일을 한다.

  • systemd는 부팅 때 처음 실행되는 프로세스(PID 1)다. 다른 프로그램을 시작하고 지켜본다.
  • unit 파일은 "무엇을 어떻게 실행할지" 적은 설정 파일이다. 서비스는 이름.service다. 직접 만드는 파일은 보통 /etc/systemd/system/에 둔다.
  • [Unit]: 설명, 시작 순서(After=). [Service]: 실행 명령(ExecStart=), 실행 사용자(User=), 다시 시작 규칙(Restart=), 자원 한도(LimitNOFILE= 등). [Install]: 부팅 때 켤지(WantedBy=multi-user.target).
  • unit 파일을 고친 뒤에는 systemctl daemon-reload로 다시 읽게 한다.
  • 로그는 journald가 모은다. journalctl -u 이름으로 본다.
  • unit 파일의 자리는 둘이다. /usr/lib/systemd/system/: 패키지(apt)가 놓는다. 업그레이드하면 덮어쓴다. /etc/systemd/system/: 관리자가 놓는다. 이름이 같으면 /etc 쪽이 이긴다. 패키지의 unit 일부만 바꾸려면 systemctl edit 이름으로 덧붙이는 파일(drop-in)을 만든다.
  • systemctl enable은 링크 하나를 만든다. 예: /etc/systemd/system/multi-user.target.wants/docker.service. 부팅 중 multi-user.target을 준비할 때 이 링크의 서비스도 시작한다. preset: enabled는 배포판이 "설치하면 기본으로 켠다"고 정한 정책이다.
  • Restart=의 값: no(기본, 다시 시작하지 않음), on-failure(실패로 끝났을 때만), always(정상 종료여도). RestartSec=는 다시 시작하기 전에 기다리는 시간이다. 짧은 시간에 너무 자주 죽으면 systemd가 다시 시작을 멈춘다(StartLimitBurst=, StartLimitIntervalSec=).
자주 하는 오해systemd 서비스는 /etc/security/limits.conf를 읽지 않는다. 그 파일은 로그인한 사용자 세션에 쓰인다. 서비스의 한도는 unit 파일의 Limit…=로 정한다.
내 환경과 비교promet의 Docker도 보통 systemd 서비스다(docker.service). kind 클러스터는 그 위에서 돈다. 생각은 Kubernetes와 같다: "이 상태로 유지하라"를 적어 두면 관리자가 지킨다. 다른 점: systemd는 서버 한 대 안에서만 지킨다.
직접 확인 
ls -l /etc/systemd/system/multi-user.target.wants/   # enable이 만든 링크들
systemctl list-units --type=service | grep -i docker   # 정확한 서비스 이름
systemctl status docker            # 상태, PID, 최근 로그
systemctl cat docker               # unit 파일 내용
journalctl -u docker --since today

systemd 의존성: After=, Wants=, Requires=

왜 알아야 하나systemd는 부팅 때 많은 unit을 동시에 시작한다. "이것 다음에 시작하라"와 "이것도 같이 시작하라"를 적지 않으면, 네트워크나 디스크가 준비되기 전에 프로그램이 시작할 수 있다.

줄 (A의 unit에 씀)B를 시작시키나순서B가 실패하면
After=B아니다B가 시작되는 경우에만 B 다음영향 없음
Wants=B시작시킨다정하지 않는다 (동시에)A는 그대로 시작
Requires=B시작시킨다정하지 않는다After=B도 있으면 A는 시작하지 않는다. B를 멈추면 A도 멈춘다
  • 그래서 보통 둘을 같이 쓴다: After=B와 Wants=B(또는 Requires=B). 하나는 순서이고, 하나는 "같이 시작"이다.
  • target은 "이 단계에 도달함"을 뜻하는 이름표 unit이다. 실행하는 프로그램이 없다. 예: multi-user.target(보통 서버의 부팅 완료 지점).
  • network.target: 네트워크 설정을 시작했다는 뜻이다. 주소를 받았다는 뜻이 아니다. network-online.target: 네트워크를 실제로 쓸 수 있다는 뜻이다. 이 target은 어떤 unit이 Wants= 할 때만 부팅에 들어온다. 기다리는 만큼 부팅이 늦어지기 때문이다.
  • RequiresMountsFor=경로: 그 경로에 필요한 마운트 unit들에 Requires=와 After=를 건다. 디스크가 붙기 전에 서비스가 시작하지 않게 한다.
  • [Install]의 WantedBy=multi-user.target은 반대 방향이다. systemctl enable을 하면 multi-user.target이 이 서비스를 Wants= 하게 된다.
자주 하는 오해After=는 상대를 시작시키지 않는다. After=network-online.target만 쓰고 아무도 그 target을 Wants= 하지 않으면, 그 target은 부팅에 없다. 그러면 기다릴 것이 없어서 바로 시작한다.
내 Bitcoin 노드와 비교Bitcoin Core가 주는 unit 파일(contrib/init/bitcoind.service)에는 After=network-online.target과 Wants=network-online.target이 둘 다 있다. 그 위의 주석은 systemd의 NetworkTarget 문서를 가리킨다. 같은 파일에 Restart=on-failure, TimeoutStopSec=600, User=bitcoin도 있다. 줄마다 주석이 이유를 적어 둔, 읽어 볼 만한 unit 파일이다(2026-10-16 master에서 확인).

/etc/fstab: 부팅 때 디스크를 붙이는 목록

왜 알아야 하나mount 명령으로 붙인 디스크는 재부팅하면 떨어진다. 재부팅 뒤에도 같은 자리에 붙이려면 /etc/fstab에 적는다. 디스크가 붙지 않은 채로 프로그램이 시작하면, 데이터가 엉뚱한 디스크에 쌓인다.

  • 리눅스의 디렉터리 트리는 하나다. 디스크는 그 트리의 한 디렉터리에 붙는다(마운트). 그래서 경로가 디스크를 정한다.
  • mount 장치 디렉터리는 지금만 붙인다. /etc/fstab은 "부팅할 때마다 이렇게 붙여라"는 목록이다. 한 줄이 마운트 하나다.
  • 한 줄의 칸: 장치, 마운트 지점, 파일시스템, 옵션, dump(지금은 거의 0), 부팅 때 검사 순서(루트는 1, 다른 디스크는 2, 검사 안 함은 0).
  • 장치는 /dev/sdb1보다 UUID=…로 쓴다. 디스크 이름(sdb)은 인식 순서에 따라 바뀔 수 있다. UUID는 파일시스템에 붙은 번호라서 바뀌지 않는다.
  • systemd는 부팅 때 fstab의 줄마다 .mount unit을 만든다. 예: /data → data.mount. 그래서 서비스가 "이 마운트 다음에 시작"을 걸 수 있다(RequiresMountsFor=).
  • 루트 디스크(OS 디스크)와 데이터 디스크를 나누는 이유: OS 파일과 큰 데이터가 서로의 공간과 I/O를 뺏지 않게 한다. 데이터 디스크가 가득 차도 OS는 계속 돈다.
자주 하는 오해마운트가 안 된 마운트 지점도 그냥 디렉터리다. 쓰기가 실패하지 않는다. 그 안에 쓴 파일은 루트 디스크에 쌓인다. 루트 디스크가 가득 차면 로그도 못 쓰고 서버 전체가 멈출 수 있다. 나중에 디스크를 붙이면 그 파일들은 마운트 아래에 가려져서 보이지 않는다.

서비스 사용자와 최소 권한

왜 알아야 하나서버 프로그램은 언젠가 버그나 공격을 겪을 수 있다. 그때 프로그램은 자기를 실행한 사용자의 권한만큼 해를 끼칠 수 있다. 그래서 서비스마다 전용 사용자를 두고, 꼭 필요한 권한만 준다.

  • 노드에는 신원이 둘 있다. 리눅스 사용자는 커널이 보는 신원이다(UID). 프로세스가 어떤 파일을 읽고 쓸지 정한다. 노드 keypair는 네트워크가 보는 신원이다. 다른 노드가 이 노드를 누구로 아는지 정한다.
  • 둘은 키 파일에서 만난다. 키 파일도 리눅스 파일이다. 그래서 "어느 리눅스 사용자가 이 키를 읽을 수 있나"는 파일의 소유자와 권한이 정한다.
  • 프로세스는 자기를 실행한 사용자로 돈다. systemd 서비스는 User=와 Group=으로 정한다. 적지 않으면 root로 돈다.
  • 서비스 전용 사용자는 로그인할 일이 없다. 그래서 보통 시스템 사용자로 만들고 셸을 막는다(useradd --system --shell /usr/sbin/nologin 이름).
  • 설치 단계(디렉터리 만들기, unit 파일 쓰기)에는 root 권한이 필요하다. 실행 단계(프로세스가 도는 동안)에는 보통 필요 없다. 둘을 나눠서 생각한다.

커널 파라미터: sysctl

왜 알아야 하나커널에는 실행 중에 바꿀 수 있는 설정이 아주 많다. 기본값은 보통의 컴퓨터에 맞춰져 있다. 큰 서버 프로그램은 어떤 기본값이 작아서 문제를 겪을 수 있다.

  • sysctl 값은 /proc/sys/ 아래의 파일로 보인다. 이름의 점(.)은 경로의 /와 같다. net.ipv4.ip_forward = /proc/sys/net/ipv4/ip_forward.
  • 이름의 앞부분이 영역이다: net. 네트워크, vm. 메모리, fs. 파일, kernel. 그 밖.
  • sysctl -w 이름=값은 지금만 바꾼다. 재부팅하면 사라진다. 계속 쓰려면 /etc/sysctl.d/의 .conf 파일에 적고 sysctl --system으로 읽게 한다.
  • net. 값의 많은 수는 network namespace마다 따로 있다(전부는 아니다). 그래서 Pod 안의 값과 호스트의 값이 다를 수 있다.
  • 값을 바꾸기 전에 "왜 이 값인가"를 그 프로그램의 공식 문서에서 확인한다. 어디서 본 값을 이유 없이 붙이지 않는다.
  • 뜻의 예(값은 그 프로그램의 공식 문서에서 찾는다). net.core.rmem_max와 net.core.wmem_max: 프로그램이 소켓 하나에 요청할 수 있는 받기·보내기 버퍼의 최대 크기다. UDP 패킷이 몰릴 때 받기 버퍼가 작으면 넘친 패킷은 버려진다. vm.max_map_count: 프로세스 하나가 가질 수 있는 메모리 매핑 영역의 수다. 파일을 많이 mmap하는 프로그램은 이것이 모자랄 수 있다. fs.nr_open: 프로세스 하나가 열 수 있는 파일 수의 커널 상한이다.
  • sysctl -p 파일은 그 파일의 값을 지금 바로 적용한다. 설정 파일에 적고 이 명령을 실행하면, 재부팅 없이 바로 바뀌고 재부팅 뒤에도 남는다.

리소스 한도: ulimit과 LimitNOFILE

왜 알아야 하나프로그램이 "Too many open files" 오류로 멈출 수 있다. 메모리와 CPU가 남아 있어도 생긴다. 프로세스마다 "열 수 있는 개수"의 한도가 따로 있기 때문이다.

  • 리눅스는 프로세스마다 한도(rlimit)를 둔다. 예: 열린 파일 수(nofile), 프로세스 수(nproc), 잠근 메모리(memlock).
  • 리눅스에서는 소켓(네트워크 연결)도 파일로 센다. 연결이 많은 서버는 nofile을 많이 쓴다.
  • 한도는 두 개다. soft는 지금 적용되는 값이다. hard는 soft를 올릴 수 있는 최대값이다.
  • 정하는 곳: 셸은 ulimit, 로그인 세션은 /etc/security/limits.conf, systemd 서비스는 unit 파일의 LimitNOFILE= 등. 컨테이너는 컨테이너 런타임이 정한다.
  • nofile 한도는 커널 상한 fs.nr_open을 넘을 수 없다. 그래서 두 값은 함께 본다.
  • systemd에서 모든 서비스의 기본값은 /etc/systemd/system.conf의 [Manager] 아래 DefaultLimitNOFILE=다. 서비스 하나의 값은 그 unit의 [Service] 아래 LimitNOFILE=다. unit의 값이 기본값보다 우선한다.
자주 하는 오해ulimit과 cgroup은 다르다. cgroup은 프로세스 묶음 전체의 양(메모리 바이트, CPU 시간)을 제한한다. ulimit은 프로세스 하나가 가질 수 있는 개수를 제한한다.
내 환경과 비교bitcoind도 파일과 소켓을 많이 연다: 블록 파일, LevelDB 파일, 피어 연결. bitcoind는 시작할 때 이 한도를 확인한다. 한도가 작으면 연결 수(-maxconnections)를 스스로 줄이고 경고를 남긴다.

kubectl -n bitcoin-lab exec bitcoin-node-0 -- cat /proc/1/limits   # 컨테이너의 첫 프로세스

포트 번호: 구역과 범위 표기

왜 알아야 하나포트 번호에는 구역이 있다. 어떤 구역은 root만 쓸 수 있다. 어떤 구역은 커널이 나가는 연결에 자동으로 쓴다. 프로그램에 포트나 범위를 줄 때 구역과 표기법을 모르면 충돌이 나거나 개수를 틀린다.

  • 포트는 0–65535다. TCP와 UDP는 포트 공간이 따로다. 53/tcp와 53/udp는 다른 창구다. DNS는 둘 다 쓴다.
  • 0–1023(잘 알려진 포트): 리눅스에서는 root만 여기서 리슨할 수 있다. 예: 22(SSH), 80(HTTP), 443(HTTPS). root가 아닌 프로그램이 쓰려면 CAP_NET_BIND_SERVICE 권한이 필요하다. 그래서 일반 서비스는 보통 1024 이상을 쓴다.
  • 리눅스는 나가는 연결의 내 쪽 포트를 임시 범위에서 자동으로 고른다(net.ipv4.ip_local_port_range, 보통 32768–60999).
  • 포트를 여러 개 여는 프로그램은 "이 범위 안에서 골라 써라"는 설정을 받기도 한다. 범위 안의 빈 포트를 프로그램이 고른다.
  • 범위 표기는 두 가지다. 닫힌 구간 a–b, [a, b]: 양 끝을 포함한다. 개수 = b − a + 1. 반열린 구간 [a, b): a는 포함하고 b는 빠진다. 개수 = b − a. 프로그래밍 언어의 범위(Python의 range(a, b), Rust의 a..b)는 보통 반열린 구간이다.
자주 하는 오해"포트가 열려 있다"에는 두 뜻이 있다. 하나는 프로그램이 그 포트에서 듣고 있다는 뜻이다(ss로 본다). 다른 하나는 중간의 방화벽이 그 포트를 통과시킨다는 뜻이다. 둘은 따로 확인한다.
내 환경과 비교NodePort는 30000–32767(닫힌 구간, 2,768개)에서 고른다. 실습의 30333이 여기 있다. Signet의 38333과 38332는 1024 이상이라서 bitcoind는 root 없이 리슨한다. promet의 Caddy가 443에서 리슨하려면 root 권한이나 CAP_NET_BIND_SERVICE가 있어야 한다. 어느 쪽인지는 아래 명령으로 본다.

생각해 볼 질문서버 프로그램의 포트를 임시 포트 범위(32768–60999) 안에 두었다. 재부팅 직후에 이 프로그램이 늦게 시작하면 어떤 일이 생길 수 있을까?

왜 알아야 하나"Permission denied"는 가장 흔한 오류다. 원인은 항상 "어떤 사용자의 프로세스가, 누구 소유의 파일에, 어떤 동작을 했는가"이다.

du와 df는 왜 다른 값을 보이는가

왜 알아야 하나실습 A에서 "노드를 몇 개 더 둘 수 있는가"를 계산한다. 두 명령의 값이 다르면 어느 쪽을 믿을지 알아야 한다.

dudf

du -h는 모든 하위 디렉터리를 한 줄씩 보인다. 마지막 줄이 합계다. du -sh는 합계 한 줄만 보인다(-s = summary). 어느 디렉터리가 큰지 볼 때는 du -h --max-depth=1을 쓴다.

값이 다른 이유:

  • 지워졌지만 열려 있는 파일. 프로세스가 파일을 열고 있으면 삭제 후에도 공간이 남는다. du는 못 보고 df는 센다.
  • 예약 블록. ext4는 기본으로 약 5%를 root용으로 남긴다. df의 Used + Avail이 Size보다 작다.
  • 다른 파일시스템. du는 경로 안의 다른 마운트도 더한다. -x를 쓰면 막는다.
  • 권한. 읽을 수 없는 디렉터리는 du가 세지 못한다.
내 환경에서"공간이 얼마나 남았나"는 df로 본다. "노드 하나가 얼마나 쓰나"는 du로 본다. 2026-10-12 관찰: 루트 226G 중 약 156G 여유, 기존 노드 PVC bitcoin-data는 약 27G 사용. 노드 데이터는 kind 노드 안에 있으므로, Pod 안에서 du를 실행하면 노드 크기를 정확히 볼 수 있다.

메모리, 페이지 캐시, 스왑

왜 알아야 하나bitcoind 성능은 메모리와 디스크 사이에서 정해진다. "메모리가 부족하다"와 "캐시가 많다"를 구분하지 못하면 측정을 잘못 읽는다.

  • 커널은 빈 메모리를 놀리지 않는다. 디스크에서 읽은 내용을 메모리에 남긴다. 이것이 페이지 캐시다.
  • 페이지 캐시는 필요하면 즉시 비울 수 있다. 그래서 free의 available을 본다. free 열은 거의 의미가 없다.
  • 스왑은 메모리 내용을 디스크로 내보내는 공간이다. 스왑이 많이 쓰이면 느려진다.
  • 메모리 한도를 넘으면 커널의 OOM killer가 프로세스를 종료한다. 단, 그 전에 먼저 페이지 캐시를 버린다.
  • cgroup은 페이지 캐시도 그 cgroup의 메모리로 센다. 그래서 컨테이너의 메모리 사용량에는 캐시가 들어 있다.
  • 스왑 used가 크면 과거에 메모리 압박이 있었다는 흔적이다. 커널은 그 내용이 다시 필요할 때까지 스왑에 둔다.
자주 하는 오해같은 실험을 두 번 하면 두 번째가 빠를 수 있다. 데이터가 페이지 캐시에 남아 있기 때문이다. 이것을 "캐시 효과"라고 하고, 실험 기록에 남긴다.

캐시를 잃으면: refault와 thrashing

왜 알아야 하나메모리가 부족해도 프로세스는 바로 죽지 않는다. 커널은 먼저 page cache를 버린다. 그러면 프로그램은 오류 없이 느려지기만 한다. 그래서 이 문제는 숫자로만 찾을 수 있다.

  • cgroup은 page cache도 그 cgroup의 메모리 사용량으로 센다.
  • cgroup이 한도에 닿으면 커널은 먼저 캐시를 버린다(evict). 그래도 모자라면 OOM killer가 프로세스를 종료한다.
  • 버린 데이터를 다시 읽으면 커널은 refault로 센다. refault가 계속되는 상태가 thrashing이다.

cgroup: 자원을 세고 제한하기

왜 알아야 하나자원 실험(실습 E, F)은 전부 cgroup으로 한다. kubectl top, Docker 한도, Kubernetes limits는 모두 cgroup 값을 쓰거나 읽는다.

  • cgroup은 프로세스 묶음이다. 커널은 묶음마다 CPU, 메모리, I/O 사용량을 센다.
  • 묶음에 한도를 걸 수 있다. 예: memory.max, cpu.max.
  • cgroup은 트리다. 자식은 부모의 한도를 넘을 수 없다.
  • 내 서버는 cgroup v2를 쓴다. 파일은 /sys/fs/cgroup 아래에 있다.
  • cgroup namespace: 컨테이너 안의 /sys/fs/cgroup은 나무의 뿌리가 아니라 자기 가지다. 그래서 Pod 안에서 읽은 memory.max, cpu.stat은 그 컨테이너 자신의 값이다. 위쪽 층은 호스트에서 본다.
  • memory.events는 하위 cgroup의 이벤트까지 더한 값이다. 그 cgroup 자신만 보려면 memory.events.local을 본다(memory.events와 .local).

CPU limit의 실체: cpu.max와 throttling

왜 알아야 하나"CPU 한도가 느리게 했는가?"에는 추측하지 않고 숫자로 답할 수 있다. Kubernetes의 limits.cpu는 커널의 cpu.max 파일이 된다. 커널은 멈춘 횟수와 시간을 cpu.stat에 센다.

  • m은 밀리(1/1000)다. 1000m = 1코어, 250m = 0.25코어. 대문자 M은 메가(백만)다.
  • cpu.max의 형식은 <quota> <period>이고, 단위는 마이크로초(µs)다. 100000 100000은 "100ms마다 CPU 시간 100ms까지", 즉 1코어다. 500m이면 50000 100000이다.
  • 창 안에서 quota를 다 쓰면 커널은 다음 창까지 그 cgroup을 멈춘다. 이것이 throttling이다.
cpu.stat의 줄뜻계산
usage_usec지금까지 쓴 CPU 시간의 합÷ 걸린 시간 = 평균 사용 코어 수
nr_periods실행할 일이 있었던 창의 수—
nr_throttled그중 멈춘 창의 수÷ nr_periods = 멈춘 창의 비율
throttled_usec멈춘 시간의 합한도를 없애면 줄일 수 있는 최대 시간
내 환경에서2026-10-13에 bitcoin-node-1의 IBD 기록을 읽었다. limit 1000m → cpu.max = 100000 100000. 멈춘 창은 16,441 / 625,561(약 2.6%), 멈춘 시간은 약 625초(약 10분)였다. IBD는 약 4시간 53분이었으므로 CPU 한도는 주된 원인이 아니었다. 평균 사용은 약 7,922초 ÷ 17,570초 = 약 0.45코어였다. 즉 CPU는 시간의 절반 넘게 다른 것을 기다렸다.
자주 하는 오해throttling이 있다고 CPU가 원인인 것은 아니다. 비율과 시간을 계산한다. 평균 사용이 한도보다 훨씬 낮으면, CPU는 디스크나 네트워크를 기다린 것이다.

memory.events와 .local: 무엇을 세는가

왜 알아야 하나숫자를 비교하기 전에, 그 숫자가 무엇을 세는지 먼저 확인해야 한다. memory.events는 하위 cgroup의 이벤트까지 더한다. 그래서 부모의 값만 보고 "부모가 가득 찼다"고 말하면 틀릴 수 있다.

  • memory.events: 이 cgroup과 모든 하위 cgroup의 이벤트를 더한 값이다(계층 값).
  • memory.events.local: 이 cgroup 자신의 이벤트만 센다.
  • max: 사용량이 이 cgroup의 memory.max를 넘으려 한 횟수다. 이때마다 커널은 메모리를 회수한다. 먼저 page cache를 버린다.
  • 부모가 가득 차면 커널은 자식의 page cache도 회수한다. 자식의 한도에 여유가 있어도 그렇다. 이때 늘어나는 것은 부모의 max다. 자식의 max는 늘지 않는다.
내 환경에서실습 F 실행 2(상자 4GiB, 2026-10-14): 상자의 memory.events.local max는 21,206,152 → 23,813,701(+2,607,549)이 되었다. 같은 기간 node-1 컨테이너의 max는 0, peak는 1.44GiB였다. 그래도 refault는 969GB였다. 그래서 회수 압력은 상자 층에서 왔다. 주의: 이 증가분에는 상자를 4GiB로 줄인 순간의 회수(그때 memory.current 약 4.97GiB)와, 작업이 끝난 뒤의 대기 시간도 들어 있다.

아직 모르는 것. 실행 1(상자 8GiB)에서 컨테이너의 max는 113번뿐인데 refault는 412GB였다. Pod 층의 cgroup(한도 2Gi, pause 컨테이너 포함)이 먼저 가득 찼을 수 있다. 확인하지 않았다.

자주 하는 오해"부모의 max가 크다 = 부모가 가득 찼다"는 틀릴 수 있다. 하위 cgroup이 각자 자기 한도에 닿은 횟수도 부모의 값에 더해진다. 2026-10-13의 "상자가 2,400만 번 넘게 가득 찼다"도 이 계층 값이었다. 10-14에 .local로 다시 보니 약 83%가 상자 자신이었다. 결론은 유지되었지만, 이제 비교는 .local로 한다.

Kubernetes KUBERNETES

Kubernetes는 "명령을 실행하는 도구"가 아니다. "원하는 상태를 적어 두면 계속 맞추는 시스템"이다.

API 서버와 desired state

왜 알아야 하나Pod를 지워도 다시 생긴다. 이것은 오류가 아니다. Kubernetes의 기본 동작이다. 이 원리를 알면 대부분의 "이상한 동작"이 설명된다.

나YAML 작성
kubectl apply
요청 →
API 서버원하는 상태를 etcd에 저장
← 관찰
변경 →
컨트롤러, kubelet현재 상태와 비교
차이를 줄인다
  • desired state(원하는 상태): YAML의 spec. 예: "bitcoind Pod 1개".
  • current state(현재 상태): 실제로 있는 것. status에 기록된다.
  • 컨트롤러는 둘을 계속 비교한다. 다르면 고친다. 이 반복을 reconcile loop라고 한다.
  • 모든 구성 요소는 API 서버를 통해서만 대화한다. kubectl도 API 서버의 클라이언트일 뿐이다.
  • kubectl apply를 하면 API 서버가 내용을 etcd에 저장한다. 그 뒤로 내 파일을 고쳐도, 다시 apply하기 전에는 클러스터가 바뀌지 않는다. 그래서 지금 실제로 도는 설정의 정답은 클러스터 쪽(get -o yaml)이다.
자주 하는 오해Pod를 직접 고치거나 지우는 것은 임시 조치다. 바꾸고 싶으면 원하는 상태(Deployment의 YAML)를 바꾼다.
자주 하는 오해클러스터에서 읽은 YAML은 내 파일과 같지 않다. 내가 쓰지 않은 항목(기본값, status, metadata.uid)이 많다. API 서버가 채운 것이다. 비교할 때는 grep으로 필요한 줄만 본다.

직접 확인

YAML 구조와 들여쓰기

왜 알아야 하나YAML에서 들여쓰기는 구조 자체다. 공백 두 칸이 틀리면 값이 다른 부모에 붙는다. 오류가 안 나고 다르게 동작할 때도 있다.

  • YAML은 두 가지로만 되어 있다. 맵(키: 값)과 리스트(- 항목).
  • 같은 깊이에 있는 키는 같은 부모에 속한다. 깊이는 공백으로 정한다. 탭은 쓰지 않는다.
  • -는 "리스트의 새 항목"이다. 그 뒤의 키들은 그 항목에 속한다.
  • 모든 매니페스트는 4개의 최상위 키를 가진다: apiVersion, kind, metadata, spec.
  • ---는 문서 구분선이다. 파일 하나에 객체 여러 개를 넣을 때 쓴다. kubectl apply는 이 선으로 나누어 객체를 하나씩 보낸다.
  • - 다음 첫 글자가 그 목록 항목의 기준선이다. 같은 항목의 키는 이 기준선에 맞춘다. 하위 키는 2칸 더 들어간다.
apiVersion: apps/v1          # 어느 API 그룹, 버전
kind: Deployment             # 어떤 객체
metadata:                    # 이름표 (맵)
  name: bitcoin-signet
  namespace: bitcoin-lab
spec:                        # 원하는 상태
  replicas: 1
  template:                  # 만들 Pod의 모양
    spec:
      containers:            # 리스트
      - name: bitcoind       # 첫 번째 항목 시작
        image: …             # name과 같은 깊이 = 같은 항목
        args: ["-signet"]
자주 하는 오해image:가 - name:보다 두 칸 왼쪽에 있으면, image는 컨테이너 항목이 아니라 spec에 붙는다. 파일을 적용하기 전에 kubectl apply --dry-run=server -f 파일로 검사한다.

오류 경로 읽기. unknown field "spec.volumeClaimTemplates[0].name"에서 점(.)은 "안으로", [0]은 "목록의 첫 항목"이다. 기대한 경로는 …[0].metadata.name이었다. 즉 name이 한 단계 덜 들어가 있었다. API 서버는 종류마다 허용 키 목록(스키마)을 알고, 모르는 키는 거부한다(strict decoding).

직접 확인 
kubectl explain deployment.spec.template.spec.containers   # 어떤 키가 어디에 오는가
kubectl apply --dry-run=server -f bitcoin.yaml

Kubernetes namespace

왜 알아야 하나kubectl get pods에 내 Pod가 없으면, 보통 namespace를 빠뜨린 것이다.

  • namespace는 API 객체를 묶는 이름 공간이다. 폴더와 비슷하다.
  • 같은 namespace 안에서는 이름이 겹칠 수 없다. 다른 namespace에서는 겹쳐도 된다.
  • -n을 안 쓰면 default namespace를 본다.
  • namespace에 속하지 않는 객체도 있다. Namespace 자체, Node, PV, StorageClass는 클러스터 전체에 속한다. 그래서 kubectl get ns, kubectl get nodes에는 -n을 쓰지 않는다. 목록: kubectl api-resources --namespaced=false.
  • namespace만으로는 CPU, 메모리가 나뉘지 않는다. 한도는 limits나 ResourceQuota로 건다.
내 환경에서노드 객체는 전부 bitcoin-lab namespace에 있다. 매번 -n bitcoin-lab을 쓴다. 아니면 기본값을 바꾼다: kubectl config set-context --current --namespace=bitcoin-lab. 다른 namespace: kube-system(control plane, CoreDNS), local-path-storage(PVC 공간을 만드는 프로그램).

Service

왜 알아야 하나Pod IP는 바뀐다. 다른 Pod가 바뀌는 IP를 따라갈 수 없다. Service는 바뀌지 않는 이름과 주소를 준다.

  • Service는 라벨 선택자(selector)로 Pod를 고른다. 라벨이 맞는 Pod가 대상이다.
  • 기본 종류(ClusterIP)는 가상 IP 하나를 준다. 그 IP로 오는 연결을 대상 Pod 중 하나에 나눠 보낸다.
  • 이 가상 IP를 가진 인터페이스는 없다. kube-proxy가 만든 커널 규칙(iptables 또는 nftables)이 받는 주소를 Pod IP로 바꿔 쓴다.
  • 이름으로도 접속한다: 서비스이름.namespace.svc.cluster.local.

headless Service

왜 알아야 하나노드끼리 연결할 때(실습 D), 각 노드는 "아무 노드"가 아니라 "특정 노드"에 연결해야 한다. headless Service가 Pod마다 고정 DNS 이름을 준다.

  • headless Service는 clusterIP: None인 Service다. 가상 IP가 없고, 나눠 보내지도 않는다.
  • 대신 DNS가 Pod IP를 직접 돌려준다.
  • StatefulSet과 같이 쓰면 Pod마다 이름이 생긴다: bitcoin-node-0.bitcoin-node.bitcoin-lab.svc.cluster.local. 형식은 <Pod 이름>.<Service 이름>이다.
  • Pod가 다시 생겨서 IP가 바뀌어도 이 이름은 같다.
  • 가상 IP가 없으므로 kube-proxy는 이 Service에 포트 규칙을 만들지 않는다. 그래서 밖에서 들어오는 문으로는 쓸 수 없다. 밖으로 열려면 NodePort Service를 따로 만든다.
자주 하는 오해headless에도 DNS가 있다. 없는 것은 가상 IP다. 그리고 clusterIP에 127.0.0.1을 쓰면 거부된다. 127.0.0.1은 각 Pod 자신을 가리키고, Service IP는 10.96.0.0/16에서 자동으로 받거나(일반) None(headless)이어야 하기 때문이다.
내 환경에서bitcoind에 -addnode=bitcoin-node-0.bitcoin-node:38333처럼 쓴다. 같은 namespace 안에서는 뒷부분을 줄여도 된다. 2026-10-12 관찰: 연결된 주소가 10.244.0.11(Pod 범위)였다. Service 범위(10.96)가 아니다. 가상 IP 없이 Pod에 직접 연결한다는 증거다. 열린 질문: 2026-10-14 kubectl get svc에서 bitcoin-node가 ClusterIP 10.96.23.209로 보였다. 설계는 headless였다. 원인은 아직 확인하지 않았다. 확인: kubectl -n bitcoin-lab get svc bitcoin-node -o yaml | grep clusterIP.

NodePort Service와 externalTrafficPolicy

왜 알아야 하나Pod IP는 Pod가 다시 생길 때마다 바뀐다. 그래서 바깥 규칙에 Pod IP를 쓸 수 없다. NodePort는 Kubernetes 노드(kind 상자)에 바뀌지 않는 문을 만든다. 그 뒤의 Pod IP는 Kubernetes가 따라간다.

  • NodePort는 Service 종류의 하나다. 모든 Kubernetes 노드의 같은 포트에서 받는다. 포트는 30000–32767 중 하나다.
  • 실제 규칙은 kube-proxy가 노드의 iptables에 DNAT로 만든다. 받는 주소를 대상 Pod IP:targetPort로 바꾼다.
  • kubectl get svc의 38333:30333/TCP는 "노드 포트 30333으로 받아서 Service 포트 38333으로"라는 뜻이다.
  • selector로 대상 Pod를 고른다. StatefulSet은 Pod마다 statefulset.kubernetes.io/pod-name 라벨을 자동으로 붙인다. 이 라벨로 Pod 하나만 고를 수 있다.
  • headless Service는 포트 규칙을 만들지 않는다. 그래서 밖으로 여는 문은 NodePort를 따로 만든다.

  • Kubernetes는 자기 밖의 한도를 모른다. kind 안의 kubelet은 노드 메모리를 호스트 기준(약 14Gi)으로 보고한다. 그래서 scheduler는 kind 상자보다 큰 Pod 묶음을 배치할 수 있다.
내 환경에서bitcoind의 -dbcache는 메모리 limits보다 충분히 작아야 한다. 아니면 동기화 중에 OOMKilled가 될 수 있다. kind 노드의 Docker 한도가 있다면, 모든 Pod의 합이 그 안에 있어야 한다. 2026-10-13 측정: Pod 3개의 limit 합은 6Gi였고 kind 상자는 4GiB였다. node-1의 실제 peak는 약 1.55GB였다.

QoS 등급과 OOM 점수

왜 알아야 하나메모리가 부족하면 커널은 프로세스 하나를 골라 종료한다. 누구를 먼저 고를지는 점수로 정한다. Kubernetes는 requests와 limits로 이 점수를 정한다.

등급조건점수 (oom_score_adj)
Guaranteed모든 컨테이너에서 CPU와 메모리의 request = limit−997 (거의 마지막)
Burstablerequest가 있지만 limit과 다르다1000 − 1000 × request ÷ 노드 메모리. request가 작을수록 높다
BestEffortrequest와 limit이 모두 없다1000 (가장 먼저)
  • request는 "이만큼 예약해 주세요"다. scheduler는 request의 합으로 배치를 계산한다.
  • request보다 더 쓰는 부분은 예약이 아니다. 남는 공간에서 빌려 쓰는 것이다. 그래서 메모리가 부족하면 많이 빌린 Pod부터 줄인다.
  • 정직한 request는 작은 값이 아니다. 실제 사용량에 가까운 값이다.
내 환경에서bitcoind Pod는 request 512Mi, limit 2Gi이므로 Burstable이다. 계산: 1000 − 1000 × 512Mi ÷ 약 14Gi ≈ 965. 호스트 설정 표(2026-10-13)에는 967로 적혀 있다. 측정한 peak는 약 1.55GB로, request의 약 3배다. request를 측정값(예: 1536Mi)에 맞추면 점수가 내려간다. 단, 바꾸면 Pod가 다시 만들어지므로 실습 F가 끝난 뒤에 바꾼다.
자주 하는 오해QoS 등급은 Kubernetes 안의 규칙이다. 호스트 서비스(crawler, collector, 배치)는 Kubernetes 밖에 있다. 그 점수는 Docker나 systemd 설정으로 정한다.

kind 클러스터의 구조

왜 알아야 하나kind는 실제 서버 클러스터와 다르게 동작하는 부분이 있다. 측정 결과에 kind 때문인 부분이 섞일 수 있다.

  • kind는 "Kubernetes in Docker"다. Kubernetes 노드 하나 = Docker 컨테이너 하나다.
  • 그 컨테이너 안에서 kubelet, containerd, API 서버가 실행된다. Pod 컨테이너는 그 안의 containerd가 만든다.
  • 그래서 호스트의 docker ps에는 Pod가 안 보인다. kind 노드만 보인다.
  • 클러스터 네트워크는 Docker 네트워크 안에 있다. 외부에서 Pod로 들어오려면 별도 포트 매핑이 필요하다.
  • kind의 포트 매핑(extraPortMappings)은 클러스터를 만들 때만 넣을 수 있다. 이미 만든 클러스터에서는 호스트의 DNAT 규칙으로 kind 상자의 NodePort에 보낸다(포트 포워딩 = DNAT).
  • 잠시 끌 때의 순서: 먼저 Pod를 끈다(kubectl -n bitcoin-lab scale statefulset bitcoin-node --replicas=0, Deployment도 같게). bitcoind가 SIGTERM을 받고 정상 종료한다. 그다음 kind 상자를 멈춘다(docker stop -t 60 bitcoin-lab-control-plane). -t 60은 "60초 기다린 뒤에도 안 끝나면 강제 종료"다. 기본은 10초다. 다시 켤 때는 반대 순서다. kind delete cluster와 docker rm은 블록 데이터까지 지운다(2026-10-15).
내 환경에서노드는 bitcoin-lab-control-plane 하나다. 모든 Pod가 이 컨테이너 안에서 같은 SSD, 같은 CPU를 나눠 쓴다. "노드 여러 개"는 Kubernetes 노드가 아니라 bitcoind Pod 여러 개다. "노드"의 두 뜻을 본다. kind 노드 컨테이너에는 Docker 한도가 있다. 2026-10-13 확인: 메모리 4GiB(같은 날 8GiB로 늘림), CPU 3.5코어. 바꾸는 명령: docker update --memory 8g --memory-swap 8g bitcoin-lab-control-plane. 컨테이너는 재시작하지 않는다. 2026-10-14 확인: kind 상자는 Docker 네트워크에서 172.18.0.2다. promet은 이 Docker 네트워크의 브리지에 붙어 있어서 이 주소에 바로 닿는다. 실습 F 뒤 메모리는 다시 8GiB다.
자주 하는 오해kind 안의 kubelet은 이 Docker 한도를 모른다. 그래서 kubectl describe node의 메모리는 상자 크기가 아니라 호스트 메모리다. 2026-10-13의 IBD가 느렸던 원인이 이 차이였다(refault).

docker exec bitcoin-lab-control-plane crictl ps    # kind 노드 안의 컨테이너 목록

kubectl exec 명령의 구조

왜 알아야 하나명령의 앞부분은 호스트의 kubectl이 읽는다. -- 뒷부분은 컨테이너 안의 프로그램이 읽는다. 이 경계를 모르면 경로를 kubectl에게 주거나, 호스트 경로를 컨테이너에서 찾는 실수를 한다.

실제로 본 오류원인
you must specify at least one command for the container-- 뒤에 실행할 명령이 없다

네트워크 NETWORK

노드는 네트워크 프로그램이다. 피어 연결 수와 전송량은 성능 측정의 기본 값이다.

IP 주소, 포트, TCP 연결

왜 알아야 하나"연결이 안 된다"의 원인은 넷 중 하나다. 주소가 틀리다. 포트가 틀리다. 듣는 프로그램이 없다. 중간에서 막는다.

  • IP 주소는 장치(정확히는 네트워크 인터페이스)를 찾는다.
  • 포트는 그 장치 안의 프로그램을 찾는다. 0–65535 번호다.
  • TCP 연결은 네 값으로 구분한다: 내 IP, 내 포트, 상대 IP, 상대 포트.
  • 서버는 한 포트에서 listen(대기)한다. 클라이언트가 connect(접속)한다.
  • 포트는 IP마다 따로 있다. 같은 IP에서는 한 포트를 한 프로그램만 기다릴 수 있다. 두 번째 프로그램은 Address already in use 오류를 받는다. IP가 다르면 같은 번호를 써도 된다. 그래서 StatefulSet의 Pod 2개가 모두 38333에서 기다린다.
  • 바깥 포트와 안쪽 포트의 번호는 달라도 된다. 예: kind 상자의 30333 → Pod의 38333(NodePort).

IP의 본질. IP 주소는 "패킷을 어디로 보낼지"를 정하는 번호다. 패킷마다 보내는 주소와 받는 주소가 있다. 라우터와 커널은 받는 주소만 보고 다음 방향을 정한다. IP는 기계가 아니라 네트워크 인터페이스에 붙는다. IP는 기계까지, 포트는 그 안의 프로그램까지 데려간다.

범위 (CIDR)내 환경에서의 뜻
127.0.0.0/8loopback. 자기 자신. Pod 안에서는 그 Pod 자신이다
10.244.0.0/16Pod IP 범위 (kind 기본값). 예: node-1 = 10.244.0.11
10.96.0.0/16Service 가상 IP 범위. API 서버가 자동으로 준다

네트워크 인터페이스: 랜카드, lo, veth

왜 알아야 하나IP는 기계가 아니라 인터페이스에 붙는다. Pod IP가 왜 생기고 왜 사라지는지 알려면 인터페이스를 알아야 한다.

네트워크 인터페이스는 커널 안의 "패킷 출입구" 객체다. 출입구 뒤에 무엇이 있는지는 종류마다 다르다.

종류뒤에 있는 것예
물리실제 랜카드. 패킷이 케이블로 나간다eno1, enp3s0 (이름은 장치마다 다르다)
lo없음. 보낸 패킷이 바로 자기에게 돌아온다127.0.0.1
veth가상 케이블. 항상 양 끝 한 쌍으로 생긴다Pod의 eth0과 노드 쪽 veth…
bridge가상 스위치. 여러 veth를 묶는다docker0, br-… (kind 네트워크)
  • Pod를 만들 때 veth 한 쌍이 생긴다. 한쪽 끝은 Pod의 net namespace로 들어가서 eth0이 된다.
  • Pod는 자기가 랜카드를 가졌다고 생각한다. 실제로는 가상 케이블의 한쪽 끝이다.
  • Pod가 지워지면 veth도, 그 IP도 사라진다.
자주 하는 오해인터페이스가 곧 랜카드는 아니다. 호스트의 인터페이스 대부분은 커널이 만든 가상 장치다.

Pod IP는 어디서 오고, 왜 바뀌는가

왜 알아야 하나Pod IP는 Pod를 다시 만들 때 바뀔 수 있다. 그래서 bitcoind 설정에 IP 대신 이름을 쓴다. 이 흐름을 알면 "왜 이름이 필요한가"를 설명할 수 있다.

  1. scheduler가 Pod를 둘 노드를 정한다.
  2. 그 노드의 kubelet이 containerd에 컨테이너 생성을 요청한다.
  3. containerd가 CNI 플러그인을 부른다. CNI는 netlink(커널 네트워크 설정용 소켓)로 veth 쌍을 만든다.
  4. CNI의 IPAM(IP 주소 관리)이 노드의 Pod 범위에서 빈 주소 하나를 고른다.
  5. kubelet이 그 IP를 API 서버에 보고한다 (status.podIP).
  6. CoreDNS가 API 서버를 보고 DNS 응답을 바꾼다. bitcoind는 이름만 알면 된다.
자주 하는 오해같은 IP가 다시 나올 수도 있다. 하지만 보장되지 않는다. 보장이 없으므로 이름이 필요하다.
내 환경에서kind의 기본 CNI는 kindnet이다. Pod 범위는 10.244.0.0/16이다. 2026-10-12 관찰: node-0에서 bitcoin-node-1.bitcoin-node가 10.244.0.11로 바뀌었다.

리슨 주소: 127.0.0.1과 0.0.0.0

왜 알아야 하나프로그램이 "실행 중"이어도 다른 Pod에서 접속이 안 될 수 있다. 어느 주소에서 듣는지가 접근 범위를 정한다.

  • 127.0.0.1(localhost)에서 들으면 같은 net namespace 안에서만 접속할 수 있다. Pod에서는 같은 Pod 안이다.
  • 0.0.0.0에서 들으면 모든 인터페이스에서 접속할 수 있다.
  • bitcoind의 RPC는 기본으로 localhost에서만 듣는다. 이것은 안전을 위한 기본값이다.
  • 127.0.0.1은 network namespace마다 따로 있다. promet의 127.0.0.1과 Pod의 127.0.0.1은 다른 곳이다. 그래서 promet에서 bitcoin-cli를 실행해도 Pod 안의 RPC에 닿지 않는다.
내 환경에서kubectl exec로 Pod 안에서 bitcoin-cli를 실행하면 localhost이므로 바로 된다. 다른 Pod에서 RPC로 접속하려면 -rpcbind와 -rpcallowip를 같이 바꿔야 한다. 필요할 때만 바꾼다. 다른 방법은 kubectl port-forward다. API 서버를 거쳐 promet의 포트를 Pod 안의 포트에 잇는다. Kubernetes 권한이 있어야 쓸 수 있으므로, RPC를 Pod 밖에 열지 않아도 된다.

NAT와 포트 포워딩

왜 알아야 하나내 노드는 밖으로 연결(outbound)할 수 있다. 하지만 밖에서 내 노드로 연결(inbound)은 보통 안 된다. NAT가 몇 겹 있기 때문이다.

  • 집 공유기는 사설 IP(예: 192.168.x.x)를 공인 IP 하나로 바꾼다. 이것이 NAT다.
  • 안에서 나간 연결의 응답은 돌아온다. 밖에서 먼저 온 연결은 어디로 보낼지 모른다. 그래서 막힌다.
  • 포트 포워딩은 "이 포트로 오면 이 내부 주소로 보낸다"는 규칙이다(DNAT).
  • NAT 층은 직접 만든 것이 아니다. 각 층을 설치할 때 하나씩 따라온다: 공유기(집 인터넷), Docker(컨테이너에 172.18.x를 준다), Pod 네트워크(10.244.x, kind의 kindnet).
  • CGNAT: 통신사가 여러 집을 공인 IP 하나 뒤에 묶는 방식이다. 이 경우 공유기에 포트 포워딩을 해도 통신사 장비에서 막힌다. 판별: 공유기 관리 페이지의 WAN IP와 curl -4 ifconfig.me 값을 비교한다. 같으면 공인 IP를 직접 받는다. WAN IP가 100.64.x, 10.x, 172.16–31.x, 192.168.x이면 CGNAT 또는 이중 NAT다.
내 환경에서밖에서 Pod까지 가려면 NAT가 여러 번 있다. 공유기 → 호스트 → Docker 네트워크(kind 노드) → Pod 네트워크. 2026-10-14 확인: 집 인터넷은 SK 유선이고, 공유기 WAN IP와 curl -4 ifconfig.me 값이 같았다. 그래서 CGNAT도 이중 NAT도 없다. 공유기에는 이미 443 → promet:443(Caddy) 규칙이 있다. 같은 방법으로 38333을 연다(포트 포워딩 = DNAT).
자주 하는 오해"NAT를 너무 많이 만들었다"가 아니다. 공유기 NAT는 어느 집에나 있다. Docker 층은 kind 같은 실습 환경에만 있다. 실제 서버에 Kubernetes를 설치하면 이 층이 없다. 외부 연결을 받는 Pod는 hostNetwork나 hostPort로 Pod 층도 건너뛸 수 있다.
직접 확인 
curl -4 -s ifconfig.me; echo      # 밖에서 본 내 공인 IP
ip route | grep default           # via 뒤 = 공유기 관리 페이지 주소. 그곳의 WAN IP와 비교

연결의 방향과 conntrack

왜 알아야 하나내 노드는 밖으로 연결할 수 있다. 하지만 밖에서는 내 노드로 연결할 수 없다. 두 방향의 차이는 커널의 conntrack 표에서 온다. 이것을 알면 "왜 나가는 것만 되는가"를 설명할 수 있다.

  • 연결의 방향은 누가 먼저 SYN을 보냈는가로 정한다. SYN은 TCP 연결을 시작하는 첫 패킷이다.
  • 연결이 만들어진 뒤에는 양쪽 모두 데이터를 보낸다. 그래서 outbound 피어와도 블록을 주고받는다.
  • 안에서 나가는 패킷은 경계에서 보낸 주소가 바뀐다(SNAT, MASQUERADE). 이때 커널은 이 연결을 conntrack 표에 적는다: "이 주소와 포트로 오는 응답은 안쪽의 누구에게".
  • 응답이 오면 커널은 표를 보고 주소를 되돌린다. 그래서 outbound는 규칙 없이 된다.
  • 밖에서 먼저 온 SYN은 표에 기록이 없다. 커널은 이 패킷을 누구에게 줄지 모른다. 그래서 규칙(DNAT, 포트 포워딩)을 미리 만들어야 한다.

경비원에게 미리 적은 상시 지시: "38333으로 오는 손님은 내 방으로"포트 포워딩 (DNAT 규칙)

자주 하는 오해"inbound가 없으면 제대로 된 풀 노드가 아니다"는 틀리다. 노드는 모든 블록을 직접 검증한다. 빠진 것은 다른 노드가 먼저 연결해 올 자리다. 그래서 새 노드의 IBD를 돕지 못한다.

포트 포워딩 = DNAT: 경계마다 규칙 하나

왜 알아야 하나inbound를 열려면 경계마다 "이 포트로 오면 안쪽의 이 주소로"라는 규칙이 하나씩 필요하다. 하나라도 빠지면 연결은 그 경계에서 끝난다.

  • DNAT(Destination NAT)는 받는 주소(목적지)만 바꾼다. 보낸 주소는 바꾸지 않는다. 그래서 bitcoind는 피어의 진짜 주소를 본다.
  • 포트 포워딩은 DNAT 규칙의 다른 이름이다. 공유기 관리 페이지의 표도 DNAT 규칙이다.
  • 포트는 IP마다 따로 있다. 그래서 공인 IP의 38333은 한 곳으로만 보낼 수 있다. 다른 노드도 밖에 열려면 다른 바깥 포트를 쓴다.
  • 바깥 포트와 안쪽 포트의 번호는 달라도 된다. 예: kind 상자의 30333 → Pod의 38333. 공인 IP의 바깥 포트를 바꾸면 -externalip=주소:포트로 그 포트를 광고한다.
  • promet의 규칙은 2개다. (1) nat 표의 PREROUTING: promet LAN IP:38333으로 온 패킷의 받는 주소를 172.18.0.2:30333으로 바꾼다. (2) DOCKER-USER: 172.18.0.2:30333으로 가는 패킷을 허용한다. Docker는 자기가 publish하지 않은 포트로 가는 패킷을 막을 수 있기 때문이다.
  • iptables 규칙은 재부팅하면 사라진다. 계속 쓰려면 따로 저장한다(I-4b).
내 환경에서2026-10-14 상태: Pod(node-0은 이미 -listen=1) ✓, kind 상자(NodePort 30333) ✓. 남은 일: I-4 promet DNAT과 DOCKER-USER 허용 → I-4b 재부팅 뒤에도 유지 → I-5 공유기 38333 → promet:38333 → I-6 -externalip → I-7 외부 inbound 피어 확인. promet → kind 상자 구간은 kind의 extraPortMappings 대신 호스트 DNAT로 연다. extraPortMappings는 클러스터를 만들 때만 넣을 수 있어서, 클러스터를 다시 만들어야 하기 때문이다.
자주 하는 오해promet의 DNAT 규칙에서 받는 주소(-d promet LAN IP)를 빼면 안 된다. 빼면 규칙이 우리 노드의 outbound(외부 피어의 38333으로 가는 패킷)까지 잡아서 kind 상자로 되돌린다. 그리고 PREROUTING은 밖에서 들어오는 패킷만 본다. promet 자신이 보낸 패킷은 OUTPUT 체인을 지나므로, 시험은 집 안의 다른 기기에서 한다.
자주 하는 오해"기본 포트가 아니면 다른 노드가 연결하지 않는다"는 예전 버전의 동작이다. 지금의 Bitcoin Core는 다른 포트에도 연결한다. 피하는 것은 22(ssh)처럼 보통 인증이 필요한 서비스의 포트(bad port)뿐이다. 그래도 38333을 쓰는 이유는 DNS seed다. DNS 응답에는 포트가 없어서, bitcoind는 seed에서 받은 주소에 기본 포트를 붙인다(src/net.cpp). 다른 포트로 열면 seed로는 내 노드를 알릴 수 없다.
직접 확인 
sudo iptables -t nat -S PREROUTING          # DNAT 규칙 보기
sudo iptables -S DOCKER-USER                # Docker보다 먼저 보는 허용 규칙
sudo iptables -t nat -L PREROUTING -n -v    # 규칙마다 맞은 패킷 수

  • "리버스"인 이유: 보통의 프록시(회사 인터넷 프록시)는 손님 쪽을 대신해서 밖으로 나간다. 리버스 프록시는 반대로 서버 쪽을 대신해서 손님을 받는다.
  • HTTP는 진짜 손님 주소를 X-Forwarded-For 헤더에 적어서 넘긴다. 비트코인 P2P에는 이런 헤더가 없다.
  • 프록시를 쓰면 bitcoind는 모든 inbound 피어를 같은 주소로 본다. 그러면 두 가지가 망가진다. (1) inbound 자리가 차면 bitcoind는 피어 하나를 내보낸다. 이때 네트워크 그룹(IPv4는 /16)을 보고 다양성을 지킨다. 주소가 모두 같으면 이 보호가 없어진다. (2) 나쁜 피어 하나를 차단하면 모든 inbound가 같이 막힌다.
내 환경에서promet 호스트의 Caddy는 443에서 기다린다. 공유기에는 443 → promet:443 규칙이 있다. 그래서 443은 38333 대신 쓸 수 없다. 포트 하나는 한 곳으로만 보낼 수 있기 때문이다. 38333은 DNAT로 연다(포트 포워딩 = DNAT).

Tailscale: 문을 열지 않고 집에 들어가기

왜 알아야 하나SSH(22)와 RPC(38332)는 주인만 쓰는 문이다. 이 문을 포트 포워딩으로 열면 전 세계의 누구나 두드릴 수 있다. Tailscale은 공유기에 문을 열지 않고 집 밖에서 promet에 들어가게 한다.

  • Tailscale의 두 기기는 모두 outbound로 연결을 시작한다. outbound는 NAT를 저절로 지난다(conntrack).
  • 두 기기가 동시에 서로에게 패킷을 보낸다. 그러면 양쪽 공유기의 장부에 기록이 생기고, 상대의 패킷이 "응답"처럼 들어온다. 이 기법을 NAT hole punching이라고 한다.
  • 그래도 안 되면 Tailscale의 중계 서버(DERP)를 거친다. 느리지만 연결은 된다.
  • 내 tailnet(계정)에 등록된 기기만 들어온다. 그래서 공유기에 22번을 여는 것보다 안전하다.

HTTPS 443웹 손님포트 포워딩 → Caddy

Signet

왜 알아야 하나Signet에서 얻은 측정값을 메인넷에 그대로 쓰면 안 된다. 차이를 알아야 결과를 바르게 말할 수 있다.

  • Signet은 테스트 네트워크다. 코인에 가치가 없다.
  • 블록은 정해진 서명자만 만들 수 있다. 그래서 testnet보다 블록 간격이 안정적이다.
  • 체인이 메인넷보다 훨씬 작다. 동기화가 빠르다.
  • 프로토콜과 코드 경로는 메인넷과 거의 같다. 그래서 내부 동작을 배우기에 좋다.
자주 하는 오해Signet 블록은 트랜잭션이 적다. 검증 부하와 UTXO 크기가 메인넷과 다르다. "Signet에서 X분"은 "메인넷에서 X분"을 뜻하지 않는다.

-listen과 피어 연결

왜 알아야 하나노드끼리 연결하려면(실습 D) 한쪽은 들어오는 연결을 받아야 한다. -listen이 이것을 정한다.

  • outbound: 내 노드가 먼저 연결한다. 기본으로 여러 개를 자동으로 만든다.
  • inbound: 다른 노드가 내 노드에 연결한다. 내 노드가 P2P 포트에서 listen해야 받는다.
  • -listen=1: P2P 포트(Signet 38333)에서 들어오는 연결을 받는다. 기본값은 켜짐이다. 단 -connect나 -proxy를 쓰면 기본값이 꺼짐으로 바뀐다.
  • -addnode=주소: 이 피어에 계속 연결을 시도한다. 다른 피어도 쓴다.
  • -connect=주소: 이 피어에만 연결한다. 자동 연결을 끈다.
  • -externalip=주소: NAT 뒤의 노드는 자기 공인 주소를 모른다. 이 값을 주면 그 주소를 다른 노드에게 광고한다(addr 메시지). 광고해야 다른 노드가 나를 찾는다. 이 값을 주면 자동 탐지(-discover)는 꺼진다. 바깥 포트가 다르면 주소:포트로 쓴다. 확인: getnetworkinfo의 localaddresses.
  • -listen은 개수가 아니라 켜기/끄기(1/0)다. 연결 수는 -maxconnections가 정한다.
  • bitcoind는 피어를 보통 DNS seed(공개 주소 목록)에서 찾는다. 그래서 옆의 내 노드는 모른다. -addnode로 알려 준다.
  • 자기 자신에게 연결하면 bitcoind가 nonce(무작위 번호)를 비교해서 알아채고 끊는다.

왜 알아야 하나bitcoin-cli가 "Could not locate RPC credentials" 오류를 낼 때가 있다. 원인은 비밀번호가 아니라 쿠키 파일의 위치와 권한이다.

  • bitcoin-cli는 bitcoind에 HTTP로 JSON-RPC 요청을 보낸다. 모든 요청에는 인증이 필요하다.
  • 요청의 실제 모양: POST http://127.0.0.1:38332/, 본문 {"method": "getpeerinfo", "params": []}. bitcoind가 함수를 실행하고 결과를 JSON으로 돌려준다.
  • 인증이 필요한 이유: RPC로 노드를 끄고(stop), 지갑의 돈을 보내고, 피어를 차단할 수 있다.
  • 설정에 비밀번호가 없으면 bitcoind는 시작할 때 .cookie 파일을 만든다. 내용은 __cookie__:무작위값이다.
  • bitcoin-cli는 같은 데이터 디렉터리에서 이 파일을 읽어 인증한다.
  • 쿠키는 재시작할 때마다 바뀐다. bitcoind가 정상 종료하면 지워진다.
  • 결과: 파일을 읽을 수 있는 사용자 = RPC를 쓸 수 있는 사용자. 인증이 파일 권한으로 바뀐다.

pruned 노드

왜 알아야 하나디스크가 작으면 pruning이 답이 될 수 있다. 하지만 잃는 기능도 있다. 노드 여러 개를 둘 때의 선택지다.

  • pruned 노드도 모든 블록을 받아 모두 검증한다. 검증 수준은 풀 노드와 같다.
  • 검증 후 오래된 blk*.dat, rev*.dat를 지운다. 최근 블록과 UTXO 집합만 남긴다.
  • -prune=N: 블록 파일을 약 N MiB로 유지한다. 최소값은 550이다.
  • 잃는 것: 오래된 블록을 다른 노드에 줄 수 없다. -txindex를 쓸 수 없다. 오래된 지갑 재검색이 안 된다.
내 환경에서Signet은 작아서 지금은 pruning이 꼭 필요하지 않다. 다만 노드끼리 동기화하는 실험에서는 주의한다. pruned 노드는 처음부터 동기화하는 피어에게 오래된 블록을 줄 수 없다.

UTXO 집합과 dbcache

왜 알아야 하나IBD 속도에 가장 큰 영향을 주는 설정이다. 실습 F의 첫 번째 실험 변수가 될 수 있다.

  • UTXO는 아직 쓰지 않은 출력이다. 새 트랜잭션은 UTXO를 쓰고 새 UTXO를 만든다.
  • 블록을 검증할 때마다 UTXO를 찾고, 지우고, 추가한다. 이것이 작은 랜덤 I/O를 만든다.
  • -dbcache=N(MiB)은 UTXO를 메모리에 둘 공간이다. 크면 디스크에 덜 간다.
  • 캐시가 차면 디스크(chainstate)에 한 번에 쓴다. 이것을 flush라고 한다. 이때 I/O가 몰린다.
  • dbcache에 없는 UTXO는 chainstate/의 LevelDB 파일에서 읽는다. 그 파일이 page cache에 있으면 빠르고, 버려졌으면 디스크까지 간다.
  • 코드 경로: ConnectBlock(src/validation.cpp)이 입력 코인을 찾는다 → CCoinsViewCache::FetchCoin(src/coins.cpp, 크기 = dbcache) → 없으면 CCoinsViewDB(src/txdb.cpp) → LevelDB 읽기 → page cache → 디스크.
  • 정상 종료 신호(SIGTERM)를 받으면 bitcoind는 dbcache에 남은 변경을 chainstate에 쓰고 끝난다. 강제 종료(SIGKILL)되면 이 쓰기를 못 한다. 그러면 다음 시작 때 마지막 flush 이후의 블록을 다시 처리한다. Bitcoin Core의 unit 파일이 TimeoutStopSec=600으로 끝날 시간을 넉넉히 주는 것도 이 때문으로 보인다(추론).
자주 하는 오해dbcache를 크게 하면 항상 빠른 것은 아니다. 컨테이너 메모리 limits를 넘으면 종료된다. 페이지 캐시와도 메모리를 나눈다. 측정으로 확인한다.
내 환경에서노드는 -dbcache=512다. 2026-10-13 조사에서 IBD 동안 약 1.89TB를 다시 읽었다. 다시 읽은 대상으로 가장 유력한 것은 chainstate/의 LevelDB 파일이다(추정). 실습 F의 -reindex-chainstate가 바로 이 부분을 다시 실행했다. 읽기 중 refault는 95%(상자 8GiB), 97.9%(4GiB)였다. 다음 질문: dbcache를 키우면 LevelDB 읽기가 줄어드는가? 그런데 dbcache도 같은 2Gi limit 안에 있다. 메모리를 dbcache와 page cache 중 어디에 주는 것이 좋은가? 이것은 코드를 읽고 측정해야 답할 수 있다.

-reindex-chainstate와 bitcoin.conf

왜 알아야 하나실습 F는 같은 작업을 조건만 바꾸어 두 번 실행한다. IBD를 다시 하면 네트워크(피어 속도)가 결과를 흔든다. -reindex-chainstate는 네트워크 없이 같은 검증 작업을 다시 하게 한다.

  • -reindex-chainstate: chainstate/(UTXO 집합)를 지우고, 디스크에 이미 있는 블록으로 다시 만든다. 블록을 다운로드하지 않는다.
  • -reindex: 블록 인덱스(blocks/index/)까지 다시 만든다. 더 오래 걸린다.
  • 설정은 명령줄(args)과 bitcoin.conf에서 온다. 파일에서는 앞의 -를 빼고 쓴다: reindex-chainstate=1.
  • bitcoin.conf는 데이터 디렉터리의 맨 위에 둔다. signet/ 안이 아니다. signet/에는 데이터만 있다.
  • bitcoind는 시작할 때만 설정을 읽는다. 그래서 파일을 쓴 뒤 재시작해야 한다.
내 환경에서StatefulSet의 args에 넣으면 node-0과 node-1이 모두 reindex를 한다. 하지만 bitcoin.conf는 PVC 안에 있고, node-1의 PVC는 node-1만 쓴다. 그래서 2026-10-13에 node-1의 /home/bitcoin/.bitcoin/bitcoin.conf에만 한 줄을 썼다. 그다음 kubectl delete pod bitcoin-node-1로 재시작했다. 새 컨테이너는 새 cgroup을 받으므로 cpu.stat, io.stat, memory.stat이 0부터 다시 센다. 끝났을 때의 값이 그대로 이번 실행의 값이 된다. 2026-10-14 F-6: 실험이 끝난 뒤 bitcoin.conf(이 한 줄만 있었다)를 지우고 Pod를 다시 만들었다. 재시작 직후 blocks = headers = 326339, initialblockdownload: false였다. 재구축 없이 시작했다.
자주 하는 오해끝난 뒤에 설정 줄을 지워야 한다. 줄이 남아 있으면 Pod가 다시 시작될 때마다 reindex를 다시 한다. 그리고 블록 수로 남은 시간을 예상하지 않는다. Signet 초기 블록은 거의 비어 있어서 빨리 지나간다. verificationprogress가 더 정확하다.

성능을 보는 순서 (USE)

왜 알아야 하나느릴 때 아무 도구나 켜면 시간만 쓴다. 정해진 순서로 자원을 하나씩 확인하면 병목을 빠뜨리지 않는다.

자원(CPU, 메모리, 디스크, 네트워크)마다 세 가지를 본다:

질문예
Utilization (사용률)얼마나 바쁜가?CPU 90%, 디스크 %util
Saturation (포화)기다리는 작업이 있는가?load average, I/O 대기열, CPU throttling
Errors (오류)실패가 있는가?OOMKilled, 디스크 오류, 연결 끊김
  • 사용률이 낮아도 포화가 있을 수 있다. 예: CPU 한도 때문에 throttling되는 컨테이너.
  • 시스템 전체 값과 노드 하나의 값을 구분한다. 서버에는 다른 서비스도 있다.
내 환경에서2026-10-13의 조사를 USE로 다시 보면 이렇다.
  • CPU: 사용률 평균 약 0.45코어(낮음), 포화(throttling) 약 2.6%(낮음). 원인이 아니다.
  • 디스크: 읽기 약 1.89TB, 데이터의 약 78배. 이상하다.
  • 메모리: kind 상자의 memory.events max가 24,428,625였다(포화). 이 값은 하위 cgroup을 포함한다. 상자 자신의 값은 10-14 확인에서 약 83%였다. 오류(OOM)는 0이다.
결론: 메모리 포화 → 캐시 손실 → 디스크 읽기 → CPU 대기. 오류가 없어서 "느리기만" 했다.

USE 다음의 순서. USE는 어느 자원이 부족한지 찾는다. 실무에서는 보통 4단계로 내려간다.

  1. 시스템 관찰 (cgroup, iostat, USE): 어느 자원이 부족한가?
  2. 프로파일링 (perf, flame graph, bitcoind의 -debug=bench): 어느 함수에서 시간을 쓰는가?
  3. 소스 코드: 그 함수는 왜 그렇게 동작하는가?
  4. 수정과 재측정: 1단계의 숫자가 실제로 좋아졌는가?
자주 하는 오해성능 문제를 소스 코드부터 보지 않는다. 시간이 어디에서 쓰이는지 모르고 고치면 틀린 곳을 고친다. 이 프로젝트의 첫 원인도 코드가 아니라 환경(kind 상자 메모리)이었다. 설정 하나로 읽기가 990GB → 433GB로 달라졌다(실습 F).
내 환경에서2026-10-14에 1단계를 끝냈다. 2단계는 -debug=bench로 시작할 계획이다. 이 옵션은 블록마다 검증 단계별 시간을 debug.log에 남긴다. perf는 보통 root 권한이 필요하지만, 이 옵션은 필요 없다.

실험 설계의 기본

왜 알아야 하나측정 한 번은 증거가 아니다. 개선 효과를 남에게 보여 주려면 같은 결과가 다시 나와야 한다.

  1. 질문을 먼저 쓴다. 예: "dbcache 450 → 2000 MiB이면 Signet IBD 시간이 줄어드는가?"
  2. 기준선(baseline)을 잰다. 바꾸기 전의 값이다.
  3. 한 번에 하나만 바꾼다. 두 개를 바꾸면 어느 것이 원인인지 모른다.
  4. 여러 번 반복한다. 평균과 흩어짐을 같이 쓴다.
  5. 조건을 기록한다. 버전, 설정, 디스크, 캐시 상태, 피어 수, 다른 서비스의 부하.
  6. 결과를 원인으로 설명한다. "빨라졌다"가 아니라 "디스크 대기가 줄어서 빨라졌다".
자주 하는 오해네트워크 피어는 매번 다르다. 블록을 받는 속도가 결과를 흔든다. 검증 속도만 재고 싶으면 피어 조건을 고정하거나 없앤다. 예: 내 노드에만 -connect, 또는 블록을 다시 받지 않는 -reindex-chainstate.
