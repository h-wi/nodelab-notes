    파일시스템과 디스크 FILESYSTEM · DISK

    블록 장치 위에 무엇이 얹히는지, 그 구조에서 어떤 동작이 나오는지.

    파일시스템이란

    왜 알아야 하나블록 장치는 "N번 블록을 읽어라, 써라"만 할 줄 안다. 이름도, 권한도, 빈 블록의 목록도 없다. 이것들을 얹는 층이 파일시스템이다. 그래서 파일시스템을 어떻게 만드느냐에 따라 쓸 수 있는 용량, 만들 수 있는 파일 수, 장애 뒤의 복구 방식이 달라진다.

    • 정의: 블록 장치 위에 놓는 자료구조와, 그 자료구조를 다루는 커널 코드다.
    • 하는 일 네 가지
      • 이름을 데이터에 잇는다: 경로 → inode → 데이터 블록(inode).
      • 메타데이터를 둔다: 종류, 권한, 소유자, 크기, 시각.
      • 할당한다: 빈 블록과 빈 inode를 찾아 주고, 다 쓴 것을 돌려받는다(inode 표와 bitmap).
      • 일관성을 지킨다: 쓰는 도중에 전원이 꺼져도 자료구조가 깨지지 않게 한다. ext4는 journal을 쓴다(ext4).
    • 블록 장치 ≠ 물리 디스크: 파티션, RAID 가상 장치(/dev/md0), LVM 논리 볼륨, 파일을 블록 장치처럼 쓰는 루프 장치(/dev/loop0) 위에도 파일시스템을 만든다.
    • 블록 장치가 없는 파일시스템도 있다: /proc, /sys(커널의 정보를 파일로 보여 줌), tmpfs(메모리). 같은 open, read로 읽힌다. 이것을 가능하게 하는 층이 VFS다.
    • 마운트: 파일시스템 하나를 디렉터리 트리의 한 자리에 붙이는 일이다. 붙인 뒤에는 그 디렉터리 아래가 그 파일시스템이다.
    자주 하는 오해"물리 디스크에 정보를 체계적으로 관리하는 시스템"은 정의로 약하다. 두 가지 이유가 있다. (1) "무엇을 위해"만 있고 "어떻게"가 없다. 그래서 데이터베이스에도 똑같이 맞는다. (2) 아래가 물리 디스크가 아닐 때가 많다. "블록 장치 위에 이름, 메타데이터, 할당, 일관성을 얹는 자료구조"처럼 하는 일을 말해야 정의가 된다.

    생각해 볼 질문같은 디스크라도 파일시스템을 만드는 설정에 따라 바뀌는 운영 숫자는 무엇이 있을까? 그중 만든 뒤에 바꿀 수 없는 것은 무엇일까?

    직접 확인 
    lsblk -f                    # 장치, 파일시스템 종류, 마운트 자리
findmnt                     # 마운트 트리 (어느 디렉터리에 무엇이 붙었나)
cat /proc/filesystems       # 이 커널이 아는 파일시스템. nodev = 블록 장치가 필요 없음
stat -f /                   # 파일시스템 단위의 정보 (블록 크기, 블록 수, inode 수)

    VFS (Virtual File System)

    왜 알아야 하나프로그램은 open, read, write, stat만 부른다. 그 아래가 ext4인지, XFS인지, /proc인지 모른다. 이것이 되는 이유가 VFS다. 그리고 page cache가 이 층에 있다. 그래서 "파일을 읽었는데 디스크는 읽지 않았다"가 생긴다.

    • 자리: 커널 안에서 시스템 콜과 실제 파일시스템 사이에 있는 공통 층이다. 디스크에 자기 자료구조를 쓰지 않는다.
    • 공통 객체 네 개: 모든 파일시스템을 같은 모양으로 다룬다.
      • superblock: 마운트된 파일시스템 하나.
      • inode: 파일 하나(메모리 안의 모양).
      • dentry: 경로의 이름 하나와 그것이 가리키는 inode.
      • file: 열린 파일 하나. 읽는 위치(offset)와 모드를 가진다. 같은 파일을 두 번 열면 file은 둘, inode는 하나다.
    • 함수 표: 각 파일시스템은 file_operations, inode_operations 같은 함수 표를 VFS에 등록한다. VFS는 그 함수를 불러 실제 일을 맡긴다.
    • 공통 캐시: dentry cache(경로 찾기), inode cache, page cache(파일 데이터). 같은 파일을 두 번째 읽을 때 디스크에 가지 않는 이유다.
    • 디스크가 없는 파일시스템도 같은 함수 표를 등록한다. 그래서 cat /proc/meminfo는 보통 파일처럼 읽힌다. 내용은 읽는 순간 커널이 만든다.
    자주 하는 오해"VFS는 파일시스템의 한 종류다"는 틀리다. VFS는 종류가 아니라 모든 종류 위의 공통 층이다. 디스크 위의 모양(ext4의 inode 표 등)은 각 파일시스템이 정한다.

    생각해 볼 질문page cache가 각 파일시스템 안이 아니라 VFS 층에 있으면 무엇이 좋을까? ls -l /proc/meminfo는 크기를 0으로 보여 준다. 그런데도 cat은 내용을 보여 준다. 무엇이 다르게 일하는 걸까?

    직접 확인 
    ls -l /proc/meminfo; head -3 /proc/meminfo
ls -l /proc/self/fd           # 이 프로세스가 연 file들 (0, 1, 2 = 표준 입출력)
free -h                       # buff/cache = page cache 등
sudo grep -E '^(dentry|ext4_inode_cache) ' /proc/slabinfo   # dentry, inode 캐시의 개수

    HDD, SSD, NVMe: 파일시스템 아래

    왜 알아야 하나디스크가 HDD든 SSD든 VFS와 ext4가 하는 일은 같다. 다른 것은 그 아래 층이다. 그래서 "SSD면 무엇이 다른가?"에는 층을 나눠서 답해야 한다. 노드의 데이터베이스처럼 작은 무작위 I/O가 많은 일은 이 차이가 성능을 정한다.

    HDDSATA SSDNVMe SSD
    읽는 방법헤드가 움직이고(seek) 원판이 돌아야 한다움직이는 부품이 없다. NAND 칩을 전기로 읽는다
    무작위 읽기 한 번수 ms수십 ~ 수백 µs
    연결과 큐SATA(AHCI): 큐 1개, 깊이 32PCIe: 큐 최대 약 64K개, 큐마다 깊이 최대 약 64K
    I/O 스케줄러 (보통)mq-deadline, bfqmq-deadlinenone
    • HDD의 비용은 seek다. 그래서 순차 I/O는 빠르고 무작위 I/O는 매우 느리다. I/O 스케줄러가 요청의 순서를 바꿔 헤드의 이동을 줄인다.
    • SSD는 제자리에 덮어쓰지 못한다. NAND는 지운 자리에만 쓸 수 있고, 지우는 단위(erase block)가 쓰는 단위(page)보다 크다. 그래서 장치 안의 FTL(Flash Translation Layer)이 논리 주소를 물리 위치로 바꾸고, 새 내용은 다른 빈 자리에 쓴다.
    • garbage collection과 쓰기 증폭: 빈 erase block을 만들려면, 아직 쓰는 page를 다른 곳으로 옮기고 블록을 지운다. 그래서 장치 안의 실제 쓰기가 요청한 쓰기보다 많아진다. 이것이 쓰기 증폭이다. 수명과 성능에 영향을 준다.
    • TRIM(discard): 파일시스템이 "이 블록은 이제 쓰지 않는다"를 SSD에 알린다. 그러면 GC가 쓸데없는 데이터를 옮기지 않는다. Ubuntu는 fstrim.timer로 1주일에 한 번 한다.
    • NVMe에서 스케줄러를 none으로 두는 이유: 장치가 큐를 많이 가지고 충분히 빠르다. 그래서 커널이 순서를 바꾸는 비용이 얻는 것보다 크다.
    자주 하는 오해"SSD를 쓰면 파일시스템이 다르게 동작한다"는 대부분 틀리다. VFS와 ext4의 자료구조는 같다. 다른 것은 block layer 아래다. (TRIM처럼 파일시스템이 장치에 알려 주는 일은 있다.)

    생각해 볼 질문작은 무작위 읽기가 많은 데이터베이스와 큰 파일을 순서대로 쓰는 로그를 같은 장치에 두면 무엇이 서로 방해할까? TRIM을 하지 않고 SSD를 거의 가득 채워 쓰면 시간이 지나며 무엇이 나빠질까?

cat /sys/block/nvme0n1/queue/scheduler        # [none] 처럼 괄호가 지금 값 (장치 이름은 예시)

    inode

    왜 알아야 하나"파일을 지웠는데 공간이 그대로다", "같은 파일시스템 안의 mv는 크기와 상관없이 즉시 끝난다", "자리가 남았는데 파일을 못 만든다". 이 동작이 모두 inode의 구조에서 나온다.

    • 정의: 파일 하나마다 있는 고정 크기의 자료구조다. 이름을 뺀 메타데이터와 데이터 블록의 위치를 담는다. 번호로 구별하고, 번호는 파일시스템 안에서만 고유하다. ext4의 inode는 기본 256 bytes다.
    • 담는 것: 종류와 권한(mode), 소유자(uid, gid), 크기, 시각(접근 atime, 수정 mtime, 상태 변경 ctime, 생성 crtime), link count(이 inode를 가리키는 이름의 수), 데이터 위치(ext4는 extent).
    • 담지 않는 것: 이름. 이름은 디렉터리에 있다. 디렉터리도 파일이고, 그 데이터는 (이름, inode 번호)의 목록이다. 그래서 한 inode를 이름 여럿이 가리킬 수 있다(하드 링크).
    • 삭제: rm은 디렉터리에서 이름을 지우고 link count를 1 줄인다(시스템 콜 이름이 unlink다). 데이터 블록은 link count가 0이고, 그 파일을 연 프로세스도 없을 때 풀린다.
    • 같은 파일시스템 안의 mv: 디렉터리 항목만 바꾼다(rename). 데이터는 움직이지 않는다. 다른 파일시스템으로 옮기면 복사한 뒤 지운다.
    • 로그 회전: 로그 파일의 이름을 바꿔도 inode는 그대로다. 그래서 프로세스는 이름이 바뀐 옛 파일에 계속 쓴다. 회전 뒤에 프로세스가 경로를 다시 열게 해야 한다(신호를 보내거나, 다시 시작하거나, copytruncate).
    • 마운트 전에 켜진 서비스: 위 그림의 마지막 줄 때문에, 데이터 디스크가 마운트되기 전에 서비스가 켜지면 OS 디스크에 데이터를 쓴다. 오류도 나지 않는다. systemd의 RequiresMountsFor=가 이것을 막는다.
    • inode 고갈: ext4의 inode 수는 만들 때 정해진다. 다 쓰면 공간이 남아도 "No space left on device"가 나온다. df -i로 따로 본다(용량이 줄어드는 이유).
    자주 하는 오해"inode는 경로마다 있는, 고유한 자료구조"는 두 곳이 틀리다. (1) 경로마다가 아니라 파일마다 있다. 하드 링크면 경로 둘이 inode 하나를 가리킨다. inode에는 이름도 경로도 없다. (2) 번호는 파일시스템 안에서만 고유하다. 위 그림처럼 2번이 둘 나올 수 있다.

    생각해 볼 질문큰 로그 파일을 rm으로 지웠는데 df의 사용량이 줄지 않는다. 어떤 상태일 수 있을까? 서비스를 멈추지 않고 공간을 돌려받는 방법은 무엇이 있을까?

    생각해 볼 질문두 파일의 inode 번호가 같다. 같은 파일이라고 말하려면 무엇을 더 확인해야 할까?

    직접 확인 
    stat /etc/hostname                         # Inode, Links, 크기, 시각
ls -id / /mnt /proc                        # 루트와 마운트 지점의 inode 번호
stat -c '%d %i %n' / /mnt                  # %d = 장치 번호, %i = inode 번호
df -i /                                    # inode를 얼마나 썼나
sudo lsof +L1                              # 이름은 지웠는데 아직 열린 파일 (link count 0)

    하드 링크와 소프트 링크

    왜 알아야 하나두 링크는 이름은 비슷하지만 바뀌는 자리가 다르다. 하드 링크는 디렉터리만 바꾸고, 소프트 링크는 새 파일을 만든다. 이 차이에서 "원본을 지우면 어떻게 되나", "다른 디스크로 걸 수 있나"의 답이 나온다.

    하드 링크 ln a b소프트 링크 ln -s a c
    새로 생기는 것디렉터리 항목 하나새 inode(종류 symlink)와 디렉터리 항목 하나
    가리키는 것inode 번호경로 문자열. 열 때마다 커널이 그 경로를 다시 찾는다
    원본 이름을 지우면그대로 열린다. 두 이름은 원본과 사본이 아니라 같은 자격이다끊어진 링크(dangling)가 된다
    다른 파일시스템으로안 된다. inode 번호는 그 파일시스템 안에서만 뜻이 있다된다
    디렉터리를 가리키기보통 안 된다. 트리에 순환이 생기지 않게 막는다된다
    ls -li에서inode 번호가 같다. 링크 수 2inode 번호가 다르다. 줄이 l로 시작한다
    자주 하는 오해"하드 링크는 inode의 데이터에 무엇을 추가한다"는 틀리다. 추가되는 곳은 디렉터리의 데이터다. inode에서는 link count 숫자 하나만 바뀐다. 그리고 소프트 링크의 "간접"은 indirect block과 다른 말이다. indirect block은 데이터 블록의 위치를 적는 옛 방식의 이름이다.

    생각해 볼 질문디렉터리에 하드 링크를 허용하면 어떤 일이 깨질까? rm -r이나 디스크 사용량 계산을 떠올려 본다. 소프트 링크가 자기 자신을 가리키게 만들면 열 때 무슨 일이 생길까?

    직접 확인 
    cd "$(mktemp -d)"
echo hi > a; ln a b; ln -s a c
ls -li                      # a와 b는 inode 번호가 같고 링크 수 2. c는 번호가 다르다
rm a; cat b; cat c          # b는 열리고, c는 "No such file or directory"
readlink c                  # 소프트 링크의 내용(경로 문자열)

    연결: inodeindirect block과 extent

    indirect block과 extent

    왜 알아야 하나inode는 "파일의 몇 번째 블록이 디스크의 몇 번 블록에 있나"를 적어야 한다. 적는 방식에 따라 큰 파일을 읽고 지우는 비용이 달라진다. ext3까지는 indirect block, ext4부터는 extent를 쓴다.

    • indirect block 방식: inode에 블록 번호 칸이 15개 있다(4 KiB 블록, 번호 하나 4 bytes 기준).
      • 1~12번 칸(direct): 데이터 블록 번호를 바로 적는다 → 48 KiB까지.
      • 13번 칸(single indirect): 데이터가 아니라 "블록 번호 목록이 든 블록"을 가리킨다. 그 블록에 번호 1,024개가 들어간다 → 4 MiB 더.
      • 14번 칸(double indirect): 목록의 목록 → 4 GiB 더. 15번 칸(triple indirect): 한 단계 더 → 4 TiB 더.
      • "indirect"는 데이터가 아니라 번호가 든 블록을 거쳐 간다는 뜻이다.
    • indirect의 비용: 큰 파일의 뒤쪽을 읽으려면 번호 블록을 2~3번 더 읽는다. 큰 파일을 지우면 번호 블록을 모두 읽어 블록을 하나씩 풀어야 해서 느리다.
    • extent: 연속 구간을 (파일 안의 시작 블록, 길이, 디스크의 시작 블록)으로 적는다. 하나가 12 bytes다. inode 안의 60 bytes 칸에 머리(12 bytes)와 extent 4개가 들어간다. 더 많으면 extent tree 블록을 따로 잡고, inode에는 그 뿌리만 남긴다.
    • 조각화: extent의 이득은 파일이 연속으로 놓일 때 크다. 조각이 많으면 extent도 많아진다. ext4의 지연 할당이 연속 배치를 돕는다(ext4).
    자주 하는 오해"extent는 ext4가 처음 만든 방식이다"는 ext 계열 안에서만 맞다. XFS(1994) 같은 다른 파일시스템은 그 전부터 extent를 썼다. 정확한 말은 "ext3까지는 indirect block, ext4부터 extent"다. 그리고 extent는 경로와 블록을 잇는 것이 아니다. 경로 → inode는 디렉터리가 맡고, extent는 파일 안의 위치 → 디스크의 블록 번호를 잇는다.

    생각해 볼 질문작은 조각으로 아주 많이 흩어진 큰 파일이 있다. 이 파일에서는 extent와 indirect block의 차이가 어떻게 바뀔까? 데이터베이스처럼 파일을 계속 덧붙여 쓰는 프로그램은 조각화를 줄이려고 무엇을 할 수 있을까?

    직접 확인 
    fallocate -l 1G /tmp/big.bin; filefrag -v /tmp/big.bin   # extent 목록. 몇 개로 적혔나
rm /tmp/big.bin
sudo debugfs -R 'stat /etc/hostname' "$(findmnt -no SOURCE /)"   # inode의 EXTENTS 칸 (읽기만 한다)

    연결: inodeext4하드 링크와 소프트 링크

    inode 표와 bitmap

    왜 알아야 하나ext4는 inode를 미리 만든 배열(inode 표)에 둔다. 이 선택에서 장점(번호만 알면 위치가 계산된다)과 비용(만들 때 자리를 미리 잡는다, inode 수가 고정된다)이 함께 나온다.

    • block group: ext4는 디스크를 블록 32,768개씩(4 KiB 블록이면 128 MiB) 나눈다. 그룹마다 block bitmap(어느 블록이 쓰이나, 1 bit씩), inode bitmap(어느 inode 번호가 쓰이나), inode table(inode의 배열)이 있다. 그룹의 위치 정보는 group descriptor에 있다.
    • 위치 계산: inode 번호 N의 위치는 검색 없이 계산 한 번으로 나온다.
      • 그룹 = (N − 1) ÷ 그룹당 inode 수
      • 그룹 안의 순서 = (N − 1) % 그룹당 inode 수
      • 위치 = 그 그룹의 inode table 시작 + 순서 × inode 크기
      그래서 디렉터리 항목에는 inode 번호 하나만 적어도 된다.
    • 그룹마다 따로 두는 이유: inode와 그 파일의 데이터를 같은 그룹 안에 가깝게 두려는 것이다. HDD에서는 seek가 준다.
    • 수정: 같은 칸을 제자리에서 덮어쓴다. inode 크기가 고정이라 자리가 모자라지 않는다. extent가 4개를 넘으면 extent tree 블록을 따로 잡는다.
    • 삭제: 칸은 움직이지 않는다. 번호 = 위치이기 때문이다.
      1. 디렉터리에서 이름 항목을 지운다. link count를 1 줄인다.
      2. link count가 0이고 연 프로세스가 없으면, 데이터 블록을 block bitmap에서 빈 것으로 표시한다.
      3. inode 번호를 inode bitmap에서 빈 것으로 표시한다. 칸의 내용은 남아 있다가, 새 파일이 그 번호를 받을 때 덮어쓴다.
      4. 같은 번호의 옛 파일과 새 파일은 inode 안의 generation 숫자로 구별한다.
    • 장애에 대비하는 법: 위의 여러 곳(디렉터리 블록, inode, 두 bitmap, group descriptor)을 한 묶음(transaction)으로 journal에 먼저 쓴다. 그래서 전원이 꺼져도 반만 지워진 상태가 남지 않는다. 이름은 지웠지만 아직 열린 파일은 orphan 목록에 올린다. 그 상태에서 서버가 죽으면, 다음 마운트 때 이 목록을 보고 공간을 푼다.
    • 다른 방식과 비교: XFS는 inode를 필요할 때 묶음으로 만들고, Btrfs는 B-tree에 넣는다. 그래서 고정된 inode 표가 없고 inode 고갈이 거의 없다. 대신 위치를 찾으려면 트리를 따라간다.
    자주 하는 오해"inode를 지우면 표에서 칸이 빠지고 뒤의 번호가 당겨진다"는 틀리다. 칸은 그대로 있고, bitmap의 1 bit만 바뀐다. 번호가 곧 위치라서 칸을 옮길 수 없다.

    생각해 볼 질문inode bitmap은 "빈 번호"라고 하는데 inode 표의 칸에는 아직 옛 내용이 있다. 이 둘이 서로 맞지 않게 되면 어떤 증상이 나올 수 있을까? 이것을 찾아 고치는 도구는 무엇을 비교해야 할까?

    직접 확인 
    sudo dumpe2fs -h "$(findmnt -no SOURCE /)" 2>/dev/null \
  | grep -E 'Inode count|Inodes per group|Blocks per group|Inode size|Block size'
sudo dumpe2fs "$(findmnt -no SOURCE /)" 2>/dev/null | grep -m3 -A6 '^Group'   # 그룹마다 bitmap과 inode table의 위치

    ext4의 특징

    왜 알아야 하나ext4는 Ubuntu의 기본 파일시스템이다. "ext4의 특징은?"에는 ext3에서 새로 바뀐 것을 말해야 한다. 물려받은 것(journal)만 말하면 "그건 ext3도 있지 않나?"라는 질문이 온다.

    ext3 (2001)ext4 (2008)
    journal있다 (ext3에서 처음)물려받았다. journal에 checksum을 더했다
    블록 위치indirect blockextent
    블록 주소32 bit48 bit
    최대 크기 (4 KiB 블록)파일 2 TiB, 볼륨 16 TiB파일 16 TiB, 볼륨 1 EiB
    할당쓸 때 바로 블록을 정한다지연 할당 + 여러 블록을 한 번에 잡는 할당기
    fsck모든 그룹을 읽는다쓰지 않은 그룹과 inode 표를 건너뛴다
    그 밖에메타데이터 checksum, fallocate(공간 미리 잡기), ns 단위 시각, 생성 시각
    • 지연 할당: write 때는 데이터를 page cache에만 두고 블록을 정하지 않는다. 디스크로 내릴 때 모인 양을 보고 연속된 블록을 한 번에 잡는다. 그래서 조각화가 줄고 extent가 적어진다.
    • journal(jbd2): 바꿀 내용을 먼저 journal에 쓰고 commit한 뒤, 제자리에 쓴다. 장애 뒤에는 전체 검사 없이 journal만 다시 적용한다. 목적은 파일시스템 자료구조의 일관성이다.
    • journal 모드 (마운트 옵션 data=)
      • ordered(기본): 메타데이터만 journal에 쓴다. 데이터 블록은 그 메타데이터의 commit 전에 먼저 디스크에 쓴다. 그래서 새 크기가 기록됐는데 데이터는 옛 쓰레기인 상태를 막는다.
      • journal: 데이터도 journal에 쓴다. 가장 안전하고, 쓰기가 두 번이라 느리다.
      • writeback: 데이터 순서를 지키지 않는다. 가장 빠르고, 장애 뒤에 파일에 옛 데이터가 보일 수 있다.
    자주 하는 오해"ext4의 가장 큰 특징은 저널링이다"는 틀리다. 저널링은 ext3(2001)에서 들어왔다. 그리고 "저널링이 있으니 데이터를 잃지 않는다"도 틀리다. 기본 모드는 데이터를 journal에 쓰지 않는다. 프로그램이 fsync를 부르기 전에 전원이 꺼지면, page cache에만 있던 데이터는 잃는다.

    생각해 볼 질문지연 할당은 데이터를 page cache에 더 오래 둔다. 그러면 장애가 났을 때 무엇이 달라질까? 그래서 데이터베이스는 어떤 시스템 콜을 언제 불러야 할까?

    직접 확인 
    findmnt -no FSTYPE,OPTIONS /                          # 마운트 옵션 (data= 가 없으면 ordered)
sudo tune2fs -l "$(findmnt -no SOURCE /)" | grep -E 'features|Journal'   # has_journal, extent, 64bit, metadata_csum …

    연결: indirect block과 extentinode 표와 bitmap용량이 줄어드는 이유

    파일시스템이 용량을 줄이는 이유

    왜 알아야 하나디스크 라벨의 크기와 실제로 쓸 수 있는 크기는 다르다. 차이는 세 곳에서 나온다: 단위, 파일시스템이 만들 때 떼어 두는 자리, root만 쓰는 몫. 이 셋을 나눠 말할 수 있어야 디스크 계획이 맞는다.

    • 단위 (손실이 아니다): 디스크 회사는 10진수(1 TB = 1012 bytes)를 쓰고, df -h는 2진수(1 TiB = 240 bytes)를 쓴다. 1 TB = 0.909 TiB다.
    • inode 표 = inode 수 × inode 크기(256 bytes). inode 수 = 크기 ÷ inode_ratio(데이터 몇 bytes마다 inode 하나)다. 그래서 몫은 256 ÷ inode_ratio다. mke2fs는 파일시스템의 크기를 보고 종류를 골라 inode_ratio를 정한다(/etc/mke2fs.conf).
    파일시스템 크기종류inode_ratio (bytes)inode 표의 몫
    512 MiB 미만small4,096약 6.3%
    512 MiB ~ 4 TiBdefault16,384약 1.56%
    4 TiB ~ 16 TiBbig32,768약 0.78%
    16 TiB 이상huge65,536약 0.39%
    • 큰 디스크일수록 inode를 드물게 만드는 이유: 큰 디스크에는 보통 큰 파일이 들어간다고 본다. inode를 줄이면 메타데이터 자리가 줄고, mkfs와 fsck도 빨라진다.
    • journal 등: journal은 128 GiB 이상이면 1 GiB다. 디스크가 커도 거의 그대로라서, 큰 디스크일수록 몫이 작아진다. 그 밖에 bitmap, group descriptor, superblock 사본이 있다.
    • 예약 블록 5%: mkfs -m의 기본값이다. uid 0(root)만 쓸 수 있다. 이유는 두 가지다(man mke2fs): 디스크가 차도 root의 데몬(로그 등)이 계속 쓰게 하고, 할당기에 빈 자리를 남겨 조각화를 줄인다.
    • df와의 관계: Size에서는 메타데이터(inode 표, journal 등)가 이미 빠져 있다. Avail에서는 예약 블록이 더 빠진다. 보통 사용자로 도는 서비스가 쓸 수 있는 값은 Avail이다.
    • 바꾸는 법: 예약은 만든 뒤에도 바꾼다(tune2fs -m). inode는 만들 때만 정한다: -i(inode_ratio), -N(개수), -T(종류), -I(inode 크기). 대가는 꽉 찼을 때의 여유와 만들 수 있는 파일 수다.
    자주 하는 오해"큰 디스크에서는 inode를 크게 잡는다"는 틀리다. inode 하나의 크기(inode_size, 256 bytes)는 그대로다. 바뀌는 것은 개수(inode_ratio)다. 그리고 "inode 표는 root 몫 5%의 일부다"도 틀리다. 둘은 따로다. inode 표는 처음부터 Size에서 빠져 있고, root 몫은 데이터 블록의 일부를 root만 쓰게 남긴 것이다.

    생각해 볼 질문작은 파일을 아주 많이 둘 디스크가 있다. 큰 파일 몇 개만 둘 디스크도 있다. 기본값으로 만들면 각각 무엇이 남고 무엇이 모자랄까? 만들기 전에 무엇을 재 보면 좋을까?

    LSM-tree와 B-tree: 지운 공간의 회수

    왜 알아야 하나지워도 디스크 사용량이 바로 줄지 않는 DB가 많다. 그러나 이유와 결과는 저장 구조에 따라 다르다. 디스크 용량을 계획할 때 "지운 뒤 언제, 어떻게 공간이 돌아오나"가 여기서 정해진다.

    • LSM-tree (RocksDB, LevelDB, Cassandra)
      • 쓰기는 메모리(memtable)에 모았다가 정렬된 파일(SST)로 한 번에 쓴다. SST는 한 번 쓰면 고치지 않는다.
      • 삭제도 "지움 표시(tombstone)"를 새로 쓰는 일이다. 옛 값은 그대로 파일에 남는다.
      • compaction이 여러 SST를 읽어 합치고 다시 쓸 때, 지운 값과 지움 표시를 버린다. 이때 공간이 돌아온다.
      • 그래서 compaction 전까지는 지운 공간을 다시 쓰지도 못한다. 새 데이터는 새 파일로 가고, 사용량이 늘어난다.
    • B-tree (MySQL InnoDB, PostgreSQL, SQLite)
      • 페이지를 제자리에서 고친다.
      • 지운 줄의 공간은 정리 작업(InnoDB purge, PostgreSQL VACUUM) 뒤 DB 안에서 다시 쓴다. SQLite는 빈 페이지를 파일 안의 freelist에 넣고 다시 쓴다.
      • 파일 크기는 보통 줄지 않는다. 줄이려면 파일을 다시 쓴다(SQLite VACUUM, PostgreSQL VACUUM FULL). 대신 오래 돌면 파일 크기가 거의 일정해진다.
    • LSM-tree에서 키의 순서가 회수 속도를 정한다
      • 키가 시간 순(예: 높이, 번호가 앞에 오는 키)이면 오래된 데이터가 같은 SST 파일들에 모인다. 범위 삭제 뒤 그 범위에 완전히 들어가는 파일을 통째로 지울 수 있다(RocksDB DeleteFilesInRange). compaction을 기다리지 않는다.
      • 키가 해시나 주소 순이면 오래된 줄이 모든 파일에 흩어진다. 파일째 지울 수 없어서, compaction이 줄을 하나씩 보고 버린다(compaction filter). 회수는 compaction이 도는 주기만큼 늦다.
      • 그래서 용량 계획에는 "보관 기간 + compaction이 늦게 회수하는 몫"을 넣는다.
    • WAL: 두 구조 모두 변경을 먼저 로그 파일에 덧붙인다. SQLite WAL 모드에서는 checkpoint가 내용을 본 파일에 옮긴 뒤에야 WAL 파일을 처음부터 다시 쓴다. 긴 읽기가 checkpoint를 막으면 WAL 파일이 커진다.
    자주 하는 오해"compaction을 해야 실제로 지워지는 것은 거의 모든 DB가 같다." 늦게 회수하는 것은 흔하다. 다른 점은 그 사이의 공간이다. B-tree는 지운 자리를 DB 안에서 다시 쓴다. LSM-tree는 compaction 전까지 다시 쓰지 못해서 사용량이 계속 는다.

    생각해 볼 질문B-tree DB에서 큰 테이블의 절반을 지웠다. 디스크 사용량을 줄이려면 무엇을 해야 할까? 그 작업이 도는 동안 서비스에는 무엇이 생길까?

    직접 확인 
    du -sh <DB 디렉터리>; ls <DB 디렉터리> | grep -c '\.sst$'   # RocksDB: SST 파일 수
sqlite3 a.db 'PRAGMA freelist_count; PRAGMA page_count;'          # SQLite: 빈 페이지 수
psql -c 'SELECT relname, n_dead_tup FROM pg_stat_user_tables;'    # PostgreSQL: 지웠지만 아직 남은 줄

    메모리 VIRTUAL MEMORY

    프로세스가 보는 주소와 RAM의 실제 자리가 어떻게 이어지나. 메모리 설정 값은 모두 이 구조 위에 있다.

    page와 page table

    왜 알아야 하나VMA, mmap, swap, page cache, 메모리 고정(memlock)은 모두 page 단위로 일어난다. page를 모르면 이 설정들의 설명이 이어지지 않는다.

    • page의 정의: 가상 주소 공간을 고정 크기로 나눈 단위다. 보통 4KiB다(getconf PAGESIZE → 4096).
    • frame의 정의: 물리 메모리(RAM)를 같은 크기로 나눈 단위다. 데이터는 frame에 있다. page는 주소의 칸이고, 데이터를 담지 않는다.
    • 왜 나누나: 가상 주소와 물리 주소의 대응을 byte마다 적으면 표가 RAM보다 커진다. 덩어리 단위로 적으면 표가 작아진다. 그리고 크기가 같아서 빈 frame 아무 곳에나 page를 놓을 수 있다.
    • 주소를 둘로 나눈다: 4KiB = 212이다. 그래서 주소의 아래 12bit는 page 안의 위치(offset)이고, 나머지는 page 번호다. 변환은 page 번호만 frame 번호로 바꾼다. offset은 그대로 둔다.
    • page table의 정의: 가상 page 번호를 물리 frame 번호로 바꾸는 표다. 프로세스마다 하나 있다. 항목 하나에는 frame 번호와 상태 bit가 있다.
      • present: 지금 RAM에 frame이 있나
      • 쓰기 가능, 사용자 접근 가능(커널 전용인가)
      • accessed, dirty: 최근에 읽혔나, 쓰였나
    • 누가 하나: 커널이 표를 채운다. CPU의 MMU가 메모리 접근마다 하드웨어로 표를 읽어 주소를 바꾼다. 최근 변환 결과는 TLB라는 캐시에 둔다.
    • 표의 모양: 한 장의 큰 배열이 아니다. x86-64는 4단계의 표로 나눈다. 쓰는 구간의 표만 만든다. 프로세스를 바꾸면 커널이 CPU 레지스터(CR3)를 새 프로세스의 표 주소로 바꾼다.
    • huge page: 2MiB 같은 큰 page다. 표 항목 수가 줄어서 TLB에 맞는 범위가 넓어진다.
    자주 하는 오해(1) "page는 가상 메모리에서 데이터를 담는 단위다." 데이터를 담는 곳은 물리 메모리의 frame이다. page는 주소 공간을 나눈 칸이다. 크기(보통 4KiB)도 함께 말한다. (2) "page table은 프로세스가 가진 page들의 표다." 무엇을 무엇으로 바꾸는지가 빠졌다. "가상 page 번호를 물리 frame 번호로 바꾸는 표"라고 말해야 정의가 된다.

    생각해 볼 질문page 크기를 4KiB보다 훨씬 크게 하면 무엇을 얻고 무엇을 잃을까? 작은 프로세스가 많은 서버와 큰 프로세스 하나가 RAM을 다 쓰는 서버에서 답이 같을까?

    직접 확인 
    getconf PAGESIZE                         # page 크기 (bytes)
grep -E 'PageTables|Hugepagesize' /proc/meminfo   # page table이 쓰는 RAM, huge page 크기
cat /sys/kernel/mm/transparent_hugepage/enabled  # THP 설정

    page fault

    왜 알아야 하나page fault는 대부분 오류가 아니다. 리눅스는 메모리를 "처음 건드릴 때" 붙인다. 그 방법이 page fault다. 그래서 page fault의 종류를 보면 메모리가 부족한지, 디스크를 기다리는지를 알 수 있다.

    • 정의: MMU가 가상 주소를 frame으로 바꾸지 못할 때 CPU가 일으키는 예외다. 커널이 이어받아 처리한다.
    • 생기는 조건: page table 항목의 present bit가 0이다. 또는 권한이 맞지 않는다(읽기 전용 page에 쓰기 등).
    • 커널의 처리: 먼저 그 주소를 담은 VMA를 찾는다. 그다음 셋 중 하나다.
      • minor fault: 데이터가 이미 RAM에 있다(page cache 등). page table에 연결만 한다. 빠르다.
      • major fault: 데이터가 디스크에 있다(파일, swap). 디스크에서 frame으로 읽은 뒤 연결한다. 그동안 그 스레드는 멈춘다. 느리다.
      • 잘못된 접근: 어떤 VMA에도 없는 주소이거나, VMA의 권한을 어긴다. 프로세스에 SIGSEGV를 보낸다(segmentation fault).
    • 정상 동작에 쓰는 곳: malloc이나 mmap은 주소만 준다. RAM은 첫 접근의 page fault 때 붙는다(지연 할당). copy-on-write(fork 뒤 쓰기)도 page fault로 동작한다.
    자주 하는 오해"page를 frame으로 바꿨는데 이상한 것이 있으면 page fault다." 순서가 반대다. 변환이 끝난 뒤가 아니라, 변환을 할 수 없을 때 생긴다. 그리고 "이상한 것"이 아닌 경우가 대부분이다. 첫 접근, 파일 읽기, copy-on-write가 모두 page fault로 처리된다.

    생각해 볼 질문서버의 major fault 수가 갑자기 늘었다. 원인 후보를 두 가지 이상 들어 보자. 각각을 어떤 숫자로 구별할 수 있을까?

    직접 확인 
    ps -o pid,min_flt,maj_flt,cmd -p <pid>   # 프로세스의 minor, major fault 수
vmstat 1                                  # si, so = swap in/out
sar -B 1                                  # fault/s, majflt/s (sysstat)

    VMA와 vm.max_map_count

    왜 알아야 하나파일을 많이 연결(mmap)하거나 스레드가 많은 프로그램은 VMA가 많다. VMA 수에는 커널 상한이 있다. 상한을 넘으면 메모리 할당이 실패하고, 보통 프로세스가 죽는다.

    • 정의: VMA(virtual memory area, 커널의 vm_area_struct)는 가상 주소 공간에서 권한과 연결 대상이 같은 연속 구간이다.
    • VMA 하나가 가진 정보: 시작 주소와 끝 주소, 권한(r/w/x), 공유(shared)인지 혼자 쓰는지(private), 연결 대상(어느 파일의 어느 위치, 또는 파일 없는 익명 메모리).
    • VMA는 규칙이다: "이 구간에는 무엇이 있어야 하나"를 적는다. 실제 연결(page table 항목)은 나중에 page fault 때 이 규칙대로 채운다. VMA 목록에 없는 주소에 접근하면 SIGSEGV다.
    • 메모리 배치 (x86-64, 낮은 주소부터)
      • 코드(r-x), 읽기 전용 데이터(r--), 쓰기 데이터(rw-): 실행 파일에서 각각 VMA 하나씩
      • 힙: 연속 구간 하나. 끝(brk)을 밀어 높은 주소 쪽으로 자란다. 끝에서만 줄일 수 있다.
      • mmap 영역: 공유 라이브러리, mmap한 파일, 큰 메모리 할당, 스레드마다의 스택. 구간마다 독립된 VMA라 하나씩 만들고 하나씩 돌려준다(munmap).
      • 스택(메인 스레드): 낮은 주소 쪽으로 자란다.
    • VMA가 늘어나는 경우: mmap 한 번에 보통 하나. 공유 라이브러리 하나에 4~5개. 스레드 하나에 스택과 guard page로 2개. 한 구간의 일부만 권한을 바꾸면(mprotect) 쪼개진다. 이웃한 같은 속성의 구간은 합쳐진다.
    • vm.max_map_count: 프로세스 하나가 가질 수 있는 VMA 수의 상한이다. Ubuntu 기본값은 65,530이다. 넘으면 mmap이 ENOMEM으로 실패한다. 이 값은 VMA를 만들지 않는다. 몇 개가 생기는지는 프로그램이 정한다.
    • 적용 범위: 커널 전체의 값이다(sysctl). 모든 프로세스에 같은 상한이 걸린다. 프로세스별로 줄 방법이 없다(sysctl과 unit의 차이).
    자주 하는 오해(1) "VMA는 가상 주소를 용도별로 나눈 구간이다." 나누는 기준은 용도가 아니라 권한과 연결 대상이다. 그래서 용도가 같은 파일 수천 개를 따로 연결하면 VMA도 수천 개다. (2) "이 설정이 VMA 수를 늘린다." 늘리는 것은 개수의 상한이다. (3) "힙은 아래로, 스택은 위로 자란다." 위아래는 그림을 그리는 방향에 따라 바뀐다. 주소로 말한다: 힙은 높은 주소 쪽, 스택은 낮은 주소 쪽이다.

    생각해 볼 질문상한을 아주 크게 올리면 어떤 비용이 생길까? 반대로 프로그램이 지금 VMA를 몇 개 쓰는지 모르는 채로 값을 정하면 어떤 위험이 있을까?

    직접 확인 
    cat /proc/<pid>/maps | head       # 한 줄 = VMA 하나: 주소 구간, 권한, offset, 파일
wc -l /proc/<pid>/maps            # 그 프로세스의 지금 VMA 수
sysctl vm.max_map_count            # 상한
pmap -x <pid> | tail -1           # 구간별 크기의 합

    mmap

    왜 알아야 하나큰 파일을 다루는 프로그램은 read() 대신 mmap을 쓰기도 한다. 어느 쪽이냐에 따라 RAM 사용량의 모양, VMA 수, I/O 지연이 나타나는 자리가 달라진다.

    • 한 줄 정의: 디스크의 파일(또는 익명 메모리)을 프로세스의 주소 공간에 연결해서, 메모리처럼 주소로 읽고 쓰게 하는 시스템 호출이다.
    • 부를 때 커널이 하는 일
      1. mmap 영역에 빈 주소 구간을 잡는다. VMA가 하나 생긴다.
      2. "이 구간 = 이 파일의 이 위치부터 이 길이"라고 기록한다.
      3. 아무것도 읽지 않고 주소만 돌려준다.
    • 실제 읽기: 그 주소를 처음 건드릴 때 page fault가 난다. 커널은 그 page(4KiB)만 디스크에서 page cache로 읽고, 내 page table 항목이 그 page cache의 frame을 가리키게 한다. 그래서 큰 파일을 연결해도 건드린 page만 RAM을 쓴다.
    • read()와의 차이
      • read(): 디스크 → page cache → 내 버퍼로 복사. 부를 때마다 커널에 들어간다.
      • mmap: 디스크 → page cache. 내 주소가 그 frame을 바로 가리킨다. 복사가 없고, 연결한 뒤에는 시스템 호출 없이 읽는다.
    • 그래도 read()가 기본인 이유: 받은 데이터가 그 순간의 내 사본이 된다. 아무 주소, 아무 크기의 버퍼에 받는다(mmap은 page 경계와 page 단위만 된다). 소켓, 파이프처럼 page cache가 없는 대상도 같은 방식으로 읽는다. 작은 I/O는 복사가 page table 작업보다 싸다. 디스크 오류가 반환값으로 온다(mmap은 SIGBUS 신호로 온다).
    • page fault 때 일어나는 일: 커널이 fault 난 주소의 VMA를 찾아 "이 파일의 몇 번째 page"인지 안다. 그 page가 page cache에 없으면 디스크에서 새 frame으로 읽고 page cache에 등록한다. 그다음 프로세스의 page table에 "이 가상 page → 그 page cache frame"을 써 넣고, 멈췄던 명령을 다시 실행한다. 같은 파일을 mmap한 다른 프로세스도 같은 frame을 가리킨다.
    • MAP_SHARED와 MAP_PRIVATE: SHARED는 쓴 내용이 파일과 다른 프로세스에 보인다. PRIVATE는 쓸 때 그 page만 내 것으로 복사된다(copy-on-write).
    • 파일 없는 mmap: 익명 메모리다. glibc의 malloc은 기본으로 128KiB 이상의 요청을 힙이 아니라 mmap으로 받는다. 그래야 free 때 바로 OS에 돌려준다.
    자주 하는 오해(1) "mmap은 가상 주소를 실제 메모리로 옮기는 일이다." 주소 변환은 MMU가 page table로 한다. mmap은 VMA를 만들 뿐이다. (2) "mmap은 디스크의 데이터가 커널을 거치지 않고 메모리에 바로 연결되는 것이다." 디스크에서 읽는 일은 page fault 때 커널이 한다. 없어지는 것은 커널이 아니라 복사 한 번과 접근마다의 시스템 호출이다. (3) "mmap은 페이지 변환 없이 파일을 통째로 메모리에 가져다 놓는다." 두 곳이 틀렸다. 변환은 모든 메모리 접근에서 항상 일어난다. mmap이 없애는 것은 복사다. 그리고 통째로가 아니라 건드린 page만 나중에 읽는다.

    생각해 볼 질문프로그램이 수십만 개의 파일을 하나씩 mmap한다. 어떤 커널 한도에 먼저 닿을까? 같은 일을 read()나 비동기 I/O로 바꾸면 그 한도 대신 무엇을 신경 써야 할까?

    직접 확인 
    grep -v ' 0 *$' /proc/<pid>/maps | head   # 파일과 연결된 VMA
strace -e trace=mmap,munmap -f <명령> 2>&1 | head
free -h                                    # buff/cache = page cache

    커널 메모리와 커널 모드

    왜 알아야 하나열린 파일 정보, 소켓 버퍼, page cache, page table은 모두 커널 메모리에 있다. 프로세스는 이것을 직접 만질 수 없다. 그래서 fd 같은 "번호"로 커널에 일을 시킨다. 이 경계를 알아야 fd와 시스템 호출의 설명이 이어진다.

    • 커널 메모리의 정의: 커널이 자기 코드와 자료구조를 두는 RAM이다. 커널도 부팅 때 RAM에 올라온 코드와 데이터라서 둘 곳이 필요하다.
    • 들어 있는 것: 프로세스 정보(task_struct), 열린 파일(struct file), inode와 dentry 캐시, page cache, 소켓 버퍼, page table.
    • 주소 공간의 위쪽 절반 (x86-64)
      • 아래 절반(0x0000… ~ 0x00007fff…): 사용자 공간. 코드, 힙, mmap 영역, 스택.
      • 위 절반(0xffff8000… ~): 커널 공간. 모든 프로세스의 page table에 같은 커널이 연결된다.
      • 커널 쪽 page table 항목에는 "커널 모드에서만 접근" 표시가 있다. 사용자 모드에서 접근하면 fault다. Meltdown 이후에는 사용자 모드일 때 커널의 대부분을 아예 연결하지 않는다(KPTI).
    • 커널은 프로세스가 아니다: 따로 도는 프로세스 없이, 이 두 경우에 실행되는 코드다.
      • 시스템 호출: 프로세스가 open, read 등을 부르면 CPU가 커널 모드로 바뀐다. 커널 코드가 그 프로세스의 이름으로 실행된다. 커널용 스택은 스레드마다 따로 있다. 끝나면 사용자 모드로 돌아온다.
      • 인터럽트: 패킷 도착, 디스크 완료 같은 하드웨어 신호가 오면 커널 코드가 실행된다.
    • 예외: 커널 스레드: ps -ef에서 [kworker/…], [ksoftirqd/0]처럼 대괄호로 보인다. 커널 안에서만 도는 작업이고 사용자 공간이 없다.
    자주 하는 오해"커널은 프로세스가 아니니 자기 메모리가 없다." 커널도 코드와 자료구조를 RAM에 둔다. 그 메모리가 모든 프로세스의 주소 공간 위쪽에 연결되어 있고, 커널 모드에서만 접근할 수 있을 뿐이다.

    생각해 볼 질문프로세스의 메모리 사용량(RSS)은 작은데 서버의 남은 메모리가 계속 줄어든다. 커널 메모리 중 어디를 먼저 볼까?

    직접 확인 
    grep -E 'Slab|SReclaimable|KernelStack|PageTables' /proc/meminfo
sudo slabtop -o | head -15        # 커널 자료구조별 메모리 (dentry, inode_cache 등)
ps -ef | grep '\[' | head          # 커널 스레드

    메모리 고정(pin)과 memlock 한도

    왜 알아야 하나어떤 I/O는 장치가 프로세스의 메모리에 직접 쓴다. 그동안 그 메모리가 움직이면 다른 데이터를 덮어쓴다. 그래서 커널은 메모리를 고정한다. 고정한 메모리는 시스템이 회수할 수 없어서, 그 양에 한도가 있다.

    • 고정(pin, lock)의 정의: page의 frame을 바꾸지 못하게 하는 것이다. 고정한 page는 swap으로 나가지 않고, 다른 frame으로 옮겨지지도 않는다.
    • 왜 필요한가: 장치는 물리 주소만 안다
      • 디스크와 NIC는 CPU를 거치지 않고 메모리에 데이터를 직접 쓴다(DMA). 이때 물리 주소를 쓴다. 가상 주소와 page table을 모른다.
      • 프로세스의 page는 가만히 있지 않다. 아직 frame이 없을 수 있고, swap으로 나갈 수 있고, 커널이 다른 frame으로 옮길 수 있고(메모리 정리, NUMA), 프로세스가 munmap으로 풀 수도 있다.
      • I/O 도중에 이런 일이 생기면 장치는 이미 받은 옛 물리 주소에 쓴다.
    • 보통의 read()는 고정이 필요 없다: 장치는 커널이 관리하는 page cache에 쓴다. 그다음 커널이 내 버퍼로 복사한다.
    • 고정이 필요한 경우: 장치가 내 버퍼로 바로 쓰는 I/O다. 예: direct I/O(O_DIRECT, page cache를 건너뜀), io_uring의 등록 버퍼, RDMA.
    • I/O마다 하는 일: 버퍼의 page를 모두 찾아 frame을 붙인다 → 고정한다 → 물리 주소 목록을 장치에 넘긴다 → 끝나면 푼다. 1MiB 버퍼면 page 256개를 I/O마다 이렇게 한다. 이것이 반복 비용이다.
    • 등록 버퍼: 처음에 한 번 고정해 두고 계속 같은 버퍼를 쓴다. 반복 비용이 없어진다. 대신 그 메모리는 회수도 swap도 안 된다.
    • memlock 한도(RLIMIT_MEMLOCK): 프로세스 하나가 고정할 수 있는 메모리의 최대 bytes다. 한 프로세스가 RAM을 다 잠그지 못하게 막는다. systemd에서는 LimitMEMLOCK=, 셸에서는 ulimit -l이다. 배포판 기본은 수 MiB 수준이다.
    • 버퍼는 어디에 있나: 프로세스의 사용자 메모리다(대개 mmap 영역의 익명 메모리). 주인은 프로세스이고, 고정을 커널이 잡고 있다. 그래서 그 프로세스의 memlock 한도에서 빠진다. 커널 메모리에 있는 소켓 버퍼와 다르다.
    자주 하는 오해(1) "memlock은 page cache의 영향을 받지 않는 메모리의 한도다." page cache와 관계없다. swap이나 이동으로 RAM에서 밀려나지 않게 고정할 수 있는 양이다. (2) "mmap한 메모리가 swap되면 안 되니까 고정한다." mmap한 파일의 page는 밀려나도 된다. 원본이 디스크에 있어서 다시 읽으면 된다. 고정이 필요한 것은 장치가 직접 쓰는 I/O 버퍼다. (3) "고정했다 풀려면 시스템 호출이 필요하다." 고정은 I/O를 처리하는 커널 안에서 함께 일어난다. 비용은 시스템 호출 수가 아니라 page를 하나하나 찾아 고정하고 푸는 작업이다.

    생각해 볼 질문프로그램이 memlock 한도가 모자랄 때 실패하지 않고 보통 방식으로 I/O를 한다고 하자. 이 문제는 어떻게 발견할 수 있을까? 켜질 때의 검사와 실행 중의 지표 중 무엇이 더 확실할까?

    직접 확인 
    ulimit -l                                   # 이 셸의 memlock 한도 (KiB)
grep -i 'locked memory' /proc/<pid>/limits  # 프로세스의 한도
grep -E 'VmLck|VmPin' /proc/<pid>/status    # 지금 잠근 양, 고정한 양
systemctl show <서비스> -p LimitMEMLOCK

    익명 페이지와 파일 페이지

    왜 알아야 하나RAM이 모자랄 때 커널이 하는 일은 page의 종류에 따라 다르다. 그래서 "RAM에 올라 있다"는 같은 말도, 어떤 종류냐에 따라 "버릴 수 있는 메모리"와 "버릴 수 없는 메모리"로 나뉜다.

    • 익명 페이지(anonymous): 뒤에 파일이 없는 메모리다. 힙, 스택, MAP_ANONYMOUS로 받은 메모리가 여기에 든다. 메모리 할당기(glibc malloc, jemalloc)도 내부에서 mmap을 부르지만, 파일 없이 부르므로 결과는 익명 페이지다.
    • 파일 페이지(file-backed): 뒤에 파일이 있는 메모리다. page cache와, 파일을 mmap한 구간이 여기에 든다.
    • RAM이 모자랄 때 커널의 처리
      • 파일 페이지, 고치지 않음(clean): 그냥 버린다. 필요하면 파일에서 다시 읽는다.
      • 파일 페이지, 고침(dirty): 먼저 파일에 쓴(writeback) 뒤 버린다.
      • 익명 페이지: 다시 읽을 파일이 없다. swap이 있으면 swap으로 내보낸다. swap이 없거나 모자라면 회수할 수 없다. 끝내 모자라면 OOM killer가 프로세스를 죽인다.
    • 운영에서 보는 뜻: 프로그램이 큰 자료구조(색인, 캐시)를 힙에 두면, 그 크기만큼 RAM을 "돌려받을 수 없는 몫"으로 잡는다. RAM 계획은 이 몫이 RAM 안에 들어가는지로 판단한다. 남은 RAM은 놀지 않고 page cache(파일 페이지)로 쓰인다.
    • 프로세스의 RSS도 둘로 나뉜다: /proc/<pid>/status의 RssAnon(익명)과 RssFile(파일). 같은 RSS라도 RssFile이 크면 커널이 회수할 여지가 크다.
    자주 하는 오해"RAM 위에 올린다 = 프로세스가 파일을 mmap해 둔 상태다." 힙에 할당한 자료구조는 파일과 연결되지 않은 익명 메모리다. 할당기가 mmap을 쓰더라도 파일 없이 쓴다. 파일을 mmap한 것과는 RAM이 모자랄 때의 처리가 다르다.

    생각해 볼 질문swap을 끈 서버에서 익명 메모리가 RAM에 거의 닿았다. 그 뒤 디스크 읽기 성능은 어떻게 바뀔까? OOM이 나기 전에 어떤 신호가 먼저 보일까?

    직접 확인 
    grep -E 'RssAnon|RssFile|RssShmem|VmSwap' /proc/<pid>/status
grep -E 'AnonPages|^Cached|Dirty|SwapTotal|SwapFree' /proc/meminfo
free -h                          # available = 지금 회수할 수 있는 몫을 더한 어림
journalctl -k | grep -i 'out of memory'

    fd와 커널 한도 FD · RLIMIT · SOCKET

    프로세스가 커널의 자원을 어떻게 가리키고, 그 양을 누가 어디서 제한하나.

    fd (file descriptor)

    왜 알아야 하나열린 파일 수 한도, "지웠는데 공간이 안 풀림", 로그 회전 뒤에도 옛 파일에 쓰는 문제가 모두 fd의 구조에서 나온다.

    • 정의: 프로세스가 연 파일 하나하나에 커널이 붙여 주는 정수 번호다.
    • 왜 번호인가: 열린 파일의 실제 정보는 커널 메모리에 있다. 프로세스는 그것을 직접 만질 수 없다. 그래서 커널은 번호만 주고, 프로세스는 그 번호로 read, write를 요청한다.
    • 규칙
      • 번호는 프로세스마다 따로다. 프로세스마다 자기 fd 표가 있다. A의 3번과 B의 3번은 다른 파일일 수 있다.
      • 0, 1, 2는 표준 입력, 출력, 에러다. 부모(셸, systemd)에게서 물려받는다. 그래서 처음 연 파일은 보통 3번이다.
      • open()은 비어 있는 가장 작은 번호를 준다.
      • 파일만이 아니다. 소켓, 파이프, 터미널도 fd다.
    • 세 층의 구조
      1. fd 표의 칸(번호): 프로세스마다
      2. 열린 파일(open file description, 커널의 struct file): open() 한 번마다 하나. 읽은 위치(offset)와 열기 모드(읽기, 쓰기)를 가진다.
      3. inode: 파일 그 자체. 디스크의 inode를 커널 메모리에 올린 것이다. 소켓이면 커널 안의 소켓 객체다.
    • 층에서 나오는 동작
      • 같은 파일을 두 번 open(): fd 2개 → 열린 파일 2개 → inode 1개. 읽는 위치가 따로다.
      • dup() 또는 fork(): fd 2개 → 열린 파일 1개. 읽는 위치를 같이 쓴다. 자식은 부모의 fd 표를 복사한다.
      • fd는 이름이 아니라 inode를 가리킨다. 경로는 open() 때 inode를 찾는 데만 쓴다. 그래서 파일 이름을 바꿔도 그 fd로 계속 같은 파일에 쓴다. 새 파일에 쓰게 하려면 다시 open()해야 한다.
      • rm으로 link count가 0이 되어도 fd가 남아 있으면 inode가 살아 있다. 마지막 fd가 닫혀야 공간이 풀린다(inode).
    자주 하는 오해(1) "fd는 커널이 프로세스에게 주는 이름표다." 이름표라고 하면 파일 이름처럼 들린다. fd는 이름이 아니라 정수 번호다. (2) "열린 파일 정보에 권한이 있다." 파일의 권한(rwx)은 inode에 있고, open() 때 한 번 검사한다. 열린 파일에 남는 것은 열기 모드(이 fd로 읽기만 되나, 쓰기도 되나)다. (3) 정의를 말할 때는 "무엇"(정수 번호)을 먼저, "왜"(정보가 커널 메모리에 있다)를 뒤에 둔다.

    생각해 볼 질문로그 파일을 회전(이름 바꾸기)했는데 프로그램이 계속 옛 파일에 쓴다. fd의 세 층 중 어디 때문일까? 프로그램을 다시 켜지 않고 해결하는 방법은 무엇이 있을까?

    직접 확인 
    ls -l /proc/<pid>/fd           # 번호마다 무엇을 가리키나 (파일, socket:[…], pipe:[…])
cat /proc/<pid>/fdinfo/3       # 3번의 offset(pos)과 열기 모드(flags)
ls /proc/<pid>/fd | wc -l      # 지금 연 fd 수
lsof -p <pid> | head

    열린 파일 한도의 세 층

    왜 알아야 하나파일과 소켓을 많이 여는 프로그램은 기본 한도로 켜자마자 "Too many open files"로 실패한다. 한도는 여러 층이라, 한 층만 올리면 다른 층에 막힌다.

    • 세는 것: fd의 수다. 파일, 소켓, 파이프가 모두 하나씩이다.
    • 프로세스 하나의 층 (위가 아래를 넘을 수 없다)
      1. fs.nr_open (sysctl, 커널 전체): 프로세스별 한도를 올릴 수 있는 천장이다. 리눅스 기본값은 1,048,576이다.
      2. hard limit: 이 프로세스의 상한이다. root 권한이 없으면 올릴 수 없다.
      3. soft limit: 지금 적용 중인 한도다. 프로세스가 hard limit까지 스스로 올릴 수 있다. ulimit -n이 보여 준다.
    • 시스템 전체의 층: fs.file-max는 프로세스별이 아니라 시스템 전체의 열린 파일 총합의 상한이다. 다른 값이다.
    • systemd에서: LimitNOFILE=이 그 서비스의 soft와 hard limit을 정한다. systemd 서비스의 기본 soft limit은 1,024다. 값이 fs.nr_open보다 크면 한도를 걸지 못해서 서비스가 켜지지 않는다.
    • 에러로 구별한다: 프로세스 한도에 닿으면 EMFILE, 시스템 전체 한도에 닿으면 ENFILE이다.
    • 값을 정하는 방법: 문서의 값을 그대로 쓰기 전에, 프로그램이 동시에 여는 파일 수와 소켓 수를 세어 본다. 그리고 그 층의 기본값과 비교한다. 기본값이 이미 더 크면 그 줄은 값을 올리지 않는다.
    자주 하는 오해(1) "fs.nr_open은 열린 파일 수를 커널에서 제한한다." 이렇게 말하면 시스템 전체의 총합(fs.file-max)처럼 들린다. 정확히는 "프로세스별 한도를 올릴 수 있는 천장"이다. (2) "fs.nr_open을 쓰면 값이 올라간다." 기본값이 이미 더 크면 오히려 천장을 낮춘다. 값을 쓰기 전에 기본값과 비교한다.

    생각해 볼 질문한도를 천장까지 아주 크게 올려 두면 무엇이 나빠질 수 있을까? fd를 닫지 않고 새는 프로그램이라면, 한도가 작을 때와 클 때 장애는 각각 언제 어떻게 보일까?

    직접 확인 
    sysctl fs.nr_open fs.file-max
cat /proc/sys/fs/file-nr                 # 시스템 전체: 할당된 수, (사용 안 함), 상한
grep 'open files' /proc/<pid>/limits     # 그 프로세스의 soft, hard
systemctl show <서비스> -p LimitNOFILE -p LimitNOFILESoft
prlimit --pid <pid> --nofile

    적용 범위시스템 전체의 모든 프로세스그 서비스와 자식 프로세스
    방법커널 값을 바로 바꾼다systemd가 켤 때 setrlimit, cgroup, 사용자 전환 등으로 건다
    언제 적용되나sysctl --system 즉시서비스를 다시 켤 때(daemon-reload + restart)

    • 나누는 원칙: 서비스 하나에만 줄 수 있는 값이면 unit에 넣는다. 다른 프로세스에 영향이 없다(최소 범위). 프로세스별로 줄 방법이 없는 값만 sysctl로 바꾼다.
    • sysctl을 함께 고르는 이유: vm.*, net.core.* 같은 값은 프로세스별 값이 없다. 그래서 컨테이너 안에서도 바꾸지 못하고 호스트에서 정한다(Docker가 아닌 systemd).

    소켓 버퍼: rmem_max와 wmem_max

    왜 알아야 하나UDP는 받는 쪽이 느려도 보내는 쪽이 속도를 줄이지 않는다. 그래서 받기 버퍼가 차면 커널이 새 패킷을 버린다. 패킷이 몰려서 오는 프로그램은 이 버퍼 크기에 따라 데이터를 잃는다.

    • 받기 버퍼: 패킷이 NIC에 도착하면 커널이 그것을 소켓의 받기 큐에 넣는다. 프로세스는 나중에 recv()(여러 개를 한꺼번에: recvmmsg)로 꺼낸다. 받기 버퍼는 꺼내 가기 전까지 쌓아 두는 곳이다.
    • 보내기 버퍼: send()를 부르면 데이터가 커널의 보내기 큐로 복사된다. 커널과 NIC가 그 큐에서 꺼내 내보낸다.
    • net.core.rmem_max, wmem_max: 프로세스가 setsockopt(SO_RCVBUF / SO_SNDBUF)로 요청할 수 있는 버퍼 크기의 상한(bytes)이다. 더 크게 요청해도 이 값으로 잘린다. Ubuntu 기본값은 212,992 bytes(208KiB)다.
    • 상한일 뿐이다: 실제 크기는 프로그램이 요청해서 정한다. 커널은 실제로 쌓인 만큼만 메모리를 쓴다. 요청하지 않은 소켓은 rmem_default를 쓴다. 그래서 값을 올려도 다른 프로그램은 바뀌지 않는다.
    • UDP 전용 값이 아니다: 모든 소켓에 적용된다. 다만 흐름 제어가 없는 UDP(와 그 위의 QUIC)에서 문제가 크게 드러난다.
    • 버퍼가 차면
      • 받기: 들어오는 속도 > 꺼내는 속도가 이어지면 큐가 찬다. 그 뒤 들어온 패킷은 커널이 버린다. 큐가 크면 프로세스가 잠깐 늦어도 그동안의 몰림을 담는다.
      • 보내기: blocking 소켓이면 send()가 자리가 날 때까지 멈춘다. non-blocking이면 바로 실패한다(EAGAIN). 프로그램이 버리거나 다시 시도한다.
    • 더 아래 단계: NIC에도 받기/보내기 링이 있다(ethtool -g). 패킷이 너무 빨리 와서 그 링이 차면 소켓 버퍼에 닿기 전에 NIC 단계에서 버려진다.
    자주 하는 오해(1) "프로세스가 버퍼에서 한 번에 가져가는 양(수레)의 크기다." 반대다. 가져가기 전까지 쌓아 두는 곳(창고)의 크기다. 한 번에 가져가는 양은 recv()에 넘기는 버퍼 크기와 묶음 수가 정한다. (2) "최대 패킷 저장 개수다." 개수가 아니라 bytes이고, 요청할 수 있는 상한이다.

    생각해 볼 질문받기 버퍼의 상한을 아주 크게 올리면 패킷 버림은 사라질까? 꺼내는 쪽이 계속 느리다면 큰 버퍼는 무엇을 바꾸고 무엇을 바꾸지 못할까?

    직접 확인 
    sysctl net.core.rmem_max net.core.wmem_max net.core.rmem_default
nstat -az UdpRcvbufErrors UdpSndbufErrors   # 버퍼가 차서 버린 수
ss -uamp | head                              # 소켓마다 버퍼 크기(rb, tb)와 쌓인 양
ethtool -S <nic> | grep -i drop              # NIC 단계에서 버린 수

    bind와 0.0.0.0

    왜 알아야 하나서비스가 "어디서 오는 연결을 받는가"는 bind 주소가 정한다. 방화벽 설정 하나에만 기대지 않으려면, bind로 받는 범위를 먼저 좁힐 수 있어야 한다.

    • NIC와 네트워크 인터페이스: NIC(Network Interface Card)는 네트워크로 데이터를 보내고 받는 하드웨어다. 커널은 NIC 하나를 네트워크 인터페이스 하나로 보인다(eth0, enp1s0 등). 하드웨어가 없는 가상 인터페이스도 있다(lo, 브리지). IP 주소는 관리자가 인터페이스에 붙인다. 인터페이스 하나에 주소가 여러 개일 수 있다.
    • bind의 정의: 소켓에 (IP 주소, 포트 번호) 한 쌍을 붙이는 시스템 호출이다. 연결이나 패킷이 오면 커널은 목적지 주소와 포트를 둘 다 보고 받을 소켓을 고른다.
      • 포트: 이 서버의 어느 소켓인가. 프로그램 하나가 소켓을 여러 개 열 수 있다.
      • 주소: 이 서버의 어느 주소로 온 것을 받나.
    bind 주소받는 연결
    127.0.0.1같은 서버 안에서 온 것만(루프백)
    특정 주소 (예: 내부망 192.168.0.5)그 주소로 온 것만
    0.0.0.0 (INADDR_ANY)이 서버의 모든 IPv4 주소로 온 것. 공인 주소가 붙은 인터페이스도 포함한다
    • 같은 포트, 다른 주소: 127.0.0.1:P와 192.168.0.5:P는 다른 소켓으로 따로 bind할 수 있다. 0.0.0.0:P는 둘 다를 덮어서, 이것이 있으면 같은 포트를 다른 주소로 bind하지 못한다.
    • 소켓마다 받는 범위를 다르게 한다: 한 프로그램 안에서도 상대가 다르면 소켓을 나눈다. 예: 블록체인 노드의 P2P 소켓은 인터넷의 다른 노드가 닿아야 해서 모든 주소에서 받는다. 클라이언트용 API 소켓은 쓰는 쪽이 내부망뿐이면 내부망 주소에만 bind한다.
    • 층을 겹친다: 바깥 방화벽, 서버의 방화벽(nftables, ufw), bind 주소는 서로 다른 층이다. bind를 좁혀 두면 방화벽 설정이 실수로 열려도 그 소켓은 밖에서 받지 않는다.
    자주 하는 오해(1) "bind는 포트 번호로 하는 것이다." 주소와 포트 한 쌍이다. (2) "IP 주소는 NIC가 정한다." 주소는 인터페이스에 붙인 것이고, 하나의 인터페이스에 여러 개일 수 있다. (3) "프로그램이 받을 주소를 하나로 좁히면 모든 통신이 좁혀진다." 프로그램이 소켓을 여러 개 쓰면, 소켓마다 bind 주소를 정하는 설정이 따로일 수 있다. 인터넷 쪽 상대가 필요한 소켓까지 내부망으로 좁히면 그 통신이 끊긴다.

    생각해 볼 질문서버에 인터페이스가 공인망과 내부망 두 개 있다. 내부망 주소에만 bind한 API를 같은 서버 안의 다른 프로그램이 127.0.0.1로 부르면 닿을까? 닿게 하려면 무엇을 바꿔야 할까?

    직접 확인 
    ip -br addr                 # 인터페이스와 붙은 주소
ss -ltnp; ss -lunp          # TCP/UDP 소켓의 bind 주소:포트와 프로그램
sudo nft list ruleset | head
curl -sS http://127.0.0.1:<포트>/ ; curl -sS http://<내부망 주소>:<포트>/

    비동기 I/O IO_URING · RING BUFFER

    빠른 장치의 능력을 다 쓰려면 I/O 요청을 어떻게 넘겨야 하나.

    io_uring

    왜 알아야 하나NVMe는 초당 수십만 번 이상의 I/O를 처리한다. 요청을 하나씩 보내고 기다리는 방식으로는 그 능력을 다 쓰지 못한다. io_uring은 이 문제를 풀려고 나왔다. 그리고 memlock 한도, 컨테이너 seccomp 설정과 이어진다.

    • 정의: 리눅스의 비동기 I/O 인터페이스다(커널 5.1, 2019). 많은 I/O 요청을 한꺼번에 커널에 넘기고, 끝난 결과를 나중에 받는다.
    • 보통 read()의 한계
      • I/O 하나 = 시스템 호출 하나 = 사용자 모드와 커널 모드의 전환 한 번.
      • 끝날 때까지 그 스레드가 멈춘다(동기).
      • 그래서 동시에 걸어 둘 수 있는 요청 수가 스레드 수에 묶인다.
    • 구조: 공유 메모리의 큐 두 개 (프로세스와 커널이 같이 보는 메모리를 mmap으로 연결한다)
      1. SQ(submission queue): 프로세스가 요청을 적는다. 예: "fd 5의 offset 0부터 1MiB를 이 버퍼로 읽어라."
      2. 요청을 여러 개 적은 뒤 시스템 호출 한 번(io_uring_enter)으로 한꺼번에 넘긴다. 설정에 따라 이 호출도 없앨 수 있다(커널 쪽 스레드가 SQ를 살핀다).
      3. 커널이 I/O를 처리하는 동안 프로세스는 다른 일을 한다.
      4. CQ(completion queue): 커널이 결과를 적는다. 프로세스가 읽어 간다.
    • 얻는 것: 시스템 호출 수가 크게 준다. 스레드가 기다리며 멈추지 않는다. 한 번에 많은 요청을 걸어 두어서 장치의 여러 큐를 다 쓴다.
    • 등록(registered) 기능
      • 고정 버퍼(fixed buffers): I/O에 쓸 데이터 버퍼를 미리 등록해 한 번 고정한다. I/O마다 고정하고 푸는 일이 없어진다. 고정한 메모리라 memlock 한도 안에서만 등록된다.
      • 고정 파일(fixed files): fd도 미리 등록해서 I/O마다 fd 표를 찾는 일을 줄인다.
    • 단점: 커널의 큰 기능이라 보안 취약점이 많이 나왔다. 그래서 Docker 기본 seccomp 프로필(25.0부터)과 일부 배포판, 일부 클라우드 커널이 io_uring을 막는다.
    자주 하는 오해"고정 메모리는 비동기 I/O를 위한 공용 메모리다." 두 가지가 섞였다. 비동기를 위한 공용 메모리는 요청과 결과를 주고받는 SQ/CQ 링이다. memlock으로 고정하는 것은 실제 데이터를 담는 등록 버퍼다. 그리고 등록 버퍼는 선택 기능이라, 쓰지 않아도 io_uring은 동작한다.

    생각해 볼 질문요청을 한 번에 아주 많이 걸어 두면 장치는 언제나 더 빨라질까? 지연(한 요청이 끝나기까지의 시간)과 처리량(초당 요청 수) 중 무엇이 먼저 나빠질까?

    직접 확인 
    sysctl kernel.io_uring_disabled 2>/dev/null   # 0이면 허용 (6.6 이상 커널)
grep -c io_uring /proc/<pid>/maps             # 프로세스가 링을 연결했나
ls -l /proc/<pid>/fd | grep io_uring
fio --name=t --ioengine=io_uring --rw=randread --bs=4k --iodepth=64 --size=1G --direct=1

    링 버퍼와 FIFO 큐

    왜 알아야 하나io_uring의 SQ/CQ, NIC의 받기/보내기 큐, 커널 로그(dmesg)가 모두 링 버퍼다. 링 버퍼가 가득 찼을 때 무엇을 하느냐가 그 장치의 장애 모양을 정한다.

    • 정의: 크기가 고정된 배열을, 끝에 닿으면 처음으로 돌아가게 써서 FIFO 큐로 쓰는 자료구조다.
    • 구조: 배열 하나와 번호 두 개다.
      • tail: 넣는 쪽이 다음에 쓸 자리. 넣으면 1 올린다.
      • head: 꺼내는 쪽이 다음에 읽을 자리. 꺼내면 1 올린다.
      • 칸 번호 = 번호 % 칸 수. 마지막 칸 다음은 0번 칸이다.
      • 비었음: head == tail. 가득 참: tail − head == 칸 수.
    • FIFO와의 관계: FIFO는 동작 규칙(먼저 넣은 것이 먼저 나간다)이다. 링 버퍼는 그 규칙을 만드는 구현 방법 중 하나다. 그래서 링 버퍼도 FIFO 큐다.
    FIFO를 만드는 방법꺼낼 때크기메모리 할당
    배열 + 나머지를 앞으로 당김데이터를 모두 한 칸씩 옮긴다(느림)고정없음
    연결 리스트앞 노드만 뗀다(빠름)제한 없음넣을 때마다
    링 버퍼head만 1 올린다(빠름)고정처음 한 번
    • 얻는 것: 넣고 뺄 때 할당도, 데이터 이동도 없다. 넣는 쪽과 꺼내는 쪽이 하나씩이면 각자 자기 번호만 고쳐서 잠금(lock) 없이 동시에 쓴다. 메모리 자리가 고정이라 다른 주체(커널, NIC)와 공유하기 쉽다.
    • 버리는 것: 크기가 고정이다. 가득 차면 더 넣을 수 없다. 그때 하는 일이 쓰는 곳마다 다르다.
      • 기다린다: io_uring은 요청 제출을 미룬다.
      • 버린다: NIC는 새 패킷을 버린다.
      • 덮어쓴다: dmesg는 옛 로그를 새 로그로 덮는다.
    자주 하는 오해"링 버퍼와 FIFO 큐는 다른 것이다." 비교의 층이 다르다. FIFO는 규칙이고 링 버퍼는 구현이다. 비교해야 할 상대는 FIFO를 만드는 다른 구현(당기는 배열, 연결 리스트)이다.

    생각해 볼 질문넣는 쪽이 둘 이상이면 "자기 번호만 고친다"는 성질이 깨진다. 왜 깨질까? 그러면 무엇을 더해야 할까?

    직접 확인 
    ethtool -g <nic>         # NIC 링의 최대 크기와 지금 크기
dmesg | head -3          # 가장 오래 남은 커널 로그 (앞쪽은 이미 덮였을 수 있다)
journalctl -k -b | head -3

    서버에 무엇을 깔고, 노드를 어떻게 돌리나.

    서버 OS: Ubuntu LTS와 Arch

    왜 알아야 하나서버가 원하는 것은 "바뀌지 않는 것"이다. 같은 설정이 오래 같은 결과를 내야 하고, 서버 수십 대를 같은 상태로 맞출 수 있어야 한다. 배포판을 고르는 기준이 여기서 나온다.

    • Arch: rolling release다. 패키지가 계속 최신으로 바뀐다. 그래서 어제 되던 것이 업데이트 뒤 깨질 수 있다. 개인 PC나 리눅스를 깊게 배우는 용도에 맞다.
    • Ubuntu LTS: 2년마다 나온다. 한 버전을 5년 동안 같은 주 버전으로 유지하고 보안 패치를 준다. 서버에서 가장 흔하다. 블록체인 클라이언트의 설치 문서도 Ubuntu를 기준으로 쓴 것이 많다.
    • 서버에서 많이 쓰는 다른 배포판: Debian, RHEL 계열(Rocky Linux 등).
    • OS를 고정해도 같은 상태가 되지는 않는다. 커널 버전, 패키지 버전, 커널 값(sysctl), 파일시스템을 만든 옵션도 같아야 한다.

    생각해 볼 질문LTS를 쓰는데도 새 커널 기능이 필요하면 어떻게 할까? 그 선택은 "바뀌지 않는 것"을 얼마나 깨뜨릴까?

    직접 확인 (Ubuntu에서 기본으로 쓰는 명령) 
    cat /etc/os-release; uname -r           # 배포판 버전, 커널 버전
systemctl status <서비스>; journalctl -u <서비스> -f
lsblk; df -h; findmnt                    # 디스크
ss -tulpn; ip -br addr                   # 열린 포트, 주소
free -h; uptime                          # 메모리, load average

    연결: Docker가 아닌 systemd파일시스템이란

    노드를 Docker가 아닌 systemd로 돌리는 이유

    왜 알아야 하나둘은 반대말이 아니다. Docker 데몬도 systemd가 켠다. 질문의 뜻은 "노드 프로그램을 호스트 프로세스로 바로 돌리나, 컨테이너 안에서 돌리나"다. 답은 "컨테이너가 주는 것"과 "그 대가"를 이 경우에 대어 보면 나온다.

    • 컨테이너가 주는 것: 의존성을 묶어 어디서나 같은 환경, 한 서버 안의 여러 서비스를 나누기(namespace로 보이는 것을 나누고, cgroup으로 쓰는 양을 나눔), 같은 이미지로 다시 만들기.
    • 이 경우에 얻는 것이 작은 이유: 노드 클라이언트는 보통 바이너리 하나이고, 서버 한 대를 혼자 쓴다. 나눌 다른 서비스가 없다. 대신 dockerd라는 의존성(장애 지점)이 하나 는다.
    • 결국 호스트 설정이 필요해서, 격리의 뜻이 사라진다
      • 네트워크: P2P 노드는 포트를 범위로 많이 쓰고, 자기 공인 주소와 포트를 다른 노드에 알린다. 기본 bridge 네트워크(NAT)에서는 범위를 모두 매핑해야 하고, 알리는 주소가 틀어지기 쉽다. 그래서 사실상 --network host를 쓴다.
      • 커널 값: vm.max_map_count 같은 vm.* 값은 커널 전체의 값이다. 컨테이너 안에서 바꾸지 못하고 호스트에서 정한다.
      • 시스템 콜: Docker 25.0부터 기본 seccomp 프로필은 io_uring 시스템 콜을 허용하지 않는다(moby 기본 프로필). io_uring을 쓰는 프로그램이면 프로필을 풀어야 한다.
    • systemd만으로 필요한 것을 한다: 죽으면 다시 켜기(Restart=), 부팅 때 켜기(WantedBy= + enable), 순서(After=network-online.target, RequiresMountsFor=), 프로세스 한도(LimitNOFILE=, LimitMEMLOCK=), 자원 한도(MemoryMax=, CPUQuota=: systemd 서비스도 cgroup 안에서 돈다), 로그(journald).
    • 근거로 쓸 수 있는 문서: Solana 클라이언트(Agave)의 validator 요구사항 문서는 mainnet에서 Docker로 돌리는 것을 권하지 않는다.
    자주 하는 오해"Docker의 장점은 없고, 네트워크를 한 번 더 관리해야 한다"는 방향은 맞지만 막연하다. (1) 장점이 왜 없는지(나눌 서비스가 없다)를 말한다. (2) 네트워크의 무엇이 문제인지(포트 범위, 알리는 주소, NAT)를 말한다. (3) "systemd인 이유"(systemd가 주는 것)를 함께 말한다. 순서는 근거(문서) → 얻는 것이 없는 이유 → 비용 → systemd로 충분함.
    내 환경과 비교홈서버처럼 한 대에 여러 서비스를 올리면 사정이 반대다. 서비스끼리 자원을 뺏지 않게 나누는 것이 목적이라 컨테이너와 cgroup 한도가 쓸모 있다. 노드 서버는 서비스 하나가 서버 전체를 쓴다.

    생각해 볼 질문노드를 쿠버네티스 위에서 돌리는 회사도 있다. 그들은 무엇을 얻으려는 걸까? 그 대신 위의 비용 중 무엇을 받아들이는 걸까?

    직접 확인 
    systemctl status docker            # dockerd도 systemd 서비스다
systemd-cgls --no-pager | head -30 # systemd 서비스마다 cgroup이 있다
systemctl show <서비스> -p MemoryMax -p LimitNOFILE -p Restart
sysctl vm.max_map_count

    리눅스의 부팅 순서

    왜 알아야 하나"재부팅 뒤에도 설정이 남나", "서비스가 디스크보다 먼저 켜지지 않나"는 부팅의 어느 단계에서 무엇이 적용되는지로 답한다.

    1. 펌웨어(UEFI): 하드웨어를 검사(POST)하고 초기화한다. 부팅 디스크의 EFI 시스템 파티션(FAT32)에서 부트로더 파일을 찾아 실행한다. 옛 BIOS 방식은 디스크의 첫 512 bytes(MBR)를 읽는다.
    2. 부트로더(GRUB2): 커널 이미지(vmlinuz)와 initramfs를 메모리에 올린다. 커널 명령줄(root=UUID=… 등)을 넘기고 커널을 실행한다.
    3. 커널: CPU, 메모리(page table), 내장 드라이버를 초기화한다. initramfs를 임시 루트로 붙이고 그 안의 /init을 실행한다.
    4. initramfs: 진짜 루트 파일시스템에 닿는 데 필요한 모듈을 올린다(NVMe, RAID, LVM, 암호화 등). 루트 파일시스템을 마운트하고 그쪽으로 루트를 바꾼다(switch_root).
    5. systemd (PID 1): 첫 사용자 공간 프로세스다. unit의 의존 관계를 보고 목표 target(서버는 보통 multi-user.target)까지 병렬로 켠다. 대략의 순서:
      • sysinit.target: fstab의 마운트, udev, /etc/sysctl.d/ 적용(systemd-sysctl.service)
      • basic.target
      • 네트워크 → network-online.target(누군가 원할 때만)
      • multi-user.target에 걸린 서비스들
    6. 로그인: getty, sshd가 로그인을 받는다.
    • 서비스 설정이 걸리는 자리: sysctl 파일은 5단계 초기에 다시 적용된다. 그래서 재부팅 뒤에도 남는다. WantedBy=multi-user.target + enable이면 5단계에서 자동으로 켜진다. RequiresMountsFor=는 그 경로의 마운트가 끝난 뒤에 켠다.
    자주 하는 오해"systemd는 서비스를 한 줄로 차례차례 켠다." 의존 관계와 순서 조건이 없는 unit은 동시에 켠다. 그래서 순서가 필요한 곳에는 순서 조건을 적어야 한다(Wants=와 After=).

    생각해 볼 질문루트 디스크를 NVMe RAID로 바꿨더니 부팅이 initramfs 단계에서 멈춘다. 어떤 단계의 무엇이 빠졌을 수 있을까?

    직접 확인 
    systemd-analyze                             # 펌웨어, 부트로더, 커널, 사용자 공간 각각의 시간
systemd-analyze critical-chain <서비스>     # 무엇을 기다렸다 켜졌나
systemd-analyze blame | head
journalctl -b -u systemd-sysctl             # 이번 부팅의 sysctl 적용 기록
lsinitramfs /boot/initrd.img-$(uname -r) | grep nvme

    systemd의 Wants=와 After=

    왜 알아야 하나systemd는 "무엇을 함께 켤까"와 "어떤 순서로 켤까"를 따로 다룬다. 둘 중 하나만 쓰면 의도한 순서가 생기지 않는다.

    • Wants=: 함께 켠다(의존). "나를 켤 때 그것도 켜라." 순서는 정하지 않는다. 둘이 동시에 켜질 수 있다.
    • After=: 순서만 정한다. "둘 다 켜진다면, 그것이 끝난 뒤에 나를 켜라." 그것을 켜지는 않는다. 그것이 켜지지 않으면 기다릴 것이 없어서 바로 켠다.
    • Requires=: 강한 의존이다. 그것이 실패하면 나도 켜지지 않는다. Wants=는 약한 의존이라, 그것이 실패해도 나는 켜진다.
    • network.target과 network-online.target
      • network.target: 네트워크 관리 서비스가 시작되었다는 뜻뿐이다. 주소가 붙었다는 보장이 없다.
      • network-online.target: 주소가 실제로 설정된 뒤다. 누군가 원해야만 켜지는 수동 target이다.
    • 그래서 짝으로 쓴다: 네트워크가 준비된 뒤에 켜야 하는 서비스는 Wants=network-online.target(켜게 한다)과 After=network-online.target(끝날 때까지 기다린다)을 함께 쓴다. systemd 문서도 이 짝을 권한다.
    쓴 것network-online.target서비스가 켜지는 때
    Wants=만켜진다기다리지 않고 동시에
    After=만아무도 원하지 않으면 켜지지 않는다기다릴 것이 없어 바로
    둘 다켜진다그것이 끝난 뒤
    자주 하는 오해"After=는 대상을 강제로 켜지 않고 그냥 기다린다." 반만 맞다. 대상이 켜질 때만 기다린다. 대상이 켜지지 않으면 기다리지 않는다. 그리고 차이만 말하면 답이 끝나지 않는다. "그래서 둘을 함께 썼다"는 결론까지 말한다.

    생각해 볼 질문네트워크 대기가 timeout으로 실패했다. Wants=를 쓴 서비스와 Requires=를 쓴 서비스는 각각 어떻게 될까? 스스로 다시 연결하는 프로그램이라면 어느 쪽이 나을까?

    직접 확인 
    systemctl show <서비스> -p Wants -p Requires -p After
systemctl list-dependencies <서비스>
systemctl is-active network-online.target

    재시작 정책과 재시작 제한

    왜 알아야 하나자동 재시작은 일시적 장애를 사람 없이 복구한다. 그러나 설정 오류처럼 다시 켜도 안 고쳐지는 원인에서는 같은 실패를 끝없이 반복한다. 켤 때 큰 데이터를 읽는 서비스는 반복할 때마다 비용이 크다.

    • Restart=: 언제 다시 켤지다. always(어떻게 끝나든), on-failure(실패로 끝날 때만) 등.
    • RestartSec=: 다시 켜기 전에 기다리는 시간이다.
    • 시작 횟수 제한: StartLimitIntervalSec= 구간 안에 StartLimitBurst=번 넘게 켜지면 멈춘다(failed 상태). 기본은 10초에 5번이다.
    • 제한이 걸리지 않는 경우: 기본 구간 10초에 5번이 넘으려면 2초보다 자주 켜져야 한다. RestartSec=이 그보다 길면 이 제한에 닿지 않는다. 그래서 서비스가 끝없이 다시 켜진다.
    • 끝없는 재시작이 나쁜 이유
      • 원인이 고쳐지지 않는다: 옵션 오타, 커널 값 부족은 다시 켜도 같다.
      • 비용이 크다: 켤 때마다 큰 상태 파일을 읽거나, 내려받기를 다시 할 수 있다.
      • 장애가 늦게 보인다: 서비스는 "켜지는 중"으로 보이고, 로그만 쌓인다.
    • 개선 방법
      1. 제한을 서비스에 맞게 둔다: 예 StartLimitIntervalSec=30min + StartLimitBurst=5. 반복 실패면 멈추고 사람이 본다.
      2. 간격을 점점 늘린다: RestartSteps=, RestartMaxDelaySec=(systemd 254부터).
      3. 재시작 횟수를 감시한다: NRestarts 값이 늘면 알림. 멈췄을 때 알림을 보내는 unit을 OnFailure=에 건다.
    자주 하는 오해"Restart=always를 쓴 것 자체가 실수다." 일시적 장애를 자동으로 복구하려는 선택은 맞다. 빠진 것은 제한이다. 인정할 범위를 좁혀서 말한다: 의도(자동 복구) → 빠진 것(반복 실패의 제한) → 개선(제한, 간격 늘리기, 알림).

    생각해 볼 질문재시작 제한에 걸려 서비스가 멈췄다. 새벽에 사람이 없을 때 이것은 자동 재시작보다 나은 결과일까? 어떤 서비스에서 답이 바뀔까?

    직접 확인 
    systemctl show <서비스> -p Restart -p RestartUSec -p StartLimitIntervalUSec -p StartLimitBurst -p NRestarts
systemctl --version | head -1          # RestartSteps를 쓸 수 있나
journalctl -u <서비스> | grep -c 'Started'
systemctl reset-failed <서비스>       # 제한에 걸린 상태를 지운다

    CPU 사용량의 단위: "코어 1개 미만"의 뜻

    왜 알아야 하나"이 작업은 코어 0.2개를 쓴다"는 말을 코어를 쪼개 가진다는 뜻으로 읽으면, CPU 계획과 top의 숫자를 잘못 읽는다.

    • 정의: CPU 사용량은 "정해진 시간 동안 코어가 그 작업을 실행한 시간"이다. 1초 중 0.2초를 실행했으면 0.2 코어다. top의 %CPU로는 20%다.
    • 시분할: 스레드는 할 일이 있을 때만 코어에서 돈다. 할 일이 없으면 잠든다(sleep). 그동안 그 코어는 스케줄러가 고른 다른 스레드를 실행한다. 그래서 한 코어를 여러 스레드가 시간으로 나누어 쓴다.
    • 한 스레드의 최대: 스레드 하나는 한순간에 코어 하나에서만 돈다. 그래서 스레드 하나의 최대는 1 코어(100%)다. 여러 스레드를 가진 프로세스는 100%를 넘을 수 있다(예: 4 스레드가 쉬지 않으면 400%).
    • 코어 수의 단위: nproc와 top이 세는 것은 논리 CPU다. 하이퍼스레딩이 켜져 있으면 물리 코어 하나가 논리 CPU 둘이다. 논리 CPU 둘이 같은 물리 코어의 실행 장치를 나누어 쓰므로, 처리량이 두 배가 되지는 않는다.
    • load average와의 차이: load average는 사용률이 아니다. 실행 중이거나 실행을 기다리는 스레드 수(리눅스는 디스크를 기다리는 D 상태도 셈)의 평균이다. 그래서 CPU가 한가해도 디스크 대기 때문에 load가 높을 수 있다.
    자주 하는 오해"어떤 작업이든 코어를 최소 1개는 써야 한다." 코어는 작업에 통째로 묶이지 않는다. 작업이 실행되는 시간만 그 코어를 쓰고, 나머지 시간에는 다른 스레드가 쓴다. 그래서 1개 미만이 정상이다.

    생각해 볼 질문어떤 작업이 평균 0.2 코어를 쓴다고 측정되었다. 이 숫자만으로 그 작업이 다른 작업의 지연을 늘리지 않는다고 말할 수 있을까? 평균이 가리는 것은 무엇일까?

    직접 확인 
    nproc; lscpu | grep -E 'Thread|Core|Socket'   # 논리 CPU 수, 물리 코어 구성
top -H -p <pid>              # 스레드별 %CPU
pidstat -u -t -p <pid> 1     # 스레드별 사용률 (sysstat)
mpstat -P ALL 1              # 코어별 사용률
cat /proc/loadavg

    nice와 CPU 우선순위

    왜 알아야 하나같은 서버에서 중요한 일과 덜 중요한 일이 CPU를 나눠 쓰면, 바쁠 때 중요한 일이 늦어진다. nice는 이 다툼에서 누구에게 더 많은 시간을 줄지를 정하는 가장 간단한 손잡이다.

    • 정의: 일반 스케줄링 정책(SCHED_OTHER)의 스레드에 붙는 우선순위 값이다. 범위는 −20(가장 높음)부터 19(가장 낮음)까지이고, 기본값은 0이다.
    • 동작: 리눅스 스케줄러(CFS, 6.6부터 EEVDF)는 nice 값을 가중치로 바꾼다. nice가 1 오를 때마다 가중치가 약 1.25배 작아진다. 그래서 CPU를 두고 다툴 때 받는 시간 몫이 약 10%씩 준다.
    • 다툼이 있을 때만 효과가 있다: 놀고 있는 코어가 있으면 nice가 높은 스레드도 바로 돈다. nice는 "덜 받는다"이지 "막는다"가 아니다.
    • 단위는 스레드다: 리눅스에서 nice는 스레드마다 따로 있다. 그래서 프로그램이 일부 스레드(예: 외부 요청을 처리하는 스레드)만 nice를 올릴 수 있다. renice는 기본으로 프로세스의 스레드 하나에만 적용된다.
    • 권한: nice를 올리는(우선순위를 낮추는) 일은 누구나 한다. 낮추려면(음수) root나 CAP_SYS_NICE가 필요하다.
    • 다른 손잡이와 구별
      • 실시간 정책(SCHED_FIFO, SCHED_RR, chrt): nice와 다른 체계다. 일반 스레드보다 항상 먼저 돈다. 잘못 쓰면 시스템을 멈춘다.
      • cgroup의 CPUWeight=: 서비스(cgroup) 사이의 몫이다. nice는 같은 cgroup 안의 스레드 사이에서 작동한다.
      • CPU 고정(taskset, CPUAffinity=): 몫이 아니라 어느 코어에서 도는지를 정한다.
    자주 하는 오해"nice를 올리면 그 스레드의 CPU 사용량이 그만큼 제한된다." 다툼이 없으면 제한이 없다. 상한을 걸려면 cgroup의 CPUQuota= 같은 다른 손잡이를 쓴다.

    생각해 볼 질문덜 중요한 스레드의 nice를 올렸는데도 중요한 스레드가 여전히 늦다. CPU 시간 말고 두 스레드가 함께 다툴 수 있는 자원은 무엇이 있을까?

    직접 확인 
    ps -eLo pid,tid,ni,pri,comm | grep <이름> | head   # 스레드별 nice
top -H -p <pid>                                  # NI 열
renice -n 5 -p <tid>                             # 스레드 하나의 nice를 5로
systemctl show <서비스> -p Nice -p CPUWeight -p CPUQuotaPerSecUSec

    NUMA

    왜 알아야 하나CPU 소켓이 둘 이상인 서버에서는 메모리를 읽는 속도가 "어느 CPU가 어느 메모리를 읽나"에 따라 다르다. 큰 자료구조를 RAM에 두는 프로그램은 그 메모리가 어디에 놓였는지에 따라 성능이 달라진다.

    • 정의: NUMA(Non-Uniform Memory Access)는 CPU와 메모리를 여러 묶음(NUMA 노드)으로 나눈 구조다. 각 노드는 자기 CPU 코어와 자기 메모리를 가진다.
    • 로컬과 원격: CPU는 자기 노드의 메모리(로컬)를 빠르게 읽는다. 다른 노드의 메모리(원격)는 노드 사이의 연결을 거쳐서 지연이 더 길고 대역폭이 더 좁다. 연결 자체도 공유 자원이라 붐빌 수 있다.
    • 리눅스의 기본 배치: first-touch: 메모리를 할당할 때가 아니라 page를 처음 쓸 때(page fault 때) frame을 고른다. 그때 그 스레드가 돌던 CPU의 노드에 둔다. 그래서 한 스레드가 큰 자료구조를 혼자 채우면 메모리가 한 노드에 몰린다.
    • 메모리 정책
      • local(기본): 처음 쓴 CPU의 노드
      • bind: 정한 노드에만
      • preferred: 정한 노드를 먼저, 모자라면 다른 노드
      • interleave: page마다 노드를 번갈아 둔다. 평균 지연을 고르게 하고, 한 노드의 메모리가 먼저 차는 것을 막는다. 대신 모든 접근의 일부가 원격이 된다.
    • 정하는 방법: numactl --interleave=all <명령>, systemd의 NUMAPolicy=와 NUMAMask=(systemd 243부터), 프로그램 안의 set_mempolicy/mbind.
    • 장치도 노드에 붙는다: NIC와 NVMe도 PCIe로 한 노드에 붙어 있다. 그 장치의 인터럽트와 데이터를 같은 노드의 CPU가 처리하면 원격 접근이 준다.
    • 판단의 순서: 먼저 재고 나서 바꾼다. 노드별 메모리가 한쪽으로 크게 치우쳤는지, 원격 접근이 많은지 본 뒤에 정책을 바꾼다.
    자주 하는 오해"메모리는 할당할 때 어느 노드에 둘지 정해진다." 기본 정책에서는 처음 쓸 때 정해진다. 그래서 할당한 스레드가 아니라, 처음 채운 스레드가 어느 CPU에서 돌았는지가 배치를 정한다.

    생각해 볼 질문한 프로세스가 RAM의 대부분을 쓰는 서버에서, 그 프로세스를 bind 정책으로 한 노드에 묶으면 어떤 일이 생길까? 다른 노드에 빈 메모리가 많아도 그럴까?

    직접 확인 
    lscpu | grep -i numa                      # 노드 수, 노드별 CPU 번호
numactl --hardware                        # 노드별 메모리, 노드 사이 거리
numastat -p <pid 또는 이름>               # 프로세스의 노드별 메모리
cat /sys/class/net/<nic>/device/numa_node # NIC가 붙은 노드
systemctl show <서비스> -p NUMAPolicy -p NUMAMask

    Solana의 계정 모델

    왜 알아야 하나Solana에서는 지갑, 프로그램, 토큰 잔고, 투표 정보가 모두 "계정"이다. 계정의 구조와 owner 규칙을 알아야 RPC 조회와 색인이 무엇을 찾는지 설명할 수 있다.

    • 모든 계정의 구조는 같다: lamports(잔고), data(바이트 배열), owner(소유 프로그램), executable(실행 가능 여부). 종류는 구조가 아니라 owner와 executable의 값으로 나뉜다.
    • 규칙: 계정의 data를 고치고 lamports를 빼는 일은 owner 프로그램만 한다. owner는 항상 프로그램이다. 서명하는 지갑은 코드가 없어서 owner가 될 수 없다.
    • 하는 일로 본 세 갈래: Solana는 코드와 상태를 다른 계정에 나눈다.
      1. 서명하는 계정(지갑): 개인키가 있다. 트랜잭션에 서명하고 수수료를 낸다. owner는 System Program이고 data가 없다. SOL 잔고만 직접 가진다.
      2. 실행하는 계정(프로그램): executable = true. 코드만 있고 상태는 없다. 업그레이드할 수 있는 프로그램은 둘로 나뉜다: 주소만 가진 프로그램 계정과, 바이트코드를 가진 programdata 계정. owner는 로더 프로그램이다.
      3. 저장하는 계정(데이터): 상태만 있다. owner 프로그램만 고친다. 예: 토큰 계정, mint 계정, Vote·Stake 계정, sysvar(Clock, Rent 등 클러스터 상태).
    • owner와 authority: 계정의 owner = 고치는 코드(프로그램). data 안의 authority 칸 = 허락하는 사람(서명자). 예: 프로그램을 업그레이드할 수 있는 사람은 programdata의 data 안 upgrade authority 칸에 적는다. 이 칸을 비우면 아무도 고칠 수 없다.
    • 토큰
      • mint 계정: 토큰 종류 하나를 정의한다. 그 주소가 토큰의 ID다. 총 발행량, 소수점 자리수, 발행 권한(mint authority), 동결 권한을 가진다. 누가 얼마를 가졌는지는 갖지 않는다.
      • 토큰 계정: "어느 mint의 토큰을, 어느 지갑이, 얼마" 가졌는지를 data에 적는다. 계정의 owner는 Token 프로그램이고, data 안의 owner 칸이 지갑 주소다. 지갑은 토큰을 보낼 때 그 owner로서 서명한다.
      • ATA(Associated Token Account): 지갑 하나와 mint 하나에 두는 기본 토큰 계정이다. 주소는 지갑 주소와 mint 주소로 계산한다.
    • PDA: 프로그램이 주소를 계산해서 만든 계정이다. 개인키가 없다. 그 프로그램만 그 주소로 서명할 수 있다.
    • 왜 나누나: 트랜잭션은 읽고 쓸 계정을 미리 적는다. 상태가 계정마다 따로 있어서, 쓰는 계정이 겹치지 않는 트랜잭션은 병렬로 실행할 수 있다.
    자주 하는 오해(1) "프로그램 계정의 주인은 서명하는 계정이다." 계정의 owner는 항상 프로그램이다. 사람의 권한은 data 안의 authority 칸에 있다. (2) "mint 계정에 보유자가 등록되어 있다." 방향이 반대다. mint는 보유자를 모른다. 토큰 계정이 mint 주소를 가리킨다. (3) "지갑은 SOL만 거래한다." 지갑은 토큰도 보내고 받는다. 다만 토큰 잔고가 지갑 안이 아니라 따로 있는 토큰 계정에 있다.

    생각해 볼 질문"이 지갑이 가진 토큰 전부"를 찾으려면 노드는 무엇을 훑어야 할까? 그 일이 자주 들어오면 노드는 무엇을 미리 만들어 둘 수 있을까?

    RPC 노드의 보조 색인

    왜 알아야 하나RPC 노드가 받는 조회의 일부는 "이 조건에 맞는 계정 전부"다. 색인이 없으면 이 조회 하나가 모든 계정을 훑는다. 색인이 있으면 빠르지만 RAM을 크게 쓴다. 이 둘 사이의 선택이 RPC 노드의 RAM 계획을 정한다.

    • 기본 색인: 계정 주소 → 그 계정의 최신 버전이 저장소의 어디에 있나. "이 주소의 계정"을 바로 찾는다. 트랜잭션을 실행할 때도 매번 쓴다. 그러나 "이 조건에 맞는 계정 전부"는 찾지 못한다.
    • 보조 색인: 키 → 그 키에 속한 계정 주소들을 미리 만든 표다. Agave에는 세 가지가 있다.
      • 프로그램별: owner 프로그램 → 그 프로그램이 owner인 계정들. 모든 계정이 들어간다(지갑은 System Program 아래). getProgramAccounts가 쓴다.
      • 토큰 owner별: 지갑 주소 → 그 지갑의 토큰 계정들. 토큰 계정만 들어간다. getTokenAccountsByOwner가 쓴다.
      • 토큰 mint별: mint 주소 → 그 토큰의 토큰 계정들. 토큰 계정만 들어간다. mint 필터가 있는 getProgramAccounts, getTokenLargestAccounts가 쓴다.
    • 토큰 색인의 키는 data 안에 있다: 토큰 owner별 색인의 "owner"는 계정의 owner(Token 프로그램)가 아니라, 토큰 계정 data 안의 owner 칸(지갑)이다. 두 토큰 색인 모두 결과는 토큰 계정이다. 사람이나 토큰 이름이 아니다.
    • 대가
      • RAM: 보조 색인은 RAM의 해시표다. 힙에 있는 익명 메모리라서 RAM이 모자라도 커널이 버릴 수 없다. 계정 수가 많을수록 커진다.
      • 쓰기 비용: 계정이 바뀔 때마다 색인도 고친다. 실행(replay)이 이 일을 함께 한다.
    • 색인이 없으면: 그 조회는 해당 프로그램의 계정을 모두 훑은 뒤 거른다. 요청 하나가 RPC 스레드와 CPU를 오래 잡는다.
    • 무거운 조회는 실행을 늦출 수 있다: 큰 결과를 모으는 동안 색인의 일부에 잠금을 잡으면, 같은 자리를 고치려는 실행이 기다린다. 그래서 요청 수 제한, 필터 없는 요청 거절, 스레드 우선순위(nice) 같은 보호를 함께 생각한다.
    자주 하는 오해(1) "토큰 owner별 색인은 사용자가 가진 토큰의 종류를, mint별 색인은 그 토큰을 가진 사용자를 돌려준다." 둘 다 토큰 계정을 돌려준다. 종류(mint)와 사용자(owner)는 그 토큰 계정의 data 안에 있다. (2) "색인이 RAM에 있다 = 파일을 mmap해 둔 상태다." 보조 색인은 힙의 익명 메모리다.

    생각해 볼 질문RAM이 모자라 색인 하나를 꺼야 한다. 무엇을 기준으로 고를까? 끄기 전에 할 수 있는 중간 단계는 무엇이 있을까?

    slot, leader, epoch

    왜 알아야 하나Solana의 기록은 slot 번호로 정리된다. slot과 블록을 같은 것으로 보면 "slot 번호와 블록 높이가 왜 다른가"를 설명하지 못한다.

    • slot의 정의: leader 일정표의 번호 붙은 차례다. slot마다 leader가 한 명 정해져 있다. 그 leader는 그 slot에 블록을 최대 하나 만든다.
    • 시간은 그다음: slot에는 목표 길이가 있다. 그러나 정의의 중심은 시간이 아니라 차례다.
    • 빈 slot: leader가 죽거나 늦으면 그 slot은 건너뛴다(skip). 그래서 slot 번호와 블록 높이(block height)는 다르다.
    • leader가 하는 일: 트랜잭션을 모으고, 실행하고, 블록으로 만들어 보낸다. "모은다"만으로는 부족하다.
    • leader window: 한 leader가 slot 4개를 연속으로 맡는다.
    • epoch: slot 432,000개다. leader 일정표는 epoch마다 stake 비율로 다시 만든다. stake 변경과 기능(feature) 활성화도 epoch 경계에서 적용된다.
    자주 하는 오해(1) "slot은 리더가 블록을 만드는 시간이다." 시간보다 먼저 "번호 붙은 차례"다. (2) "slot은 블록 하나가 들어가는 단위다." 최대 하나다. 빈 slot이 있다.

    생각해 볼 질문네트워크에서 빈 slot의 비율이 갑자기 늘었다. 노드 운영자로서 의심할 원인은 무엇이 있을까? 자기 노드가 leader일 때 빈 slot이 생겼다면 무엇부터 볼까?

    직접 확인 (Solana CLI) 
    solana epoch-info                 # 지금 epoch, epoch 안의 slot 위치, block height
solana leader-schedule | head     # slot별 leader
solana block-production           # leader별 맡은 slot, 건너뛴 slot

    snapshot

    왜 알아야 하나노드를 새로 켜거나 다시 맞출 때 snapshot에서 시작한다. snapshot에 무엇이 있고 무엇이 없는지를 알아야, 켠 노드가 어떤 질문에 답할 수 있는지 안다.

    • 정의: 특정 slot에서 모든 계정(account)의 상태와 bank 상태를 저장한 파일이다.
      • 계정: 지갑, 토큰 계정, 프로그램 같은 상태 저장 단위다.
      • bank 상태: slot, epoch, stake 정보, 최근 blockhash 목록, 수수료 상태 등.
      • 어느 slot인지가 파일 이름에 있다: snapshot-<slot>-<hash>.tar.zst
    • 들어 있지 않은 것: 블록과 트랜잭션의 기록이다. 기록은 ledger에 있다. 그래서 snapshot으로 켠 노드는 그 slot 이전의 기록을 갖고 있지 않다.
    • 왜 쓰나: 새 노드가 genesis부터 모든 블록을 다시 실행(replay)하지 않고, 그 slot부터 시작해서 뒤의 블록만 replay하려고.
    • 두 종류: full(전체 상태)과 incremental(마지막 full 뒤에 바뀐 계정만). 노드는 둘을 주기적으로 만들고, 정해진 수만 남긴다.
    • 믿는 방법: 받은 snapshot의 hash가 신뢰하는 validator들이 gossip에 알린 hash와 같아야 쓴다. 위조된 snapshot을 막는다.
      • 운영자가 적는 것은 hash가 아니라 신뢰할 노드의 identity 공개키다. hash는 snapshot마다 바뀌어서 미리 적으면 곧 낡는다. 공개키는 바뀌지 않는다.
      • 그 노드들은 새 snapshot을 만들 때마다 (slot, hash)를 gossip에 알린다. gossip 메시지에는 보낸 노드의 서명이 있다. 그래서 "이 hash를 정말 그 노드가 알렸다"를 검사한다.
      • 받는 곳을 그 노드들의 RPC로 좁히는 선택도 있다. 나쁜 노드에서 큰 파일을 다 받은 뒤에야 위조를 아는 시간을 줄인다. 대가는 받을 곳이 적어지는 것이다. 그 노드들이 모두 응답하지 않으면 시작하지 못한다.
    • entrypoint와 다른 점: entrypoint는 gossip에 처음 들어가기 위한 주소(host:port)다. 다른 노드 목록, 밖에서 보이는 내 주소, 네트워크 구분값(shred version)을 받는다. 데이터를 믿는 기준이 아니다. 들어간 뒤에는 다른 노드와 직접 통신한다.
    • 비교: Bitcoin의 assumeutxo도 기록 없이 "지금 상태"(UTXO 집합)를 가져와 시작한다.
    자주 하는 오해(1) "신뢰 명단에 적은 값은 유효한 snapshot의 hash다." 명단에는 노드의 공개키를 적는다. hash는 그 노드들이 서명해서 알린 최신 값을 쓴다. (2) "네트워크에 참여하는 모든 계정의 한 순간을 저장한 것." 세 곳을 다듬는다. "참여하는"은 노드나 사용자 목록처럼 들린다. "한 순간"은 "특정 slot"으로 말한다. 계정만이 아니라 bank 상태도 있다. 그리고 "무엇"에 "왜 쓰나"(replay를 줄이려고)를 붙여야 이해한 답으로 들린다.

    생각해 볼 질문오래된 snapshot으로 노드를 켜면 무엇이 늘어날까? snapshot을 자주 만들수록 노드는 무엇을 더 쓰게 될까?

    직접 확인 
    ls -lh <snapshot 디렉터리>        # 파일 이름의 slot, full과 incremental
solana slot                        # 지금 slot과 비교해 얼마나 뒤인가

    합의의 변화: TowerBFT + PoH에서 Alpenglow(Votor)로

    왜 알아야 하나예전 자료는 "slot은 PoH로 센다"고 설명한다. Alpenglow 뒤에는 이 설명이 맞지 않는다. 투표의 자리가 바뀌어서 블록의 내용과 노드의 일도 바뀌었다.

    • 전: TowerBFT + PoH
      • PoH: leader가 SHA-256을 쉬지 않고 이어서 계산한다. 해시 사슬이 "시간이 흘렀다"는 증거(검증 가능한 시계)다. 정해진 tick 수가 지나면 slot이 끝난다.
      • 투표: validator가 투표를 트랜잭션으로 만들어 블록에 넣었다. 블록 공간의 큰 몫이 투표였다.
    • 후: Votor
      • 투표가 블록 밖으로 나갔다. validator끼리 투표를 직접 주고받고, 모은 서명을 인증서(certificate)로 만든다. 투표 서명은 BLS 방식이다.
      • PoH가 없다. 공통 시계 없이 stake 투표의 인증서가 순서를 정한다.
      • finality가 훨씬 짧아진다(발표 기준 100~150ms 수준 목표).
    • 공통 시계 없이 slot을 진행하는 방법
      • slot 번호와 leader는 일정표로 미리 정해져 있다. 시계와 상관없다.
      • 앞 블록의 인증서가 모이면 노드 안에서 ParentReady 사건이 생긴다. 그 순간 각 노드가 자기 타이머를 켠다. leader는 이때 블록을 만들기 시작한다.
      • 정해진 timeout 안에 블록이 오지 않으면 노드는 skip 투표를 한다. skip 인증서가 모이면 다음 slot으로 간다. 네트워크가 계속 멈추면 timeout을 조금씩 늘린다.
      • 타이머는 벽시계가 아니라 monotonic clock으로 잰다. NTP가 시각을 바꿔도 영향이 없다. 문제가 되는 것은 시계가 가는 속도의 차이(drift)뿐인데, 수백 ms 구간에서는 아주 작다.
    • 노드 운영에서 보이는 변화: 블록에 투표 트랜잭션이 없어서 TPS 숫자와 블록의 구성이 바뀐다. 그래서 블록 하나의 크기, 저장 공간 계산을 다시 해야 한다. 노드는 PoH 서비스를 돌리지 않는다.
    자주 하는 오해(1) "slot은 PoH로 만든다." Alpenglow 전의 설명이다. (2) "노드마다 시계가 다르면 slot을 맞출 수 없다." 노드는 "지금 몇 시인가"를 보지 않는다. "어떤 사건 뒤에 얼마나 지났나"만 잰다. 그래서 시각이 같을 필요가 없다.

    validator 키와 키를 두는 자리

    왜 알아야 하나노드 데이터는 지우고 다시 받을 수 있다. 키는 다시 만들 수 없다. 키마다 권한이 달라서, 서버가 뚫렸을 때 무엇을 잃는지가 서버에 둔 키로 정해진다.

    키하는 일서버에 두나
    identity노드의 신원. gossip에서 나를 증명하고, leader일 때 블록에 서명한다둔다
    vote account 키투표 계정의 주소를 정한다. 계정을 만들 때 한 번 서명에 쓴다만든 뒤에는 필요 없다
    authorized voter투표에 서명한다. 기본은 identity와 같은 키다둔다
    authorized withdrawer투표 계정의 돈을 빼고, 권한을 바꾼다. 가장 중요하다두지 않는다(오프라인, 하드웨어 지갑)
    • 원칙: 서버에는 노드가 돌아가는 데 꼭 필요한 키만 둔다. 서버가 뚫려도 withdrawer가 없으면 돈과 권한은 지켜진다.
    • 투표하지 않는 노드(RPC): identity 하나만 있으면 된다.
    • stake 계정의 키(stake authority, withdraw authority)는 stake를 맡긴 사람이 가진다. 노드 서버와 관계없다.
    • 데이터와 키를 나눈다: ledger와 accounts는 깨지면 통째로 지우고 snapshot에서 다시 시작한다. 이것이 흔한 복구 방법이다. 키를 같은 디렉터리에 두면 함께 지워진다. 키를 잃으면 새 키 = 다른 노드다. 투표 노드라면 stake와의 연결이 끊긴다.
    • 파일 권한: 노드 프로세스의 사용자가 읽을 수 있어야 한다. 더 막으려면 주인을 root, 그룹을 노드 사용자, 권한을 640으로 둔다. 그러면 노드는 읽기만 하고 고치지 못한다.
    자주 하는 오해"키를 홈에 두면 root 권한으로 관리할 수 있다." root는 어느 자리의 파일이든 읽는다. 그래서 이것은 자리를 고르는 이유가 되지 못한다. 이유는 (1) 키는 다시 만들 수 없는 자격 증명이라 지울 수 있는 데이터 디렉터리 밖에 둔다, (2) 작아서 OS 디스크에 둬도 된다, (3) 노드 사용자가 읽을 수 있어야 한다, 이다.

    생각해 볼 질문노드 사용자가 identity 키 파일을 쓸 수도 있다. 공격자가 노드 프로세스를 장악하면 이것으로 무엇을 할 수 있을까? 쓰기를 막으면 무엇이 불편해질까?

    직접 확인 
    ls -l <키 파일>                          # 주인, 그룹, 권한
solana-keygen pubkey <키 파일>           # 공개키만 출력
solana vote-account <투표 계정 주소>      # voter, withdrawer가 누구인가

    accounts와 ledger를 다른 디스크에 두는 이유

    왜 알아야 하나노드가 클러스터를 따라가지 못하는 흔한 원인 하나는 디스크 지연이다. 두 데이터의 I/O 모양이 달라서, 같은 장치에 두면 한쪽이 다른 쪽을 늦춘다.

    • accounts(상태): replay가 slot마다 트랜잭션을 실행하면서 계정을 읽고 새 버전을 쓴다. 작은 무작위 읽기가 아주 많다. RPC의 계정 조회도 여기를 읽는다. 지연에 민감하다: replay가 slot 안에 끝나야 해서, 읽기가 늦으면 노드가 뒤처진다.
    • ledger(기록, RocksDB): 들어오는 블록 조각이 순차 쓰기로 꾸준히 쌓인다. RocksDB compaction이 주기적으로 큰 파일을 읽고 다시 쓴다. 이때 I/O가 한꺼번에 몰린다. 오래된 slot을 지우는 정리도 있다.
    • 같은 장치면: compaction이 장치의 대역폭과 큐를 차지하는 동안 accounts의 작은 읽기가 그 뒤에서 기다린다. NVMe도 IOPS와 대역폭에 한계가 있다. 쓰기가 많으면 SSD 내부 GC로 지연이 갑자기 튄다.
    • 나눠서 얻는 것은 "따로 서는 줄"이다
      • CPU 쪽은 원래 병렬이다. 스레드는 각자 다른 코어에서 요청을 보낸다. NVMe는 코어마다 요청 큐를 따로 가질 수 있다(blk-mq). 데이터 이동은 장치가 DMA로 한다.
      • 막히는 곳은 장치다. 장치 하나의 처리 능력은 정해져 있다. 장치를 나누면 처리 능력도 둘이 되어, 한쪽이 바빠도 다른 쪽의 줄은 짧다.
    • I/O 말고 이유 두 개: 용량(ledger는 한도까지 계속 커져서 accounts의 자리를 먹을 수 있다), 장애 범위(디스크 하나가 고장 나도 한쪽만 다시 받는다).
    • 면접에서는 꼭지 하나: "ledger의 큰 쓰기가 accounts의 작은 읽기를 막아 replay가 늦어진다." 용량과 장애 범위는 꼬리 질문에 꺼낸다.
    자주 하는 오해(1) "디스크를 나누면 다른 코어가 읽기와 쓰기를 병렬로 실행한다." 병렬은 디스크가 하나여도 있다. 나누는 것은 장치의 줄(대기열)이다. (2) "accounts는 ms 단위로 읽고 쓴다." NVMe 읽기는 µs 단위다. 숫자 대신 "replay가 slot 안에 끝나야 해서 지연에 민감하다"로 말한다. (3) "accounts 디스크는 replay를 실행한다." 디스크는 실행하지 않는다. replay는 CPU가 하고, 디스크는 replay가 읽고 쓰는 상태를 저장한다. (4) "ledger는 지난 기록을 받아온다." 지금 들어오는 블록을 계속 쌓고, 보관 기간 동안 조회에 답한다.

    생각해 볼 질문디스크가 하나뿐인 서버에서 같은 간섭을 줄이려면 무엇을 해 볼 수 있을까? 각 방법은 무엇을 대가로 내줄까?

    shred

    왜 알아야 하나블록은 shred 단위로 퍼지고, 받고, 저장된다. 노드가 블록을 잃었을 때 다시 만들 수 있는지, 저장 공간을 무엇으로 세는지가 shred의 구조에서 나온다.

    • 정의: leader가 블록 데이터를 UDP 패킷 하나에 들어가게 자른 단위다.
    • 자르는 대상: 트랜잭션이 아니라 블록(slot의 entry들)이다. leader는 블록 데이터를 이어 붙인 뒤 자른다. 그래서 트랜잭션 하나가 shred 두 개에 걸칠 수 있다.
    • 크기를 정하는 이유: 속도가 아니라 패킷 하나에 맞추는 것이다. 패킷이 경로의 MTU보다 크면 IP 단계에서 조각난다. 조각 하나만 잃어도 패킷 전체를 잃는다.
    • 두 종류
      • data shred: 블록 데이터를 담는다.
      • coding shred: 복구용이다. Reed-Solomon 이레이저 코딩으로 data shred에서 만든다.
    • 묶음(FEC set): data shred와 coding shred를 묶음 단위로 만든다. Agave 소스의 기본은 묶음마다 data 32개, coding 32개다. 그래서 묶음에서 어느 shred든 절반까지 잃어도 data를 다시 만든다.
    • 위조 방지: leader가 묶음의 Merkle root에 서명한다. 각 shred에는 그 서명과 Merkle 증명이 있다. 받는 노드는 shred 하나만 받아도 leader의 것인지 검사한다.
    • 퍼짐과 저장: Turbine으로 노드에서 노드로 퍼진다. 그래도 모자란 shred는 repair로 다른 노드에 요청한다. 받은 shred는 blockstore(ledger)에 shred 단위로 저장된다.
    자주 하는 오해(1) "트랜잭션을 잘게 쪼갠 것이다." 쪼개는 대상은 블록 데이터다. (2) "shred 하나에 데이터와 복구용이 반반 들어 있다." shred는 두 종류로 따로 있고, 반반인 것은 묶음이다. (3) "검증용 shred가 있다." 두 번째 종류는 복구용이다. 검증은 leader의 서명으로 한다. (4) "UDP로 빠르게 보내려고 자른다." 크기의 이유는 패킷 하나에 들어가야 한다는 것이다.

    생각해 볼 질문coding shred의 비율을 data와 같게 하지 않고 더 낮추면 무엇을 얻고 무엇을 잃을까? 패킷 손실이 많은 네트워크에서는 어느 쪽이 나을까?

    트랜잭션 meta

    왜 알아야 하나블록과 트랜잭션을 조회하는 RPC 노드는 트랜잭션 원문만으로는 부족하다. 사용자는 "실행 결과"를 묻는다. 결과 기록을 저장할지, 얼마나 자세히 저장할지가 응답의 내용과 디스크 사용량을 함께 정한다.

    • 원문과 meta
      • 트랜잭션 원문: 누가 무엇을 요청했나. 서명, 계정 목록, 명령(instruction).
      • meta: 실행한 뒤의 결과. 성공·실패와 오류, 수수료, 실행 전후의 잔고(SOL, 토큰), 쓴 계산 단위.
    • meta 안의 자세한 칸
      • log messages: 프로그램이 실행 중에 남긴 로그 문자열
      • inner instructions: 프로그램이 실행 중에 다른 프로그램을 부른 기록(CPI, cross-program invocation). 예: 교환 프로그램이 Token 프로그램을 불러 토큰을 옮긴다.
      • return data: 프로그램이 돌려준 값
    • 노드의 선택: 노드는 meta를 저장하지 않을 수도, 저장할 수도 있다. 저장해도 크기가 큰 자세한 칸을 버릴 수 있다. Agave는 기본으로 meta를 저장하지 않고, 저장을 켜도 자세한 세 칸은 기본으로 버린다. 그래서 getBlock, getTransaction의 응답 내용이 노드 설정에 따라 다르다.
    • 같은 응답인지 확인하는 방법: 같은 slot이나 서명으로 두 노드에 같은 요청을 보낸다. 결과를 정렬해서(jq -S) 비교한다(diff). 이때 두 노드가 모두 그 slot을 보관하고 있어야 한다. 보관 기간 밖이면 한쪽만 오류를 준다.
    • 대가: meta는 트랜잭션마다 생긴다. 자세한 칸까지 저장하면 기록 저장소가 커진다. 용량 계산에 이 몫을 넣는다.
    자주 하는 오해"meta를 저장하는 설정만 켜면 공개 RPC와 같은 응답이 된다." 자세한 칸을 버리는 설정이 따로 있으면, 저장은 해도 응답의 칸이 빠진다. 그리고 보관 기간이 다르면 오래된 slot의 응답이 다르다.

    생각해 볼 질문두 노드의 응답을 diff로 비교했더니 한 칸만 다르다. 설정 차이 말고 무엇이 그 차이를 만들 수 있을까?
